Bash Redirecionamento

Normalmente, o que um comando responde aparece na tela, e o que ele lê vem do teclado. Redirecionar é trocar esses caminhos: mandar a resposta para um arquivo, separar as mensagens de erro, jogar fora o que não interessa ou ler a entrada de um arquivo. Quem faz isso é o Bash, antes de o comando começar.

Você vai aprender
  • Os três canais de todo comando: entrada (0), saída (1) e erro (2).
  • >, >>, <, 2>, 2>>, &> e 2>&1, e por que >arq 2>&1 é diferente de 2>&1 >arq.
  • Como jogar fora o que não interessa com /dev/null e mandar suas mensagens para o canal de erro com >&2.
  • Como se proteger de apagar arquivos com noclobber, e o que fazer com "Permissão negada" e "redirecionamento ambíguo".

Os três canais de um comando

Todo programa nasce com três "canos" ligados. Cada um tem um número (o descritor de arquivo), e é por esse número que você o redireciona.

                 ┌───────────┐ ── 1 · saída (stdout) ──►  tela
  teclado ──►    │  comando  │
  0 · entrada    └───────────┘ ── 2 · erro (stderr)  ──►  tela
  (stdin)
NúmeroNomeEm inglêsSem redirecionar, liga em…
0Entrada padrãostandard input, stdinTeclado
1Saída padrãostandard output, stdoutTela: a resposta "normal"
2Saída de errostandard error, stderrTela também: avisos e erros

Como a saída e o erro chegam na mesma tela, parecem uma coisa só. Mas são canais separados, e é isso que permite guardar a resposta num arquivo e ainda ver os erros, ou o contrário.

Gravar a saída num arquivo: >

O sinal > (maior que) liga o canal 1 a um arquivo em vez da tela.

ls Documentos
O comando, que normalmente mostraria a lista na tela.
>
"Mande a saída (canal 1) para…". É o mesmo que 1>.
lista.txt
…este arquivo. Se não existir, é criado; se existir, é esvaziado antes.
$ ls Documentos > lista.txt
$ cat lista.txt
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt

O que você está vendo:

  • O primeiro comando não mostrou nada: a lista foi para o arquivo. O código de saída foi 0, como sempre que dá certo.
  • No arquivo, cada nome está numa linha. Quando a saída não é a tela, o ls não organiza em colunas nem colore.

Atenção: > substitui o conteúdo

$ echo "primeira linha" > teste.txt
$ echo "segunda linha" > teste.txt
$ cat teste.txt
segunda linha                       « a primeira sumiu, sem nenhum aviso
O arquivo é esvaziado antes de o comando rodar

O Bash prepara os redirecionamentos antes de executar o comando. Por isso sort frutas.txt > frutas.txt apaga a lista: quando o sort vai ler, o arquivo já está vazio. Grave sempre num arquivo diferente.

Acrescentar ao final: >>

Dois sinais, >>, gravam no fim do arquivo, sem apagar o que já estava lá (append, "anexar"). É o que você quer para listas, diários e logs.

echo "kiwi"
Produz uma linha de texto.
>>
"Acrescente ao final de…".
frutas.txt
O arquivo. Também é criado se não existir.
$ echo "kiwi" >> frutas.txt
$ tail -n 3 frutas.txt
maçã
banana
kiwi                                « a linha nova entrou no fim

Missão: grave a lista de arquivos da pasta Downloads num arquivo chamado downloads.txt. Depois acrescente, no fim dele, a linha fim da lista. Confira com cat downloads.txt.

Ler a entrada de um arquivo: <

O < faz o caminho contrário: liga o canal 0 (entrada) a um arquivo, em vez do teclado. Muitos comandos aceitam o nome do arquivo como argumento, mas há uma diferença sutil:

$ wc -l Documentos/notas.txt
4 Documentos/notas.txt       « o wc abriu o arquivo e sabe o nome dele
$ wc -l < Documentos/notas.txt
4                            « o wc só recebeu o conteúdo; quem abriu foi o Bash

A segunda forma é ótima em scripts, quando você quer só o número:

$ echo "Tenho $(wc -l < Documentos/notas.txt) tarefas anotadas"
Tenho 4 tarefas anotadas

O $( ) coloca a saída de um comando dentro de outro; ele é explicado em Substituição de Comando. Para mandar várias linhas digitadas como entrada (<<EOF) ou uma linha só (<<<), veja Here-docs e Here-strings.

Prova: o erro "vaza" para a tela

Agora a Ana pede dois itens ao ls: a pasta Documentos, que existe, e nada, que não existe. A saída vai para um arquivo:

$ ls Documentos nada > saida.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente    « apareceu mesmo assim!
$ cat saida.txt
Documentos:
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt                                                         « o arquivo só tem a parte boa

O > redirecionou só o canal 1. A mensagem de erro saiu pelo canal 2, que continua ligado na tela. Para mexer no erro, diga o número dele.

Redirecionar os erros: 2> e 2>>

ls Documentos nada
Um comando que vai produzir saída e erro.
2>
"Mande o canal 2 (erros) para…". Sem espaço entre o 2 e o >.
erros.txt
…este arquivo.
$ ls Documentos nada 2> erros.txt
Documentos:
acesso.log  alunos.csv  notas.txt  projetos  relatorio.odt      « a saída boa veio para a tela
$ cat erros.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente   « o erro foi para o arquivo

Assim como >>, o 2>> acrescenta em vez de substituir. Rodando de novo, os erros se acumulam:

$ ls nada 2>> erros.txt
$ cat erros.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente

Jogar fora: /dev/null

/dev/null é um arquivo especial que descarta tudo o que recebe: o "buraco negro" do sistema. Use quando o resultado interessa e os avisos não. Exemplo: procurar arquivos .txt em duas pastas, uma delas proibida para a Ana:

$ find ~/Documentos /root -name "*.txt"
/home/ana/Documentos/notas.txt
find: ‘/root’: Permissão negada          « ruído
$ find ~/Documentos /root -name "*.txt" 2>/dev/null
/home/ana/Documentos/notas.txt           « só o que interessa

Do outro lado, comando >/dev/null descarta a resposta normal e deixa os erros. É útil quando você só quer saber se o comando deu certo, pelo código de saída.

Saída e erro no mesmo arquivo: 2>&1 e &>

Às vezes você quer tudo junto, por exemplo num log. Primeiro mande a saída para o arquivo; depois diga que o erro (2) vai para o mesmo lugar que a saída (1).

ls Documentos nada
O comando.
> tudo.txt
Primeiro passo: o canal 1 passa a apontar para tudo.txt.
2>&1
Segundo passo: o canal 2 passa a apontar para onde o 1 aponta agora. O & diz que 1 é um canal, não um arquivo chamado "1".
$ ls Documentos nada > tudo.txt 2>&1
$ cat tudo.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
Documentos:
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt

O erro apareceu primeiro porque o ls reclama dos itens inexistentes antes de listar os que existem. O Bash tem um atalho que faz a mesma coisa: &> (e &>> para acrescentar).

$ ls Documentos nada &> tudo.txt

Por que a ordem importa

O Bash lê os redirecionamentos da esquerda para a direita, um de cada vez. O 2>&1 não quer dizer "erro e saída juntos para sempre": quer dizer "o 2 aponta para onde o 1 aponta neste momento". Compare:

  > tudo.txt 2>&1                     2>&1 > tudo.txt
  ─────────────────                    ─────────────────
  1. >tudo.txt  1 → tudo.txt           1. 2>&1     2 → tela  (o 1 ainda era a tela)
  2. 2>&1      2 → tudo.txt           2. >tudo.txt 1 → tudo.txt
  resultado: os dois no arquivo        resultado: só a saída no arquivo
$ ls Documentos nada 2>&1 > tudo2.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente   « o erro continuou na tela
$ cat tudo2.txt
Documentos:
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt
Quando 2>&1 vem antes de propósito

Em comando 2>&1 | grep erro, o 2>&1 antes do | está certo: o canal 1 já aponta para o pipe, e o erro vai junto. Os detalhes estão na próxima aula.

Suas mensagens no canal de erro: >&2

O echo escreve no canal 1. Num script, avisos como "Contando…" ou "Erro: falta o arquivo" deveriam ir para o canal 2, para não se misturar com o resultado. A forma é >&2 ("o canal 1 deste comando aponta para onde o 2 aponta"):

#!/usr/bin/env bash
echo "Contando linhas de $1..."
wc -l < "$1"

A Ana quer guardar só o número num arquivo. Veja o problema:

$ bash conta.sh frutas.txt > total.txt
$ cat total.txt
Contando linhas de frutas.txt...      « o aviso entrou junto com o resultado
7

Missão: mande a mensagem "Contando linhas de…" para o canal de erro, acrescentando >&2 no fim da linha do echo. Ao rodar, o aviso deve aparecer como erro e o número como saída.

#!/usr/bin/env bash
echo "Contando linhas de $1..."
wc -l < "$1"

#!/usr/bin/env bash
echo "Contando linhas de $1..." >&2
wc -l < "$1"

Com a correção, a saída real fica assim:

$ bash conta.sh frutas.txt > total.txt
Contando linhas de frutas.txt...      « o aviso vem para a tela (canal 2)
$ cat total.txt
7                                     « o arquivo tem só o resultado

Proteção contra apagar: noclobber e >|

Como o > apaga sem perguntar, o Bash tem uma opção de segurança: noclobber (clobber = "atropelar"). Com ela ligada, o > se recusa a sobrescrever um arquivo que já existe.

set
Liga e desliga opções do shell.
-o
"Ligue a opção…" (+o desliga).
noclobber
A opção "não atropele arquivos". Atalho: set -C.
$ set -o noclobber
$ echo "teste" > notas2.txt                « o arquivo não existia: tudo bem
$ echo "outro" > notas2.txt
bash: notas2.txt: impossível sobrescrever arquivo existente
$ echo $?
1
$ echo "outro" >| notas2.txt               « >| = "eu sei, pode sobrescrever"
$ cat notas2.txt
outro
$ set +o noclobber                          « desliga a proteção

O >> continua funcionando com noclobber, porque acrescentar não apaga nada. Para ter a proteção sempre, coloque set -o noclobber no seu ~/.bashrc (veja Arquivos de Inicialização).

Ver na tela e gravar ao mesmo tempo: tee

O > manda tudo para o arquivo e nada para a tela. Quando você quer os dois, use o comando tee (o nome vem da conexão em "T" dos encanamentos), recebendo a saída por um pipe |:

$ ls Documentos | tee lista.txt
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt                « apareceu na tela e foi gravado em lista.txt

O tee e o | são explicados com calma em Pipes.

Quando não funciona

"Permissão negada" ao gravar 
$ echo x > /root/teste.txt
bash: /root/teste.txt: Permissão negada
$ touch protegido.txt; chmod 444 protegido.txt     « um arquivo só de leitura, para o teste
$ ls -l protegido.txt
-r--r--r-- 1 ana ana 0 out 15 10:30 protegido.txt
$ echo x > protegido.txt
bash: protegido.txt: Permissão negada

O que aconteceu: quem abre o arquivo é o Bash (repare no bash: no começo), rodando como a Ana. Ela não pode escrever em /root, nem num arquivo só de leitura (r--). É o mesmo erro de echo "…" >> /etc/hosts.

Como resolver: grave numa pasta sua; ou, num arquivo seu, dê permissão (chmod u+w protegido.txt). Para arquivos do sistema, sudo echo x > /etc/arquivo não funciona: o sudo vale para o echo, mas o > continua sendo feito pelo seu Bash. A forma usual é echo x | sudo tee -a /etc/arquivo, em que o tee, rodando como root, abre o arquivo.

"redirecionamento ambíguo" (ambiguous redirect) 
$ arquivo="meu relatorio.txt"
$ echo "oi" > $arquivo
bash: $arquivo: redirecionamento ambíguo
$ echo "oi" > $naoexiste
bash: $naoexiste: redirecionamento ambíguo

O que aconteceu: depois do > tem que sobrar um nome de arquivo. Sem aspas, $arquivo virou duas palavras (meu e relatorio.txt) e $naoexiste virou zero palavras (a variável está vazia).

Como resolver: coloque a variável entre aspas duplas: echo "oi" > "$arquivo". Se a variável está vazia, descubra por quê (erro de digitação no nome?). Veja Aspas e Escapes.

O arquivo ficou vazio 
$ sort frutas.txt > frutas.txt
$ wc -l frutas.txt
0 frutas.txt                      « a lista foi apagada

O que aconteceu: o > esvaziou frutas.txt antes de o sort ler. O sort leu um arquivo vazio e não reclamou.

Como resolver: grave em outro arquivo e depois renomeie: sort frutas.txt > ordenado.txt && mv ordenado.txt frutas.txt. O conteúdo perdido não volta, a não ser que exista uma cópia.

"Arquivo ou diretório inexistente" ao gravar 
$ ls > relatorios/hoje.txt
bash: relatorios/hoje.txt: Arquivo ou diretório inexistente

O que aconteceu: o > cria o arquivo, mas não cria pastas. A pasta relatorios não existe.

Como resolver: mkdir -p relatorios e repita o comando.

"impossível sobrescrever arquivo existente"

O que aconteceu: o noclobber está ligado (talvez no seu ~/.bashrc). Confira com set -o | grep noclobber.

Como resolver: se tiver certeza, use >|; para desligar, set +o noclobber.

Usei 2 > erros.txt e o erro continuou na tela 
$ ls nada 2 > erros.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
ls: não foi possível acessar '2': Arquivo ou diretório inexistente
$ cat erros.txt                       « vazio: nenhum erro chegou aqui

O que aconteceu: com espaço, o 2 virou um argumento do ls ("liste também o arquivo 2"), e o > sozinho redirecionou o canal 1. O arquivo ficou vazio.

Como resolver: escreva 2> grudado. O mesmo vale para 2>&1: nada de espaços dentro dele.

Usei 2>&1 e o erro continuou na tela

O que aconteceu: a ordem está trocada (2>&1 > arq). Quando o 2>&1 foi lido, o canal 1 ainda era a tela.

Como resolver: > arq 2>&1, ou o atalho &> arq.

"É um diretório" 
$ echo oi > Documentos
bash: Documentos: É um diretório

O que aconteceu: o destino é uma pasta. Redirecionamento só grava em arquivos.

Como resolver: dê um nome de arquivo dentro da pasta: echo oi > Documentos/oi.txt.

Resumo

  • Todo comando tem três canais: 0 (entrada), 1 (saída) e 2 (erro). O Bash faz os redirecionamentos antes de o comando rodar.
  • > substitui, >> acrescenta, < lê de um arquivo. Eles criam arquivos, mas não pastas.
  • 2> mexe só nos erros; 2>/dev/null joga os erros fora; >&2 manda suas mensagens para o canal de erro.
  • Para juntar tudo: > arq 2>&1 (nessa ordem) ou &> arq.
  • set -o noclobber protege contra o >; >| força. Variável em redirecionamento vai entre aspas.
