Bash Menus e Cores

Alguns scripts conversam com uma pessoa: mostram um menu, perguntam "tem certeza?", pintam de vermelho o que deu errado, mostram uma barra de progresso. Nesta aula você vai ver as ferramentas do Bash para isso (select, as sequências de cores ANSI, o tput, o read) e, tão importante quanto, quando não usar cores, para não sujar arquivos e pipes.

Você vai aprender
  • A montar um menu numerado com select, PS3 e REPLY.
  • A colorir textos com sequências ANSI (\e[31m) e com tput.
  • A usar cores só quando a saída é um terminal ([[ -t 1 ]]) e a respeitar NO_COLOR.
  • A fazer barra de progresso e spinner com \r.
  • A perguntar sim/não e a ler senhas sem mostrá-las (read -s).

Menus com select

O select é um laço que mostra uma lista numerada, lê o número digitado e guarda a opção escolhida numa variável. Ele repete até encontrar um break. A Ana fez um menu para a lista de frutas:

#!/usr/bin/env bash
PS3="Escolha uma opção (número): "
select opcao in "Ver frutas" "Contar frutas" "Sair"; do
  case $opcao in
    "Ver frutas") sort -u frutas.txt ;;
    "Contar frutas") wc -l < frutas.txt ;;
    "Sair") echo "Tchau!"; break ;;
    *) echo "Opção inválida: $REPLY" ;;
  esac
done
PS3="…"
O texto da pergunta. É o terceiro prompt do Bash (o PS1 é o do terminal, o PS2 o de continuação). Sem ele, o select mostra só #? .
select opcao in A B C
Mostra 1) A, 2) B, 3) C e espera um número. Itens com espaço vão entre aspas.
opcao
Recebe o texto do item escolhido (Contar frutas), ou fica vazia se o número não existir.
$REPLY
O que a pessoa digitou, exatamente (2, 7, abc…).
case … esac
Decide o que fazer com cada opção (case). O *) pega números inválidos.
break
Sai do laço do select. Sem ele, o menu nunca termina (a não ser com Ctrl+D).

Esta sessão foi feita num terminal de verdade, digitando 2, 7, Enter vazio, 1 e 3:

Repare: depois de cada resposta, o select mostra só a pergunta, e não o menu inteiro. O menu volta quando a pessoa aperta Enter sem digitar nada. O menu e a pergunta saem na saída de erro, para não se misturarem ao resultado se você redirecionar a saída do script.

A lista pode vir de um array ou de um curinga

select arq in *.txt; do … monta um menu com os arquivos da pasta. select item in "${opcoes[@]}"; do … usa um array. Assim o menu se adapta sozinho.

Cores com sequências ANSI

Terminais entendem sequências de escape ANSI: códigos que não aparecem na tela, mas mudam a cor ou o estilo do texto seguinte. Todas começam com o caractere ESC (código 27), escrito \e (ou \033) no printf, seguido de [, números e m:

\e[31m   texto vermelho   \e[0m
│ │ │                   └── 0 = volta ao normal (reset)
│ │ └ m = "fim do código de cor"
│ └ 31 = vermelho
└ ESC (caractere 27)

1Negrito31Texto vermelho
2Fraco (dim)32Texto verde
3Itálico (nem todo terminal)33Texto amarelo
4Sublinhado34Texto azul
7Inverte frente e fundo35Texto magenta
40–47Cor de fundo (mesma ordem)36Texto ciano
90–97Texto em versão clara37Texto branco
38;5;NUma das 256 cores (N de 0 a 255)1;32Vários juntos, com ;: negrito verde

Para ver o que realmente é enviado, passe a saída pelo cat -v, que mostra o ESC como ^[:

$ printf '\e[31mvermelho\e[0m normal\n' | cat -v
^[[31mvermelho^[[0m normal
$ echo -e '\e[1;32mnegrito verde\e[0m' | cat -v
^[[1;32mnegrito verde^[[0m

No terminal (sem o cat -v), o resultado é este:

ana@notebook: ~
ana@notebook:~$ printf '\e[31mvermelho\e[0m normal\n'
vermelho normal
ana@notebook:~$ echo -e '\e[1;32mnegrito verde\e[0m'
negrito verde
printf '\e[31m…'
O printf entende \e no formato. É a forma recomendada.
echo -e '\e[…'
O echo só entende com -e, e o -e não existe em todo shell.
$'\e[31m'
As aspas $'…' criam o caractere ESC já na hora de guardar numa variável: vermelho=$'\e[31m'.
Sempre feche com \e[0m

Se o script esquecer o reset (ou morrer no meio), o terminal continua colorido depois que ele termina. Se isso acontecer, rode tput sgr0 (ou reset, que reinicia o terminal inteiro).

O jeito portável: tput

Os códigos ANSI funcionam em praticamente todo terminal moderno, mas o jeito "oficial" de pedir uma capacidade ao terminal é o tput. Ele consulta o banco de dados terminfo (pelo valor de $TERM) e imprime a sequência certa para aquele terminal:

$ tput setaf 1 | cat -v; echo
^[[31m                                         « setaf 1 = a mesma sequência do \e[31m
$ tput bold | cat -v; echo
^[[1m
$ tput sgr0 | cat -v; echo
^[(B^[[m                                       « o reset completo do terminfo
$ tput cols; tput lines
80
24
$ tput colors
256

Um uso prático do tput cols: uma linha separadora que ocupa a largura toda do terminal:

largura=$(tput cols)
printf '%*s\n' "$largura" '' | tr ' ' '-'

O %*s do printf imprime um texto vazio com a largura pedida (só espaços), e o tr troca os espaços por -.

Cores só no terminal: [[ -t 1 ]] e NO_COLOR

As sequências de cor são caracteres de verdade. Se a saída do script for para um arquivo ou para outro programa, elas vão junto, como lixo: ^[[31m no meio do texto, um grep que não acha a palavra. Comandos bem-educados, como o ls --color=auto, só usam cores quando a saída é um terminal. O teste -t faz essa pergunta:

[[ -t 1 ]]
Verdadeiro se o canal 1 (saída) está ligado a um terminal (tty). -t 2 testa a saída de erro; -t 0, a entrada.
${NO_COLOR:-}
NO_COLOR é uma convenção (no-color.org): se a variável existir com qualquer valor, o usuário não quer cores. O :- evita erro com set -u.
#!/usr/bin/env bash
if [[ -t 1 && -z ${NO_COLOR:-} ]]; then
  vermelho=$'\e[31m' verde=$'\e[32m' negrito=$'\e[1m' normal=$'\e[0m'
else
  vermelho='' verde='' negrito='' normal=''
fi
printf '%sOK%s  backup concluído\n' "$verde" "$normal"
printf '%sERRO%s  disco cheio\n' "$negrito$vermelho" "$normal"

As cores ficam em variáveis. Se a saída não for um terminal (ou se NO_COLOR estiver definida), as variáveis ficam vazias e o mesmo printf sai sem cor. Sessão num terminal de verdade, mostrando os bytes com cat -v:

$ bash cores.sh | cat -v                       « a saída é um pipe: sem cores
OK  backup concluído
ERRO  disco cheio
$ NO_COLOR=1 bash cores.sh                     « no terminal, mas o usuário pediu sem cor
OK  backup concluído
ERRO  disco cheio
$ [[ -t 1 ]] && echo "terminal" || echo "não é terminal"
terminal
$ { [[ -t 1 ]] && echo "terminal" || echo "não é terminal"; } | cat
não é terminal

E rodando bash cores.sh direto no terminal:

ana@notebook: ~
ana@notebook:~$ bash cores.sh
OK  backup concluído
ERRO  disco cheio
E as mensagens de erro?

Se você colore mensagens que vão para a saída de erro, teste [[ -t 2 ]]: é possível que a saída normal vá para um arquivo e os erros continuem na tela, ou o contrário.

Barra de progresso: o \r

O caractere \r (carriage return, "retorno do carro", herança das máquinas de escrever) volta o cursor para o começo da mesma linha, sem pular para a próxima. Escrevendo de novo por cima, a linha parece se atualizar:

#!/usr/bin/env bash
total=20
for ((i = 1; i <= total; i++)); do
  pct=$(( i * 100 / total ))
  cheio=$(( i * 30 / total ))
  barra=$(printf '%*s' "$cheio" '' | tr ' ' '#')
  printf '\r[%-30s] %3d%%' "$barra" "$pct"
  sleep 0.05
done
printf '\n'
cheio=$(( i * 30 / total ))
Quantos # a barra de 30 posições deve ter agora.
printf '%*s' "$cheio" '' | tr ' ' '#'
Gera cheio espaços e troca por #.
\r
Volta ao início da linha antes de desenhar.
%-30s
A barra alinhada à esquerda num espaço de 30, completada com espaços.
%3d%%
A porcentagem com 3 posições, e %% para escrever o próprio %.
printf '\n'
No fim, pula a linha, para o prompt não grudar na barra.

No terminal, você vê uma única linha que vai enchendo até:

$ bash progresso.sh
[##############################] 100%

Por baixo, são 20 desenhos separados por \r, que o cat -v mostra como ^M:

$ bash progresso.sh | cat -v
^M[#                             ]   5%^M[###                           ]  10%^M[####                          ]  15%…
…                                              « encurtado: 20 desenhos ao todo, na mesma linha

Spinner

Quando não dá para saber quanto falta, um "spinner" (pião) mostra que o script está vivo. Este acompanha um comando em segundo plano (&) e gira enquanto ele existir:

#!/usr/bin/env bash
sleep 1 &
pid=$!
quadros='|/-\'
i=0
while kill -0 "$pid" 2>/dev/null; do
  printf '\r%s trabalhando...' "${quadros:i++%4:1}"
  sleep 0.1
done
printf '\rpronto!          \n'
sleep 1 &
O "trabalho" demorado, em segundo plano. $! é o PID dele (Jobs).
kill -0 "$pid"
O sinal 0 não faz nada; só testa se o processo ainda existe (Sinais).
${quadros:i++%4:1}
Pega 1 caractere da posição i % 4 e soma 1 em i: | / - \ em rodízio (Manipular Strings).
'\rpronto! '
Os espaços apagam o resto do texto anterior, que era mais comprido.

Perguntar sim ou não

#!/usr/bin/env bash
confirmar() {
  local resp
  while true; do
    read -rp "$1 [s/n] " resp
    case ${resp,,} in
      s|sim) return 0 ;;
      n|não|nao) return 1 ;;
      *) echo "Responda s ou n." ;;
    esac
  done
}
if confirmar "Apagar os arquivos temporários?"; then
  echo "Apagando..."
else
  echo "Nada foi apagado."
fi
read -rp "…" resp
-p mostra a pergunta; -r não interpreta barras (read).
${resp,,}
A resposta em minúsculas, para aceitar S, Sim, SIM. bash 4.0+
return 0 / return 1
A função vira um "teste": dá para usar direto no if.
while true
Repete a pergunta até vir uma resposta válida.
$ bash simnao.sh
Apagar os arquivos temporários? [s/n] talvez
Responda s ou n.
Apagar os arquivos temporários? [s/n] S
Apagando...

Uma variação comum é ter uma resposta padrão para o Enter vazio, indicada em maiúscula: [S/n] (Enter = sim) ou [s/N] (Enter = não). Para isso, inclua o texto vazio num dos casos: s|sim|"").

Senhas: read -s

A opção -s (silent) não mostra o que é digitado:

#!/usr/bin/env bash
read -rsp "Senha: " senha
echo
echo "A senha tem ${#senha} caracteres."

$ bash senha.sh
Senha:                                         « a pessoa digitou 10 caracteres; nada aparece
A senha tem 10 caracteres.

O echo logo depois do read pula a linha, porque o Enter digitado também não foi mostrado. Lembre que a senha fica numa variável comum: não a mostre, não a passe como argumento de outro comando (argumentos aparecem no ps) e não a grave em arquivos.

Quando não funciona

Aparece \e[31m ou ^[[31m no texto, em vez da cor

O que aconteceu: com \e[31m literal, o comando não interpretou o escape: echo sem -e, ou aspas simples comuns numa variável (c='\e[31m'). Com ^[[31m, o escape foi gerado, mas a saída foi para um arquivo ou para o less, que não interpretam cores.

Como resolver: use printf ou $'\e[31m'; para o arquivo, desligue as cores fora do terminal com [[ -t 1 ]]. No less, a opção -R mostra as cores.

O terminal ficou todo colorido depois do script

O que aconteceu: faltou o \e[0m no fim de uma mensagem, ou o script foi interrompido no meio.

Como resolver: tput sgr0 agora; no script, feche cada cor e, por segurança, ponha trap 'tput sgr0' EXIT (trap).

O select não para nunca

O que aconteceu: falta o break no caso de saída, ou o case compara com um texto diferente do item ("sair" × "Sair").

Como resolver: confira o texto exato; Ctrl+D (fim da entrada) também encerra o select, com código 1.

tput: No value for $TERM and no -T specified (no cron ou em CI)

O que aconteceu: sem terminal, não há TERM, e o tput não sabe o que responder.

Como resolver: só use tput depois de testar [[ -t 1 ]]; para a largura, use um padrão: largura=$(tput cols 2>/dev/null || echo 80). Veja Agendar Scripts.

A barra de progresso vira dezenas de linhas

O que aconteceu: o printf tem \n no fim (ou foi usado echo), então cada desenho pula de linha.

Como resolver: só \r no começo, sem \n no fim; um único printf '\n' depois do laço.

Resumo

  • select + case monta menus numerados; PS3 é a pergunta, $REPLY o que foi digitado, break sai.
  • Cores: \e[31m (vermelho), \e[1m (negrito), \e[0m (normal), com printf ou $'…'; ou tput setaf/bold/sgr0.
