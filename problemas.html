Bash Erros Comuns

A mensagem de erro é a melhor amiga de quem escreve scripts: ela diz onde (o arquivo e a linha) e, quase sempre, o quê. Esta página reúne as mensagens que mais aparecem, exatamente como o Bash 5.3 as escreve em português, com a causa, como confirmar, a solução e a aula do assunto. Use Ctrl+F e cole um pedaço da mensagem que você recebeu.

Como ler uma mensagem de erro do Bash 
$ bash conserte.sh
conserte.sh: linha 4: $arquivo: redirecionamento ambíguo
conserte.sh:
Quem reclamou: o script. No terminal, aparece bash:; quando é um programa, o nome dele (cp:, mkdir:).
linha 4:
Onde. Em erros de sintaxe, a linha pode ser a seguinte à do erro real (o Bash só percebe o problema depois).
$arquivo:
O pedaço que causou o problema.
redirecionamento ambíguo
O quê. Procure esta parte nesta página.

Se as suas mensagens saem em inglês, o sistema está em inglês (echo $LANG); a tabela de cada seção mostra também o original. Para depurar, bash -n script.sh confere a sintaxe e bash -x script.sh mostra cada comando antes de rodar. Veja Depurar.

Ao rodar um comando ou script

bash: xyz: comando não encontrado (command not found) 
$ sl
bash: sl: comando não encontrado
$ echo $?
127

O que aconteceu: o Bash não achou nada com esse nome: nem alias, nem função, nem comando interno, nem programa nas pastas do PATH. Código 127. Causas comuns: erro de digitação (sl em vez de ls); programa não instalado; programa instalado numa pasta fora do PATH. No Ubuntu, um aviso extra pode sugerir o pacote que tem o comando. Como confirmar: type nome e echo $PATH. Como resolver: corrija o nome, instale o programa, ou rode-o pelo caminho completo. Veja PATH e Onde os Comandos Moram.

bash: s.sh: comando não encontrado, mas o arquivo está ali 
$ ls s.sh
s.sh
$ s.sh
bash: s.sh: comando não encontrado

O que aconteceu: por segurança, a pasta atual não está no PATH; um nome sem / só é procurado lá. Como resolver: ./s.sh (o ./ diz "nesta pasta"), ou instale-o em ~/.local/bin. Veja Formas de Executar.

bash: ./s.sh: Permissão negada (Permission denied) 
$ ./s.sh
bash: ./s.sh: Permissão negada
$ echo $?
126

O que aconteceu: o arquivo não tem permissão de execução (código 126 = "achei, mas não posso executar"). Como confirmar: ls -l s.sh mostra -rw-…, sem x. Como resolver: chmod +x s.sh, ou rode com bash s.sh (aí só é preciso permissão de leitura). Se o arquivo está num pendrive ou partição montada com noexec, só o bash s.sh funciona. Veja Seu Primeiro Script.

/bin/bash^M: interpretador incorreto: Arquivo ou diretório inexistente (bad interpreter) 
$ ./crlf.sh
bash: ./crlf.sh: /bin/bash^M: interpretador incorreto: Arquivo ou diretório inexistente

O que aconteceu: o script foi salvo com quebras de linha do Windows (CRLF, \r\n). O \r (que o terminal mostra como ^M) grudou no fim do shebang, e o sistema procura um programa chamado bash␍, que não existe. Com #!/usr/bin/env bash, a mensagem é env: ‘bash\r’: Arquivo ou diretório inexistente. Como confirmar: file crlf.sh diz "with CRLF line terminators"; cat -A crlf.sh mostra ^M$ no fim das linhas. Como resolver: sed -i 's/\r$//' crlf.sh (ou dos2unix crlf.sh), e configure o editor para salvar com quebras de linha "LF"/"Unix". Veja Seu Primeiro Script.

cd: $'/tmp\r': Arquivo ou diretório inexistente e outros $'…\r' 
$ bash win.sh
win.sh: linha 1: cd: $'/tmp\r': Arquivo ou diretório inexistente
Olá, Ana!

O que aconteceu: o mesmo CRLF, num script rodado com bash win.sh (que não usa o shebang). Cada linha termina com um \r invisível, que vira parte do último argumento: cd procura a pasta /tmp␍. Algumas linhas parecem funcionar, mas a saída também carrega o \r. Como resolver: como no caso anterior, sed -i 's/\r$//' win.sh.

/bin/bassh: interpretador incorreto 
$ ./ruim.sh
bash: ./ruim.sh: /bin/bassh: interpretador incorreto: Arquivo ou diretório inexistente
$ echo $?
126

O que aconteceu: o caminho do shebang está errado (aqui, digitado errado; em outros sistemas, o bash fica em outro lugar, como /usr/local/bin/bash no FreeBSD ou no Homebrew). Como resolver: use #!/usr/bin/env bash, que procura o bash no PATH. Veja Seu Primeiro Script.

Erros de sintaxe

O Bash lê cada comando composto inteiro (o if até o fi, o for até o done) antes de executar. Se a estrutura estiver quebrada, nada daquele bloco roda. bash -n script.sh encontra esses erros sem executar nada.

erro de sintaxe próximo ao token inesperado `fi' (syntax error near unexpected token) 
x=1
if [ $x = 1 ] then
  echo um
fi
$ bash sint.sh
sint.sh: linha 4: erro de sintaxe próximo ao token inesperado `fi'
sint.sh: linha 4: `fi'

O que aconteceu: falta o ; (ou a quebra de linha) antes do then. Sem ele, then virou mais um argumento do [, o if nunca recebeu seu then, e o Bash só percebeu ao encontrar o fi (por isso a linha 4, e não a 2). A segunda linha da mensagem mostra o trecho onde ele parou. Como resolver: if [ $x = 1 ]; then. Veja if.

erro de sintaxe próximo ao token inesperado `echo' 
$ bash sint2.sh
sint2.sh: linha 1: erro de sintaxe próximo ao token inesperado `echo'
sint2.sh: linha 1: `for i in 1 2; echo $i; done'

O que aconteceu: faltou o do: for i in 1 2; do echo $i; done. O "token inesperado" é a primeira palavra que não se encaixa na gramática; o erro de verdade está logo antes dela. Outros casos clássicos: ( inesperado (array ou extglob num shell que não entende, veja bash × sh), done inesperado (um do a mais ou um while a menos), else inesperado (um fi antes da hora). Veja for.

encontrado EOF inesperado enquanto procurava por `"' correspondente (unexpected EOF while looking for matching) 
echo "oi
echo fim
$ bash eof.sh
eof.sh: linha 1: encontrado EOF inesperado enquanto procurava por `"' correspondente

O que aconteceu: uma aspa foi aberta e nunca fechada; o Bash leu até o fim do arquivo (EOF, end of file) procurando o par. A linha indicada é a da aspa aberta. No terminal, o mesmo erro aparece como o prompt > esperando você fechar a aspa (aperte Ctrl+C). Como resolver: feche a aspa; um editor com cores de sintaxe mostra o problema na hora (todo o resto do arquivo fica da cor de texto). Veja Aspas.

erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 1 
$ bash eof2.sh
eof2.sh: linha 3: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 1

O que aconteceu: um bloco não foi fechado: falta o fi do if que começou na linha 1 (ou o done de um laço, o } de uma função, o esac de um case). Como resolver: feche o bloco; indentar o código deixa visível qual bloco ficou aberto. Veja if.

aviso: here-document na linha 1 delimitado pelo fim do arquivo (desejava `FIM') 
cat <<FIM
oi
  FIM
echo depois
$ bash here.sh
here.sh: linha 4: aviso: here-document na linha 1 delimitado pelo fim do arquivo (desejava `FIM')
oi
  FIM
echo depois

O que aconteceu: a palavra que fecha o here-doc precisa estar sozinha na linha, sem espaços antes ou depois. Com o FIM indentado, ele não foi reconhecido e o resto do arquivo virou texto (repare que echo depois foi impresso, e não executado). Como resolver: tire os espaços, ou use <<-FIM, que aceita indentação com TABs (não espaços). Veja Here-docs.

${x y}: substituição incorreta (bad substitution) 
$ echo ${x y}
bash: ${x y}: substituição incorreta

O que aconteceu: o que está dentro de ${ } não é uma forma válida: espaço no nome, operador errado, ou um recurso que a sua versão não tem (${x,,} no Bash 3.2 do macOS, ${x@U} antes do 5.1). Rodando com sh, a mensagem é Bad substitution. Como resolver: confira a forma na Cola de Expansões e a versão com bash --version. Veja Expansão de Parâmetros.

Testes com [ ]

O [ é um comando como outro qualquer: recebe palavras como argumentos, depois que as variáveis foram expandidas e separadas. Quase todos os erros abaixo vêm de uma variável sem aspas. Com [[ ]] (palavra reservada do Bash) eles não acontecem. Veja Testes.

[: número excessivo de argumentos (too many arguments) 
$ arq="meu arquivo.txt"
$ [ $arq = x ]
bash: [: número excessivo de argumentos

O que aconteceu: sem aspas, $arq virou duas palavras e o [ recebeu meu arquivo.txt = x: argumentos demais para um teste. O mesmo acontece com uma variável que contém um curinga que casa vários arquivos. Como resolver: [ "$arq" = x ], ou [[ $arq = x ]].

[: meu: esperava operador binário (binary operator expected) 
$ [ -f $arq ]
bash: [: meu: esperava operador binário

O que aconteceu: de novo a variável sem aspas: [ -f meu arquivo.txt ] tem três palavras, e com três o [ espera "valor operador valor"; meu deveria ser um operador como =. Como resolver: [ -f "$arq" ].

[: =: esperava operador unário (unary operator expected) 
$ vazio=
$ [ $vazio = sim ] && echo sim
bash: [: =: esperava operador unário

O que aconteceu: a variável estava vazia e, sem aspas, sumiu: [ = sim ]. Com dois argumentos, o [ espera "operador valor" (como -f arq), e = não é um deles. Como resolver: [ "$vazio" = sim ]. Muito comum com $1 quando o script é chamado sem argumentos.

[: abc: esperava número inteiro (integer expression expected) 
$ [ abc -gt 3 ]
bash: [: abc: esperava número inteiro
$ [[ abc -gt 3 ]]; echo $?
1

O que aconteceu: -gt, -lt, -eq… comparam números, e o valor não era um (texto, vazio, 3,5). Repare que no [[ ]] não há mensagem: abc é tratado como uma variável (vale 0), e o teste simplesmente dá falso, o que pode esconder o problema. Como resolver: valide antes com [[ $x =~ ^[0-9]+$ ]]; para comparar textos, use = e !=. Veja Regex.

Variáveis e contas

nome: comando não encontrado ao criar uma variável 
$ nome = Ana
bash: nome: comando não encontrado
$ nome= Ana
bash: Ana: comando não encontrado

O que aconteceu: espaço em volta do =. Com espaços, nome virou um comando com os argumentos = e Ana. No segundo caso, nome= (vazio) valeu só para o comando Ana. Como resolver: nome=Ana, tudo junto; com espaço no valor, nome="Ana Maria". Veja Variáveis: o Básico.

export: `2x=1': não é um identificador válido (not a valid identifier) 
$ export 2x=1
bash: export: `2x=1': não é um identificador válido

O que aconteceu: nome de variável inválido. Nomes só podem ter letras sem acento, números e _, e não podem começar com número: 2x, meu-nome e preço são inválidos. Aparece também em read, declare, local e for. Como resolver: x2, meu_nome, preco. Veja Variáveis.

naoexiste: variável não associada (unbound variable) 
$ set -u; echo $naoexiste; set +u
bash: naoexiste: variável não associada

O que aconteceu: com set -u (parte do modo estrito), usar uma variável que não existe é erro, e o script para. Em geral é um erro de digitação ou um argumento que não veio ($1). Como resolver: corrija o nome, ou dê um padrão quando a ausência for normal: ${1:-}, ${var:-padrão}. Para arrays associativos, conte com ${a[$k]:-0}. Veja set -euo pipefail.

PI: a variável permite somente leitura (readonly variable) 
$ readonly PI=3; PI=4
bash: PI: a variável permite somente leitura

O que aconteceu: a variável foi marcada com readonly (ou declare -r) e não pode mais mudar nesta sessão. Também aparece ao tentar mudar variáveis do Bash como UID. Como resolver: use outro nome, ou abra um novo shell. Veja Variáveis.

08: valor muito grande para esta base de numeração (value too great for base) 
$ echo $(( 08 + 1 ))
bash: 08: valor muito grande para esta base de numeração (token de erro é "08")

O que aconteceu: na aritmética do Bash, um número começado com 0 é octal (base 8), onde os dígitos 8 e 9 não existem. Acontece muito com horas e datas: $(date +%H) às 8h dá 08. Como resolver: force a base 10: $(( 10#08 + 1 )), ou $(( 10#$hora + 1 )). Veja Contas.

divisão por 0 (token de erro é "0 ") 
$ echo $(( 5 / 0 ))
bash: 5 / 0 : divisão por 0 (token de erro é "0 ")

O que aconteceu: o divisor era zero, muitas vezes uma variável vazia ou um total ainda não calculado. Como resolver: teste antes: (( total > 0 )) && echo $(( parte * 100 / total )). Veja Contas.

local: somente pode ser usado em uma função / return: possível retornar (`return') apenas de uma função… 
$ local x=1
bash: local: somente pode ser usado em uma função
$ return 2
bash: return: possível retornar (`return') apenas de uma função ou script carregado (com `source')

O que aconteceu: local e return fora de uma função. No corpo principal do script, use uma variável comum e exit. Veja local, return e Saída.

Arquivos e redirecionamentos

$arquivo: redirecionamento ambíguo (ambiguous redirect) 
$ arq="meu arquivo.txt"
$ echo oi > $arq
bash: $arq: redirecionamento ambíguo

O que aconteceu: depois do > tem de haver um nome de arquivo, e a variável sem aspas virou dois (ou nenhum, se estiver vazia, ou vários, se tiver um curinga). Como resolver: echo oi > "$arq". Veja Redirecionamento.

cat: meu: Arquivo ou diretório inexistente, mas o arquivo existe 
$ cat $arq
cat: meu: Arquivo ou diretório inexistente
cat: arquivo.txt: Arquivo ou diretório inexistente

O que aconteceu: o nome tem espaço e a variável está sem aspas: o cat recebeu dois nomes, nenhum dos dois existe. Como resolver: cat "$arq". A regra de ouro: sempre aspas duplas em volta de variáveis. Veja Aspas.

ls: não foi possível acessar '*.xyz': Arquivo ou diretório inexistente 
$ ls *.xyz
ls: não foi possível acessar '*.xyz': Arquivo ou diretório inexistente

O que aconteceu: nenhum arquivo casou com o curinga, e o Bash passou o texto *.xyz como está. Num laço for f in *.xyz, o laço roda uma vez com f='*.xyz'. Como resolver: confira o padrão; em scripts, shopt -s nullglob faz o curinga sem resultado sumir, ou teste [[ -e $f ]] || continue no laço. Veja Curingas.

mkdir: cannot create directory ‘a/b/c’: Arquivo ou diretório inexistente 
$ mkdir a/b/c
mkdir: cannot create directory ‘a/b/c’: Arquivo ou diretório inexistente

O que aconteceu: as pastas do meio (a e a/b) não existem. (A primeira parte da mensagem sai em inglês mesmo com o sistema em português: a tradução do coreutils não tem essa frase.) Se a mensagem terminar em Permissão negada, você não pode escrever na pasta pai; se for Arquivo existe, o nome já está em uso. Como resolver: mkdir -p a/b/c cria todas as que faltam. Veja Criar, Copiar e Mover.

cp: -r não especificado; omitindo o diretório / É um diretório 
$ cp Documentos alvo
cp: -r não especificado; omitindo o diretório 'Documentos'
$ rm Documentos
rm: não foi possível remover 'Documentos': É um diretório
$ cat Documentos
cat: Documentos: É um diretório

O que aconteceu: o comando espera um arquivo e recebeu uma pasta. Como resolver: cp -r para copiar pastas; rmdir (pasta vazia) ou rm -r (com tudo dentro, cuidado!) para apagar; ls para ver o conteúdo. Veja Criar, Copiar e Mover e Apagar com Segurança.

Lista de argumentos muito longa (Argument list too long) 
$ /bin/true $(seq 1 400000)
bash: /bin/true: Lista de argumentos muito longa

O que aconteceu: o sistema limita o tamanho total dos argumentos de um programa (cerca de 2 MB no Linux). Acontece com rm *.log numa pasta com centenas de milhares de arquivos. Como resolver: não passe tudo de uma vez: find . -name '*.log' -delete, ou printf '%s\0' *.log | xargs -0 rm (o printf é interno, não tem o limite). Veja Pipes e xargs.

Problemas sem mensagem de erro

A variável "some" depois do while 
$ total=0; printf '1\n2\n3\n' | while read -r n; do total=$((total + n)); done; echo "total=$total"
total=0
$ total=0; while read -r n; do total=$((total + n)); done < <(printf '1\n2\n3\n'); echo "total=$total"
total=6

O que aconteceu: cada parte de um pipe roda num subshell. O while depois do | somou tudo, mas na cópia; quando o pipe terminou, a cópia morreu com o total. Como resolver: dê a entrada ao laço sem pipe: done < arquivo ou done < <(comando) (substituição de processo), ou ligue shopt -s lastpipe num script. Veja Subshells e Ler Arquivos Linha a Linha.

O cd do script não muda a pasta do terminal 
$ cat vai.sh
cd /tmp
$ bash vai.sh; pwd
/home/ana

O que aconteceu: o script roda num processo filho; ele mudou a pasta dele e terminou. O mesmo vale para export e variáveis. Como resolver: use uma função ou um alias no .bashrc, ou rode o arquivo com source vai.sh. Veja Formas de Executar.

O script parou no meio, sem dizer nada 
$ cat sete.sh
set -e
echo antes
grep -q nada frutas.txt
echo depois
$ bash sete.sh; echo "código $?"
antes
código 1

O que aconteceu: com set -e, qualquer comando que devolve diferente de 0 encerra o script, e o grep que não acha nada devolve 1 sem escrever erro nenhum. O mesmo acontece com (( x++ )) quando x vale 0. Como confirmar: bash -x sete.sh mostra o último comando executado. Como resolver: para comandos em que "falhar" é normal, use-os num if ou acrescente || true. Veja set -euo pipefail.

O read engoliu a barra invertida 
$ read x <<< 'a\b'; echo "$x"
ab
$ read -r x y z <<< "a\\b c"; echo "$x"
a\b

O que aconteceu: sem -r, o read trata \ como escape e o remove. Caminhos do Windows e expressões regulares saem estragados. Como resolver: use sempre read -r. Veja read.

O alias funciona no terminal, mas no script dá "comando não encontrado" 
$ cat al.sh
alias oi="echo oi"
oi
$ bash al.sh
al.sh: linha 2: oi: comando não encontrado

O que aconteceu: em scripts (shell não interativo), aliases vêm desligados, e os do seu .bashrc nem são carregados. Como resolver: use funções em scripts. Veja alias.

Funciona no terminal, mas não no cron

O que aconteceu: o cron roda o script com um ambiente mínimo: PATH=/usr/bin:/bin, sem o seu .bashrc (nem aliases, nem variáveis que você exportou lá), com sh como shell das linhas do crontab e a pasta pessoal como pasta atual. E a saída, sem redirecionamento, vai para um e-mail local que ninguém lê. Num crontab, o % tem significado especial (vira quebra de linha) e precisa de \%: date +\%F. Como confirmar: acrescente >> ~/cron.log 2>&1 à linha do crontab e leia o log; env > ~/cron-env.txt numa linha de teste mostra o ambiente que o cron dá. Como resolver: caminhos absolutos para arquivos e programas, cd explícito no começo do script, PATH definido no próprio script e saída sempre redirecionada para um log. (Ilustrativo: o cron não roda no laboratório do guia.) Veja Agendar Scripts.

bash: !xyz: event not found ao usar ! no terminal

O que aconteceu: no terminal interativo, ! dentro de aspas duplas chama o histórico (!! repete o comando anterior, !xyz procura um comando começado com xyz). A mensagem sai em inglês. Como resolver: aspas simples (echo 'Oba!') ou set +H. Em scripts, isso não acontece. Veja Histórico.

Roda no bash, quebra no sh

No Debian e no Ubuntu, sh é o dash, um shell POSIX que não entende os recursos exclusivos do Bash. As mensagens dele são em inglês e trazem o número da linha sem a palavra "linha". Acontece quando você roda sh script.sh, ou o shebang é #!/bin/sh. Veja POSIX sh e Bashismos.

$ sh bashismo.sh
bashismo.sh: 3: [[: not found
bashismo.sh: 4: Syntax error: "(" unexpected
$ sh b2.sh
b2.sh: 2: source: not found
b2.sh: 3: Syntax error: "}" unexpected
Mensagem do shRecurso do Bash usadoSaída
[[: not found[[ … ]]rode com bash ou use [ … ]
Syntax error: "(" unexpectedarray arr=(a b), function, extglobbash

A solução quase sempre é a mesma: shebang #!/usr/bin/env bash e rodar com ./script.sh ou bash script.sh, nunca sh script.sh.

Experimente: conserte o script

Missão: este script tem três erros clássicos desta página. Rode, leia as três mensagens e conserte-os até ele mostrar Olá, Ana! O arquivo existe.

#!/usr/bin/env bash
nome = Ana
arquivo="lista de compras.txt"
echo "café" > $arquivo
if [ -f $arquivo ]; then
  echo "Olá, $nome! O arquivo existe."
fi

#!/usr/bin/env bash
nome=Ana
arquivo="lista de compras.txt"
echo "café" > "$arquivo"
if [ -f "$arquivo" ]; then
  echo "Olá, $nome! O arquivo existe."
fi

As mensagens que ele dá, no Bash real:

$ bash conserte.sh
conserte.sh: linha 2: nome: comando não encontrado
conserte.sh: linha 4: $arquivo: redirecionamento ambíguo
conserte.sh: linha 5: [: número excessivo de argumentos
