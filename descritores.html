Bash Descritores de Arquivo

Você já usa os canais 0, 1 e 2 toda vez que escreve >, 2> ou <. Esses números são descritores de arquivo, e o Bash deixa você abrir os seus: o 3, o 4, o 5… Com o comando exec, um arquivo fica aberto durante o script inteiro, e você escreve nele, lê dele ou redireciona tudo de uma vez.

Você vai aprender
  • O que é um descritor e como ver os do seu shell em /proc/$$/fd.
  • Abrir, usar e fechar os seus: exec 3> arquivo, echo … >&3, exec 3>&-, exec 3< arquivo e read -u 3.
  • Ler dois arquivos ao mesmo tempo, linha a linha.
  • Mandar toda a saída de um script para um log com exec > log 2>&1 (e ainda ver na tela, com tee).
  • Trocar a saída e o erro de lugar, deixar o Bash escolher o número ({fd}) e conhecer o /dev/tcp.

O que é um descritor

Quando um programa abre um arquivo, o sistema não devolve o arquivo em si, devolve um número: "de agora em diante, o arquivo que você abriu é o 3". Esse número é o descritor de arquivo (file descriptor, abreviado fd). Para ler ou escrever, o programa só diz o número.

Todo processo já nasce com três descritores abertos, os que você conheceu em Redirecionamento:

NúmeroNomeNormalmente aponta para
0entrada padrão (stdin)o teclado (o terminal)
1saída padrão (stdout)a tela (o terminal)
2saída de erro (stderr)a tela (o terminal)
3 a 9livreso que você abrir
10 em dianteuso interno do Bashevite escolher esses à mão (veja {fd} abaixo)

Vendo os descritores do seu shell

No Linux, a pasta /proc/NÚMERO/fd mostra os descritores abertos de um processo, um link por número. $$ é o número (PID) do seu shell:

$ echo $$
37401
$ ls -l /proc/$$/fd
total 0
lrwx------ 1 ana ana 64 out 16 09:52 0 -> /dev/pts/0      « entrada: o terminal
lrwx------ 1 ana ana 64 out 16 09:52 1 -> /dev/pts/0      « saída: o terminal
lrwx------ 1 ana ana 64 out 16 09:52 2 -> /dev/pts/0      « erro: o terminal
lrwx------ 1 ana ana 64 out 16 09:52 255 -> /dev/pts/0    « cópia que o Bash guarda para si

/dev/pts/0 é a janela de terminal em que você está (o comando tty mostra o nome da sua). Os três canais apontam para ela: por isso você digita no mesmo lugar onde lê as respostas. O 255 é uma cópia que o Bash interativo mantém do terminal; ignore-o.

Abrir um descritor para escrever: exec 3> arquivo

Até agora, cada > abria o arquivo, gravava e fechava, só para aquele comando. O exec sem nenhum comando faz outra coisa: aplica o redirecionamento ao próprio shell, e ele fica valendo até você desfazer.

exec
Sem um comando depois, "aplique estes redirecionamentos ao shell atual, para sempre".
3
O número do descritor que você está criando. Colado no >.
>
Abre para escrita, esvaziando o arquivo (como sempre). >> abriria para acrescentar.
diario.txt
O arquivo.
$ exec 3> diario.txt
$ ls -l /proc/$$/fd
total 0
lrwx------ 1 ana ana 64 out 16 09:52 0 -> /dev/pts/0
lrwx------ 1 ana ana 64 out 16 09:52 1 -> /dev/pts/0
lrwx------ 1 ana ana 64 out 16 09:52 2 -> /dev/pts/0
lrwx------ 1 ana ana 64 out 16 09:52 255 -> /dev/pts/0
l-wx------ 1 ana ana 64 out 16 09:52 3 -> /home/ana/diario.txt   « o novo descritor

O exec não mostrou nada e deixou código de saída 0. Mas o shell agora tem um quarto canal, o 3, aberto para escrita (l-wx: w de write) em diario.txt.

Escrever no descritor: >&3

Para mandar a saída de um comando para o descritor 3, use >&3: "a saída vai para onde o 3 aponta". O & diz que 3 é um descritor, não um arquivo chamado "3".

$ echo "primeira linha" >&3
$ echo "segunda linha" >&3
$ cat diario.txt
primeira linha
segunda linha                     « as duas ficaram: o arquivo continuou aberto entre um echo e outro

Repare: usamos >&3 duas vezes e a primeira linha não foi apagada. Quem esvaziou o arquivo foi o exec 3>, uma vez só. Num laço que grava milhares de linhas, isso também é mais rápido do que abrir e fechar o arquivo a cada volta com >>.

Fechar: exec 3>&-

O - no lugar do número quer dizer "feche". Depois de fechado, usar o 3 é erro:

$ exec 3>&-
$ echo "terceira" >&3
bash: 3: Descritor de arquivo inválido

Feche sempre os descritores que abriu quando não precisar mais deles. No fim de um script, o sistema fecha tudo sozinho, mas fechar explicitamente deixa claro onde o arquivo deixou de ser usado e garante que tudo foi gravado.

Missão: abra o descritor 3 para escrever em compras.txt. Usando >&3, grave as linhas pão e leite. Feche o descritor e confira com cat compras.txt.

Abrir para ler: exec 3< arquivo e read -u 3

Com <, o descritor é aberto para leitura. Cada read nele pega a próxima linha, porque o descritor lembra onde parou.

read
Lê uma linha e guarda numa variável (veja Ler do Teclado).
-u 3
Lê do descritor 3 em vez do 0 (u de unit, "unidade", nome antigo para descritor). Equivale a read <&3.
linha
A variável que recebe a linha.
$ exec 3< frutas.txt
$ read -u 3 linha; echo "$linha"
banana                                « 1ª linha
$ read -u 3 linha; echo "$linha"
maçã                                  « continuou de onde parou
$ read -r linha <&3; echo "$linha"
laranja                               « <&3 é o mesmo que -u 3
$ cat <&3
banana                                « o cat lê o RESTO do arquivo
uva
maçã
banana
$ read -u 3 linha; echo "código: $? linha: [$linha]"
código: 1 linha: []                   « fim do arquivo: read devolve 1
$ exec 3<&-

Compare com read linha < frutas.txt: esse abre o arquivo do zero a cada vez e sempre lê banana. O descritor aberto com exec é como um marcador de livro: guarda a posição.

Quando o arquivo acaba, o read devolve código 1 e deixa a variável vazia. É isso que faz um while read parar.

Ler dois arquivos ao mesmo tempo

Aqui os descritores fazem algo que não dá de outro jeito com um laço só. A Ana tem os nomes num arquivo e as notas em outro, na mesma ordem:

$ printf 'Ana\nBruno\nCarla\n' > nomes.txt
$ printf '9.5\n7.0\n8.5\n' > resultados.txt
#!/usr/bin/env bash
# lê nomes.txt e resultados.txt ao mesmo tempo, linha a linha
exec 3< nomes.txt 4< resultados.txt
while read -r nome <&3 && read -r nota <&4; do
  echo "$nome tirou $nota"
done
exec 3<&- 4<&-
LinhaO que faz
exec 3< nomes.txt 4< resultados.txtAbre os dois arquivos para leitura: um no 3, outro no 4. Um exec aceita vários redirecionamentos.
while read -r nome <&3 && read -r nota <&4; doA cada volta, lê a próxima linha de cada arquivo. O laço continua enquanto as duas leituras derem certo.
echo "$nome tirou $nota"Usa as duas variáveis.
exec 3<&- 4<&-Fecha os dois descritores.
$ bash dois.sh
Ana tirou 9.5
Bruno tirou 7.0
Carla tirou 8.5
$ echo $?
0

Por que não dá com done < nomes.txt? Porque aí as duas leituras viriam do mesmo canal 0, uma linha de cada vez, do mesmo arquivo. Com descritores diferentes, cada read tem o seu "marcador de livro".

Missão: o script abre os dois arquivos, mas só lê os nomes e escreve "tirou ?". Faça o laço ler também uma linha do descritor 4 a cada volta e mostrar a nota de verdade.

#!/usr/bin/env bash
exec 3< nomes.txt 4< resultados.txt
while read -r nome <&3; do
  echo "$nome tirou ?"
done
exec 3<&- 4<&-

#!/usr/bin/env bash
exec 3< nomes.txt 4< resultados.txt
while read -r nome <&3 && read -r nota <&4; do
  echo "$nome tirou $nota"
done
exec 3<&- 4<&-

Ler e escrever no mesmo: <>

exec 5<> arquivo abre para leitura e escrita, sem esvaziar. Ler e escrever andam com a mesma posição:

$ printf 'abcdef\n' > abc.txt
$ exec 5<> abc.txt
$ read -n 3 -u 5 tres; echo "$tres"
abc                                   « leu 3 caracteres; a posição agora é a 4ª
$ echo -n "XY" >&5
$ exec 5>&-
$ cat abc.txt
abcXYf                                « "XY" foi escrito por cima de "de"

É um recurso raro em scripts do dia a dia (serve para arquivos de dispositivo e conexões, como o /dev/tcp mais abaixo), mas é bom reconhecer quando aparecer.

Redirecionar o script inteiro: exec > log 2>&1

Um script de backup que roda sozinho de madrugada precisa guardar tudo o que disse num log. Em vez de pôr >> backup.log 2>&1 em cada linha, ponha um exec no começo:

#!/usr/bin/env bash
exec > backup.log 2>&1
echo "Início: backup de Documentos"
ls Documentos nada
echo "Fim"
exec
Aplica ao shell que roda o script, daqui para baixo.
> backup.log
O canal 1 (saída) passa a ser o arquivo.
2>&1
O canal 2 (erro) vai para onde o 1 aponta agora: o mesmo arquivo. A ordem importa, como em qualquer redirecionamento.
$ bash backup.sh
$ echo $?
0                                     « nada na tela, e terminou bem (o último comando foi o echo "Fim")
$ cat backup.log
Início: backup de Documentos
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
Documentos:
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt
Fim

Tudo, inclusive o erro do ls, foi para o log. Troque > por >> para acumular as execuções em vez de apagar o log a cada vez.

Na tela e no log: exec > >(tee backup.log) 2>&1

Quando você roda o script à mão, quer ver o que está acontecendo. A combinação com substituição de processo manda a saída para o tee, que copia para a tela e para o arquivo:

#!/usr/bin/env bash
exec > >(tee backup.log) 2>&1
echo "Início: backup de Documentos"
ls Documentos nada
echo "Fim"

$ bash backup.sh
Início: backup de Documentos
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
Documentos:
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt
Fim
$ cat backup.log
Início: backup de Documentos
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
Documentos:
…                                     « (encurtado) o mesmo conteúdo da tela
Fim

O tee roda em paralelo ao script. Às vezes o prompt volta antes de as últimas linhas aparecerem na tela; o conteúdo é o mesmo.

Calar e depois devolver a saída

Antes de redirecionar, você pode guardar uma cópia do destino original num descritor livre, e depois restaurar:

$ exec 3>&1 1>/dev/null             « 3 = cópia da tela; 1 = lixo
$ echo "sumiu"
$ exec 1>&3 3>&-                     « 1 volta a ser a tela; fecha a cópia
$ echo "voltou"
voltou

O 3>&1 copia o descritor 1: o 3 passa a apontar para o mesmo lugar (a tela), mesmo depois que o 1 muda. Em scripts, essa técnica deixa você mandar a saída "normal" para um log e ainda falar com o usuário pelo 3.

Trocar a saída e o erro: 3>&1 1>&2 2>&3

O pipe | só leva o canal 1. E se você quiser filtrar os erros com grep ou sed, deixando a saída normal na tela? É preciso trocar os dois de lugar, usando o 3 como "mão livre", como quem troca o conteúdo de dois copos usando um terceiro.

$ ls Documentos nada | sed "s/^/[cano] /"
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
[cano] Documentos:                    « só a saída normal passou pelo cano
[cano] acesso.log
[cano] alunos.csv
[cano] notas.txt
[cano] projetos
[cano] relatorio.odt
$ ls Documentos nada 3>&1 1>&2 2>&3 | sed "s/^/[cano] /"
Documentos:
acesso.log  alunos.csv  notas.txt  projetos  relatorio.odt
[cano] ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente   « agora é o erro que passa
3>&1
O 3 vira cópia do 1, que neste momento é o cano.
1>&2
O 1 passa a apontar para onde o 2 aponta: a tela.
2>&3
O 2 passa a apontar para onde o 3 aponta: o cano.

Lido da esquerda para a direita, cada passo usa o estado deixado pelo anterior. Repare num detalhe da segunda saída: a lista de Documentos voltou a sair em colunas, porque agora o canal 1 do ls é o terminal de novo.

Se você quer só os erros numa variável, sem trocar nada de lugar, basta a ordem certa:

$ erros=$(ls Documentos nada 2>&1 >/dev/null)
$ echo "$erros"
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente

Dentro do $( ), o 1 é o "cano" que vai para a variável. 2>&1 manda o erro para esse cano; depois, >/dev/null manda a saída normal para o lixo.

Deixe o Bash escolher o número: {fd}> bash 4.1+

Num script grande, ou numa função que outra pessoa vai usar, escolher "3" à mão pode colidir com um 3 que já estava aberto. Escreva um nome de variável entre chaves no lugar do número: o Bash escolhe um descritor livre (10 ou mais) e guarda o número na variável.

$ exec {log}> registro.txt
$ echo $log
10                                    « o número escolhido
$ echo "linha via {log}" >&$log
$ exec {log}>&-                       « fechar também usa o nome
$ cat registro.txt
linha via {log}
{log}
"Escolha um descritor livre e guarde o número em $log." Sem $ nas chaves.
> registro.txt
Abre para escrita, como no exec 3>.
>&$log
Para usar, o número sai da variável (aqui, >&10).

No macOS, com o Bash 3.2, isso não existe: use números fixos de 3 a 9.

/dev/fd, /dev/stdin e companhia

O Linux mostra os descritores de cada processo como arquivos em /dev/fd/. É por isso que a substituição de processo vira um nome como /dev/fd/63. Os três primeiros têm apelidos: /dev/stdin (0), /dev/stdout (1) e /dev/stderr (2).

$ ls -l /dev/fd/
total 0
lrwx------ 1 ana ana 64 out 16 09:52 0 -> /dev/pts/0
lrwx------ 1 ana ana 64 out 16 09:52 1 -> /dev/pts/0
lrwx------ 1 ana ana 64 out 16 09:52 2 -> /dev/pts/0
lr-x------ 1 ana ana 64 out 16 09:52 3 -> /proc/37538/fd    « a pasta que o próprio ls abriu para ler

Surpresa: aqui quem aparece é o ls, não o seu shell. /dev/fd sempre mostra os descritores de quem está olhando. O 3 é a pasta que o ls abriu para fazer a listagem. Para ver os do shell, use /proc/$$/fd, como no começo.

Esses nomes servem para programas que só aceitam nome de arquivo: echo "Erro!" > /dev/stderr funciona, mas no Bash a forma direta >&2 é a preferida.

Conexões de rede: /dev/tcp

O Bash tem um truque especial: redirecionar para /dev/tcp/MÁQUINA/PORTA abre uma conexão de rede. Esse caminho não existe no disco (ls /dev/tcp dá "inexistente"); quem o entende é o próprio Bash, só dentro de redirecionamentos.

Exemplo ilustrativo (não rodado: o laboratório do guia não tem acesso à internet), pedindo uma página a um servidor web:

exec 3<> /dev/tcp/example.com/80
printf 'GET / HTTP/1.0\r\nHost: example.com\r\n\r\n' >&3
head -n 1 <&3          # a primeira linha da resposta, por exemplo: HTTP/1.0 200 OK
exec 3>&-

Já o caso de erro foi conferido de verdade, tentando a porta 9 da própria máquina, onde nada escuta:

$ exec 3<>/dev/tcp/127.0.0.1/9
bash: connect: Conexão recusada
bash: /dev/tcp/127.0.0.1/9: Conexão recusada
$ echo $?
1
$ cat /dev/tcp/127.0.0.1/9
cat: /dev/tcp/127.0.0.1/9: Arquivo ou diretório inexistente   « o cat não conhece o truque

É útil para testar se uma porta está aberta num servidor sem curl nem nc. Para baixar coisas de verdade, prefira curl: ele trata HTTPS, redirecionamentos e erros.

Formas diferentes de gravar várias linhas num arquivo

FormaExemploMelhor quando…
>> em cada linhaecho "a" >> logSão poucas linhas, espalhadas.
Redirecionar o laçofor …; do echo …; done > logToda a saída de um bloco vai para o mesmo arquivo.
Grupo { }{ echo a; echo b; } > logVários comandos seguidos, um arquivo (veja Subshells e Grupos).
exec 3> + >&3echo "a" >&3O arquivo é usado ao longo do script todo, misturado com a saída normal.
exec > log 2>&1no começo do scriptTudo o que o script disser deve ir para o log.
exec {fd}>echo "a" >&$fdComo o exec 3>, em funções/bibliotecas, sem risco de colidir (bash 4.1+).

E para ler dois arquivos em paralelo? Se você só quer juntá-los lado a lado, o paste nomes.txt resultados.txt resolve sem laço. Os descritores 3</4< são para quando cada linha precisa de lógica (um if, uma conta).

Quando não funciona

"Descritor de arquivo inválido" 
$ echo oi >&7
bash: 7: Descritor de arquivo inválido
$ read -u 3 x
bash: read: 3: descritor de arquivo inválido: Descritor de arquivo inválido

O que aconteceu: o descritor não está aberto: você esqueceu o exec, ele já foi fechado com >&-, ou foi aberto dentro de um subshell (( exec 3> x ) ou dentro de um pipe) e sumiu junto com ele.

Como confirmar: ls -l /proc/$$/fd lista o que está aberto no shell atual.

Como resolver: abra com exec 3> arquivo (ou 3<) no próprio shell, antes de usar.

O exec não conseguiu abrir o arquivo 
$ exec 3< nao-existe.txt
bash: nao-existe.txt: Arquivo ou diretório inexistente
$ echo $?
1

O que aconteceu: o arquivo não existe (ou não há permissão). No terminal, o shell continua; num script com set -e, ou rodado pelo sh, o script pode terminar ali.

Como resolver: confira antes, ou trate o erro: exec 3< dados.txt || { echo "sem dados.txt" >&2; exit 1; }.

Escrevi exec > log no terminal e "não aparece mais nada"

O que aconteceu: o exec mudou a saída do seu shell interativo. Todo comando agora escreve no arquivo, inclusive as respostas que você esperava ver. O terminal parece "mudo", mas os erros (canal 2) ainda aparecem.

Como resolver: devolva a saída para o terminal com exec > /dev/tty, ou feche a janela e abra outra. Para não passar por isso, use o par exec 3>&1 1>log … exec 1>&3 3>&-, ou deixe o exec > só em scripts.

Escrevi exec 3 > arquivo (com espaço) 
$ exec 3 > arquivo.txt
bash: exec: 3: não encontrado
$ echo $?
127

O que aconteceu: com espaço, o 3 deixa de ser o número do descritor e vira um comando chamado 3, que o exec tentou rodar no lugar do shell. Como ele não existe: código 127. O > arquivo.txt virou um redirecionamento comum do canal 1 e criou o arquivo vazio. No terminal o shell sobrevive; num script, o exec que falha encerra o script ali mesmo (bash: linha 1: exec: 3: não encontrado, código 127).

Como resolver: o número tem que estar colado no >: exec 3> arquivo.txt.

As linhas saem fora de ordem com exec > >(tee log)

O que aconteceu: o tee é um processo à parte. A saída de erro e a normal chegam a ele por caminhos com velocidades diferentes, e o prompt pode voltar antes da última linha.

Como resolver: para logs, a ordem dentro do arquivo é a que importa; se precisar de ordem perfeita na tela, prefira exec > log 2>&1 e acompanhe com tail -f log em outra janela.

Resumo

  • Descritor é o número de um arquivo aberto: 0 entrada, 1 saída, 2 erro; 3 a 9 são seus. Veja os abertos em /proc/$$/fd.
  • exec sem comando aplica redirecionamentos ao shell atual: exec 3> arq abre, >&3 usa, exec 3>&- fecha.
  • exec 3< arq + read -u 3 lê linha a linha guardando a posição; com dois descritores você lê dois arquivos juntos.
  • exec > log 2>&1 no topo manda o script inteiro para um log; com >(tee log), também para a tela.
  • 3>&1 1>&2 2>&3 troca saída e erro; {fd}> deixa o Bash escolher o número; /dev/tcp abre conexões.
