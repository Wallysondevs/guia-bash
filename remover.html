Bash Apagar com Segurança

O rm apaga arquivos e o rmdir apaga pastas vazias. Eles são simples, rápidos e não têm volta: no terminal não existe lixeira. Esta aula ensina a usá-los e, principalmente, a não se machucar com eles, entendendo o que o Bash faz com a linha antes de o rm receber a lista de nomes.

Você vai aprender
  • Apagar arquivos (rm), pastas vazias (rmdir) e pastas cheias (rm -r).
  • As opções que pedem confirmação (-i, -I) e a que cala tudo (-f).
  • Por que rm -rf "$pasta/" com a variável vazia é perigoso, e como ${pasta:?} e set -u protegem você.
  • Como apagar um arquivo que começa com -, e o papel do --.
  • Alternativas com lixeira e os prós e contras do alias rm -i.

Por que não existe lixeira?

A lixeira que você conhece é um recurso do gerenciador de arquivos (o app "Arquivos", o Explorer do Windows, o Finder). Quando você "apaga" por lá, o arquivo é apenas movido para uma pasta escondida, como ~/.local/share/Trash.

O rm é mais antigo e mais direto. Ele pede ao sistema para desligar o nome do arquivo do seu conteúdo; o espaço em disco fica marcado como livre e será reaproveitado. Não há "desfazer", nem pergunta, nem aviso. Em troca, ele é previsível e funciona igual em qualquer sistema, inclusive em servidores sem interface gráfica.

Por isso, a regra desta aula é: confira antes de apagar. O Bash dá ferramentas ótimas para isso, a principal delas é o echo.

rm: apagar arquivos

rm vem de remove, "remover".

rm
O programa (/usr/bin/rm, não é um comando interno do Bash).
lixo.txt
O arquivo a apagar. Pode haver vários, separados por espaço.
$ cp frutas.txt lixo.txt
$ rm lixo.txt
$ echo $?
0                                       « 0 = apagou
$ ls lixo.txt
ls: não foi possível acessar 'lixo.txt': Arquivo ou diretório inexistente

Como os outros programas de arquivos, o rm fica em silêncio quando dá certo. Quem conta o resultado é o código de saída, em $? (veja Código de Saída). Tente apagar de novo o que já não existe:

$ rm lixo.txt
rm: não foi possível remover 'lixo.txt': Arquivo ou diretório inexistente
$ echo $?
1                                       « 1 = deu errado

Vários arquivos e -v

Com -v (verbose, "detalhado"), o rm conta cada arquivo que apagou:

$ touch a.txt b.txt c.txt
$ rm -v a.txt b.txt c.txt
removido 'a.txt'
removido 'b.txt'
removido 'c.txt'

Com curinga: ensaie com echo

No comando rm *.bak, o rm nunca vê o *. Quem troca *.bak pelos nomes que existem é o Bash, antes de chamar o programa. Então você pode ver exatamente o que vai ser apagado trocando rm por echo:

$ cp frutas.txt{,.bak}
$ cp frutas.txt frutas-velho.bak
$ echo rm *.bak
rm frutas.txt.bak frutas-velho.bak      « é esta a lista que o rm vai receber
$ rm -v *.bak
removido 'frutas.txt.bak'
removido 'frutas-velho.bak'

Esse ensaio é o hábito mais valioso desta aula. Gaste dois segundos com o echo antes de qualquer rm com curinga. Os curingas são explicados em Curingas (*, ?, [ ]).

Quando o padrão não casa com nenhum arquivo, o Bash o deixa como está, e o rm procura um arquivo chamado literalmente *.xyz:

$ rm *.xyz
rm: não foi possível remover '*.xyz': Arquivo ou diretório inexistente

Nomes com espaço: o rm pode apagar a coisa errada

O Bash separa as palavras nos espaços. Veja o que acontece quando existem as pastas Fotos e Fotos Antigas, e a Ana quer apagar só a segunda:

$ ls -d Fotos*
 Fotos  'Fotos Antigas'
$ rm -r Fotos Antigas
rm: não foi possível remover 'Antigas': Arquivo ou diretório inexistente
$ ls -d Fotos*
'Fotos Antigas'                         « sobrou a errada: a pasta Fotos foi apagada!

O rm recebeu duas palavras, Fotos e Antigas. A primeira existia e foi apagada; a segunda deu erro. Com aspas, o Bash entrega um nome só: rm -r "Fotos Antigas". Use a tecla Tab para completar nomes; ela coloca as barras e aspas sozinha (veja Completar com Tab e Aspas e Escapes).

Apagar pastas: rmdir, rm -d e rm -r

Sem opções, o rm se recusa a apagar pastas:

$ rm Documentos
rm: não foi possível remover 'Documentos': É um diretório
$ echo $?
1

rmdir: só pastas vazias

rmdir vem de remove directory. Ele é o jeito mais seguro, porque só apaga pastas vazias. Se houver algo dentro, ele recusa e nada se perde:

$ mkdir -p arquivo/{2024,2025}
$ touch arquivo/2025/notas.txt
$ rmdir arquivo/2024
$ echo $?
0
$ rmdir arquivo/2025
rmdir: falhou em remover 'arquivo/2025': Diretório não vazio
$ echo $?
1

Com -p, ele apaga também as pastas "pais" que ficarem vazias. É o contrário de mkdir -p:

$ mkdir -p a/b/c
$ rmdir -pv a/b/c
rmdir: removendo o diretório 'a/b/c'
rmdir: removendo o diretório 'a/b'
rmdir: removendo o diretório 'a'

rm -d faz o mesmo que rmdir (apaga pasta vazia), útil quando você quer apagar arquivos e pastas vazias no mesmo comando.

rm -r: a pasta com tudo dentro

-r (de recursive, "recursivo") entra em cada pasta, apaga o conteúdo e depois a pasta. Com -v, você vê a ordem: de dentro para fora.

$ cp -r Documentos/projetos velho
$ rm -rv velho
removido 'velho/site/index.html'
removido 'velho/site/style.css'
foi removido o diretório: 'velho/site'
removido 'velho/backup.sh'
foi removido o diretório: 'velho'
rm -r não pede confirmação

Uma pasta com dez mil arquivos some num instante. Antes de um rm -r, confira o caminho com ls e, se ele tiver curinga ou variável, ensaie com echo.

Perguntar antes: -i e -I

-i: uma pergunta por arquivo

-i vem de interactive. Antes de cada arquivo, o rm pergunta. Responda s para apagar; qualquer outra resposta mantém o arquivo.

$ rm -i Documentos/notas.txt
rm: remover regular file 'Documentos/notas.txt'? n
$ echo $?
0                                       « recusar não é erro para o rm

A pergunta mistura português e inglês ("regular file" = arquivo comum) porque a tradução do coreutils está incompleta. Com -ri, ele pergunta até para entrar em cada pasta. Aqui, velho tem o arquivo a e a subpasta sub com o arquivo b, todos vazios:

$ rm -ri velho
rm: entrar no diretório 'velho'? s
rm: remover regular empty file 'velho/a'? s
rm: entrar no diretório 'velho/sub'? s
rm: remover regular empty file 'velho/sub/b'? s
rm: remover directory 'velho/sub'? s
rm: remover directory 'velho'? s

-I: uma pergunta só

Perguntar arquivo por arquivo cansa, e quem se cansa começa a responder s sem ler. O -I (i maiúsculo) pergunta uma vez, e só quando o risco é maior: mais de três arquivos, ou apagar com -r.

$ rm -I 1.txt 2.txt 3.txt 4.txt
rm: remover 4 argumentos? n
$ rm -rI velho
rm: remover 1 argumento recursivamente? n
$ rm -I 1.txt 2.txt                     « só dois arquivos: apaga sem perguntar

O rm pergunta sozinho, às vezes

Se um arquivo está protegido contra escrita (sem a permissão w), o rm pergunta mesmo sem -i, desde que você esteja num terminal:

$ chmod 444 protegido.txt
$ rm protegido.txt
rm: remover regular empty file 'protegido.txt' protegido contra escrita? n

Calar tudo: -f

-f vem de force, "forçar". Ele muda três coisas:

  • não pergunta nada (nem nos arquivos protegidos, nem com -i antes dele);
  • não reclama de arquivos que não existem;
  • devolve 0 nesse caso.
$ rm lixo.txt
rm: não foi possível remover 'lixo.txt': Arquivo ou diretório inexistente
$ rm -f lixo.txt
$ echo $?
0                                       « "não existe" = "já está apagado": sucesso

Isso é útil em scripts, quando o objetivo é "garantir que o arquivo não exista". Mas o -f não é um superpoder: ele não passa por cima de permissões.

$ rm -f trancada/a.txt
rm: não foi possível remover 'trancada/a.txt': Permissão negada
$ echo $?
1

Juntos, rm -rf apagam uma pasta inteira sem perguntar e sem reclamar. É o comando mais perigoso do dia a dia, e a próxima seção mostra por quê.

O perigo da variável vazia

Em scripts, é comum guardar um caminho numa variável e apagar o conteúdo dela. O problema: se a variável estiver vazia (ou com o nome digitado errado), o Bash a troca por nada, e o que sobra pode ser a raiz do sistema.

Veja com echo, que é seguro, o que o Bash monta:

$ pasta=""
$ echo rm -rf "$pasta/"
rm -rf /                                « a pasta "nada" + "/" = a raiz do sistema
$ echo rm -rf "$pasta/"*
rm -rf /bin /boot /dev /etc /home /lib /lib64 /media /mnt /opt /proc /root /run /sbin /srv /sys /tmp /usr /var

(A segunda lista foi encurtada; ela depende do sistema.) Contra a primeira forma, o GNU rm tem uma trava, a preserve-root:

$ rm -rf "$pasta/"
rm: é perigoso operar recursivamente em '/'
rm: use --no-preserve-root para contornar esta segurança
$ echo $?
1

Mas a segunda forma, com /*, não é barrada: o rm recebe /bin, /home… como nomes comuns e tenta apagar um por um. Tudo o que for seu, inclusive a sua pasta pessoal, vai embora.

O caso real costuma ser um erro de digitação num script:

#!/usr/bin/env bash
pasta_temp="$HOME/temp-relatorios"
rm -rfv "$pasta_tmp/"*          # tmp em vez de temp: a variável não existe!
echo "limpeza concluída"

Variável que não existe vale vazio, sem erro nenhum (veja Variáveis: o Básico). A linha 3 vira rm -rfv /*. Não rode este script. Há três proteções, e você pode usar todas.

Proteção 1: ${pasta:?}

Escrever a variável como ${pasta_tmp:?} diz ao Bash: "se ela estiver vazia ou não existir, pare com erro, e não rode o comando".

${
Início da forma longa de usar uma variável.
pasta_tmp
O nome da variável.
:?
"Se estiver vazia ou não definida, é erro." Depois do ? você pode escrever a mensagem: ${pasta:?informe a pasta}.
}
Fim.
#!/usr/bin/env bash
pasta_temp="$HOME/temp-relatorios"
rm -rfv "${pasta_tmp:?}/"*
echo "limpeza concluída"

$ bash limpa.sh
limpa.sh: linha 3: pasta_tmp: parâmetro nulo ou não inicializado
$ echo $?
1
$ ls temp-relatorios
r1.txt  r2.txt                          « nada foi apagado

O Bash parou o script inteiro na linha 3: nem o rm nem o echo da linha 4 rodaram. No terminal, a mesma coisa aparece sem o nome do script: bash: pasta: parâmetro nulo ou não inicializado. Essa e outras formas ${…} estão em Expansão de Parâmetros.

Proteção 2: set -u

set -u no começo do script faz o Bash tratar qualquer variável não definida como erro. Ela pega o erro de digitação mesmo onde você esqueceu o :?:

#!/usr/bin/env bash
set -u
pasta_temp="$HOME/temp-relatorios"
rm -rfv "$pasta_tmp/"*
echo "limpeza concluída"

$ bash limpa2.sh
limpa2.sh: linha 4: pasta_tmp: variável não associada
$ echo $?
1

"Variável não associada" é a tradução de unbound variable: o nome não tem valor nenhum. Repare que o set -u não pega uma variável que existe vazia (pasta=""); o :? pega as duas. Por isso o ideal é usar os dois. O set -u faz parte do "modo estrito", tema de set -euo pipefail.

Proteção 3: com o nome certo, tudo funciona

#!/usr/bin/env bash
set -u
pasta_temp="$HOME/temp-relatorios"
rm -rfv "${pasta_temp:?}/"*
echo "limpeza concluída"

$ bash limpa3.sh
removido '/home/ana/temp-relatorios/r1.txt'
removido '/home/ana/temp-relatorios/r2.txt'
limpeza concluída

E sempre: aspas em volta da variável ("$pasta"), para um nome com espaço não virar duas palavras, como no caso das Fotos Antigas.

Arquivos que começam com - e o --

Para o rm, tudo o que começa com hífen é uma opção. Um arquivo chamado -lixo.txt confunde o programa:

$ rm -lixo.txt
rm: opção inválida -- “l”
Tente "rm ./-lixo.txt" para remover o arquivo '-lixo.txt'.
Tente "rm --help" para mais informações.

O próprio rm sugere a solução. Há duas:

rm -- -lixo.txt
O -- (dois hífens sozinhos) quer dizer "acabaram as opções": tudo o que vier depois é nome de arquivo. Funciona em quase todos os comandos.
rm ./-lixo.txt
O ./ ("na pasta atual") faz o nome começar com ponto, e não com hífen.

Quando o curinga vira opção

O perigo maior aparece com curingas. O Bash expande * em todos os nomes da pasta, inclusive os que começam com hífen, e o rm não sabe que eles vieram de um curinga. Veja uma pasta com a.txt, b.txt e um arquivo chamado -v:

$ echo rm *
rm a.txt b.txt -v
$ rm *
removido 'a.txt'                        « o arquivo "-v" virou a opção -v!
removido 'b.txt'
$ ls
-v                                      « e ele próprio não foi apagado

Aqui o estrago foi pequeno. Um arquivo chamado -rf numa pasta com subpastas seria bem pior. A defesa é a mesma: rm -- * ou rm ./*. Com ./*, todos os nomes começam com ./ e nunca parecem opções.

Alternativas com lixeira

Se você quer o "desfazer", use um comando que move para a lixeira do desktop em vez de apagar.

gio trash

Vem instalado na maioria dos desktops Linux (GNOME e derivados). O arquivo vai para a mesma lixeira do app Arquivos:

$ gio trash frutas.txt
$ ls ~/.local/share/Trash/files
frutas.txt                              « está na lixeira, não apagado

Num desktop com sessão gráfica, gio trash --list lista a lixeira e gio trash --empty a esvazia; para restaurar, o mais simples é o app Arquivos. Fora de uma sessão gráfica (num servidor, por exemplo), essas duas opções podem responder Operação sem suporte.

trash-cli

Um pacote à parte (trash-cli), feito para o terminal. A saída abaixo é ilustrativa: o pacote não vem instalado e não existe no laboratório nem no simulador.

$ trash-put relatorio-velho.txt
$ trash-list
2026-10-15 10:30:12 /home/ana/relatorio-velho.txt
$ trash-restore
   0 2026-10-15 10:30:12 /home/ana/relatorio-velho.txt
What file to restore [0..0]: 0

Lembre: lixeira ocupa espaço até ser esvaziada, e scripts devem usar rm, que existe em todo lugar.

O alias rm -i: prós e contras

Muita gente coloca no ~/.bashrc a linha alias rm='rm -i', para que todo rm pergunte antes. Um alias é um apelido: o Bash troca a primeira palavra do comando pelo texto do apelido (veja alias).

$ alias rm='rm -i'
$ type rm
rm está apelidada para `rm -i'
A favorContra
Uma chance de desistir no terminal do dia a dia.Você se acostuma a responder s sem ler, e a proteção some.
Bom para quem está começando.Aliases não valem dentro de scripts, nem em outra máquina: você fica sem rede onde mais precisa.
rm -f passa por cima do -i (a última opção vence), e \rm ou command rm ignoram o alias.
$ rm -f x.txt                           « vira "rm -i -f": o -f vence, sem pergunta
$ echo $?
0
$ \rm y.txt                             « a barra invertida desliga o alias
$ command rm z.txt                      « command também

Uma opção mais equilibrada é alias rm='rm -I': pergunta só nos casos arriscados, e por isso você continua lendo a pergunta.

Quando não funciona

"É um diretório" 
$ rm Documentos
rm: não foi possível remover 'Documentos': É um diretório

O que aconteceu: o rm sem opções só apaga arquivos.

Como resolver: se a pasta está vazia, rmdir. Se tem conteúdo e você tem certeza, ls Documentos para ver o que há e então rm -r.

"Diretório não vazio" 
$ rmdir Documentos
rmdir: falhou em remover 'Documentos': Diretório não vazio
$ rm -d Documentos
rm: não foi possível remover 'Documentos': Diretório não vazio

O que aconteceu: o rmdir (e o rm -d) estão fazendo o trabalho deles: protegendo o conteúdo. Às vezes a pasta parece vazia, mas tem arquivos ocultos.

Como confirmar: ls -A Documentos mostra também os nomes que começam com ponto.

"Arquivo ou diretório inexistente" 
$ rm Área de trabalho
rm: não foi possível remover 'Área': Arquivo ou diretório inexistente
rm: não foi possível remover 'de': Arquivo ou diretório inexistente
rm: não foi possível remover 'trabalho': Arquivo ou diretório inexistente

O que aconteceu: três erros para um comando só denunciam um nome com espaço sem aspas: o Bash entregou três palavras. (Aqui foi sorte que nenhuma delas existia.) Outra causa: um curinga que não casou com nada, como *.xyz, ou um erro de digitação.

Como resolver: aspas ("Área de trabalho") ou Tab. E repare: mesmo com aspas, aquela é uma pasta, então seria rm -r.

"opção inválida" 
$ rm -lixo.txt
rm: opção inválida -- “l”
Tente "rm ./-lixo.txt" para remover o arquivo '-lixo.txt'.

O que aconteceu: o nome começa com hífen e foi lido como opção.

Como resolver: rm -- -lixo.txt ou rm ./-lixo.txt.

"Permissão negada" 
$ rm trancada/a.txt
rm: não foi possível remover 'trancada/a.txt': Permissão negada
$ ls -ld trancada
dr-xr-xr-x 2 ana ana 4096 out 15 10:30 trancada

O que aconteceu: para apagar um arquivo, você precisa poder escrever na pasta onde ele está (apagar é tirar um nome da lista da pasta). A pasta trancada não tem w. Nem o -f resolve.

Como resolver: se a pasta é sua, devolva a permissão (chmod u+w trancada). Se é do sistema, provavelmente você não deveria apagar esse arquivo.

"falta operando" 
$ rm
rm: falta operando
Tente "rm --help" para mais informações.

O que aconteceu: o rm não recebeu nenhum nome. Num script, isso costuma ser uma variável vazia sem aspas (rm $arquivo). Com -f, nem esse aviso aparece: rm -f sem nomes devolve 0 em silêncio.

Não apareceu nada… apagou?

O que aconteceu: silêncio é sucesso. Com -f, silêncio também pode significar "não havia nada para apagar".

Como confirmar: echo $? e ls no nome. Da próxima vez, use -v.

Resumo

  • rm apaga de verdade; não há lixeira no terminal.
  • rmdir só apaga pastas vazias; rm -r apaga pastas com tudo dentro.
  • -i pergunta sempre, -I pergunta uma vez, -f nunca pergunta (mas não vence permissões).
  • Quem expande *, variáveis e espaços é o Bash: ensaie com echo antes de apagar.
  • Em scripts: "${pasta:?}" e set -u contra a variável vazia.
  • Nomes com hífen: rm -- nome ou rm ./nome; prefira rm ./* a rm *.
