Bash ; && ||

Até agora você digitou um comando por vez. Com três operadores, você coloca vários na mesma linha e decide quando cada um roda: sempre (;), só se o anterior deu certo (&&) ou só se o anterior falhou (||). Quem decide é o código de saída que você acabou de aprender.

Você vai aprender
  • A diferença entre ;, && e ||, e como o código de saída escolhe o caminho.
  • Por que a && b || c não é um "se/senão", com o caso em que ele falha.
  • Como agrupar vários comandos com { …; } (e os dois detalhes que todo mundo erra).
  • O que o & no fim da linha faz, e qual operador usar em cada situação.

A ideia: uma receita com condições

Pense numa receita: "quebre os ovos e então bata" (só bate se conseguiu quebrar); "use manteiga, ou senão óleo" (só usa óleo se faltar manteiga). Os operadores do Bash fazem exatamente isso com comandos:

OperadorLê-seO segundo comando roda…
a ; b"a, depois b"Sempre.
a && b"a e então b" (and)Só se a deu certo (código 0).
a || b"a ou senão b" (or)Só se a falhou (código diferente de 0).

;: um depois do outro, sempre

O ponto e vírgula separa comandos na mesma linha. É exatamente como apertar Enter entre eles: o segundo roda quando o primeiro termina, dê certo ou não.

mkdir estudos
Primeiro comando: cria a pasta.
;
"Depois" (sem condição).
cd estudos
Segundo comando: entra nela.
;
"Depois".
pwd
Terceiro: mostra onde você está.
$ mkdir estudos; cd estudos; pwd
/home/ana/estudos

Funcionou porque nada falhou. Agora veja o perigo do ;: ele não liga para erros.

$ cd nada; pwd
bash: cd: nada: Arquivo ou diretório inexistente
/home/ana                     « o pwd rodou mesmo assim: você continua na pasta pessoal

Aqui não houve estrago, mas imagine cd pasta-temporaria; rm -r *. Se o cd falhar, o rm apaga tudo na pasta onde você está. É para isso que existe o &&.

&&: só se o anterior deu certo

mkdir projeto
Primeiro comando.
&&
"E então": só continua se o código foi 0.
cd projeto
Só roda se a pasta foi criada.
&& pwd
Só roda se o cd deu certo.
$ mkdir projeto && cd projeto && pwd
/home/ana/projeto

Tudo deu certo, então tudo rodou. Agora a Ana volta para a pasta pessoal e repete o comando. A pasta já existe, o mkdir falha, e a corrente para:

$ cd
$ mkdir projeto && cd projeto
mkdir: cannot create directory ‘projeto’: Arquivo existe
$ echo $?
1                             « o código do mkdir: o cd nem foi tentado
$ pwd
/home/ana                     « continua na pasta pessoal
A mensagem meio em inglês

"cannot create directory … Arquivo existe" é a mensagem real do GNU mkdir em português: parte dela ainda não foi traduzida. No seu sistema ela pode aparecer toda em português ou toda em inglês.

O && é a escolha certa quando o passo seguinte depende do anterior. Um exemplo do dia a dia, um backup que só avisa "feito" se tudo funcionou:

$ mkdir -p backup && cp frutas.txt backup/ && echo "Backup feito"
Backup feito

Missão: numa linha só, crie a pasta relatorios e entre nela, de modo que o cd só rode se o mkdir der certo.

||: só se o anterior falhou

O || (duas barras verticais, a tecla perto do Enter com Shift) é o "plano B": o segundo comando só roda se o primeiro falhou.

cd nada
Tenta entrar numa pasta.
||
"Ou senão": só continua se o código foi diferente de 0.
echo "Essa pasta não existe"
O plano B: avisa.
$ cd nada || echo "Essa pasta não existe"
bash: cd: nada: Arquivo ou diretório inexistente
Essa pasta não existe            « o cd falhou, então o echo rodou
$ cd Documentos || echo "Essa pasta não existe"     « o cd deu certo: o echo foi pulado (e a Ana está em Documentos)

Dois usos clássicos:

  • Criar só se faltar: [ -d backup ] || mkdir backup ("a pasta existe, ou senão crie").
  • Parar um script no erro: cd "$pasta" || exit 1 ("entre na pasta, ou senão saia com erro"). Você vai ver isso em quase todo script bem escrito.

Missão: usando ||, crie a pasta backup só se ela ainda não existir. Dica: [ -d backup ] pergunta "existe uma pasta backup?". Rode o comando duas vezes: na segunda, nada deve acontecer (nem erro).

Combinando: a armadilha do a && b || c

É muito comum ver esta linha, que parece um "se/senão" em uma linha:

$ grep -q banana frutas.txt && echo "tem banana" || echo "não tem banana"
tem banana
$ grep -q kiwi frutas.txt && echo "tem kiwi" || echo "não tem kiwi"
não tem kiwi

Funcionou nos dois casos. Mas não é um if. O Bash lê da esquerda para a direita, um operador por vez, olhando sempre o código do último comando que rodou:

  a  &&  b  ||  c
  └──┬──┘
     └─ resultado de "a && b" ──||── c
        c roda se a falhou  OU  se b falhou

Ou seja: o c roda quando a falha, mas também quando b falha. Com echo no meio, o b praticamente nunca falha, por isso o truque parece funcionar. Troque o b por algo que pode falhar e veja:

$ [ -f frutas.txt ] && grep kiwi frutas.txt || echo "O arquivo não existe"
O arquivo não existe              « mentira! o arquivo existe; quem falhou foi o grep

Passo a passo: [ -f frutas.txt ] deu 0 (o arquivo existe), então o grep rodou; o grep não achou kiwi e deu 1; como o último código foi 1, o || rodou o echo. A mensagem saiu errada.

Mais duas provas de que os operadores são lidos em fila, sem "prioridade":

$ false && echo A || echo B
B                                 « false falhou: pula o A, cai no B
$ true || echo A && echo B
B                                 « true deu certo: pula o A; o último código ainda é 0, então roda o B
Regra prática

Use a && b || c só quando b não pode falhar (um echo simples). Quando precisar de "se/senão" de verdade, use if: if [ -f frutas.txt ]; then grep kiwi frutas.txt; else echo "O arquivo não existe"; fi.

O código de saída de uma linha inteira

Quando a linha tem vários comandos, o $? fica com o código do último que rodou:

$ false; true; echo $?
0
$ true && false; echo $?
1
$ false || true; echo $?
0

Agrupar comandos: { …; }

E se o plano B tiver dois passos? grep -q kiwi frutas.txt || echo "Faltava kiwi"; echo kiwi >> frutas.txt não serve: o ; faz o segundo passo rodar sempre. Você precisa dizer "estes dois comandos são um bloco só". É o que as chaves fazem:

grep -q kiwi frutas.txt
A pergunta: tem kiwi?
||
Se não tiver…
{
…abre o bloco. Precisa de espaço depois.
echo "Faltava kiwi, adicionando...";
Primeiro passo do bloco.
echo kiwi >> frutas.txt;
Segundo passo (o >> acrescenta ao arquivo, veja Redirecionamento). Precisa do ; antes da chave.
}
Fecha o bloco.
$ grep -q kiwi frutas.txt || { echo "Faltava kiwi, adicionando..."; echo kiwi >> frutas.txt; }
Faltava kiwi, adicionando...
$ tail -n 2 frutas.txt
banana
kiwi                              « os dois passos rodaram juntos

Os dois detalhes obrigatórios

Para o Bash, { e } são palavras reservadas, como if. Por isso:

  1. Espaço depois do {, senão {echo vira uma palavra só (um "comando" que não existe).
  2. ; (ou uma quebra de linha) antes do }, senão o } vira só mais um argumento do último comando.
$ {echo oi}
bash: {echo: comando não encontrado          « faltou o espaço depois de {
$ { echo oi }
> }                                         « o Bash esperou o fim do bloco; a Ana digitou } de novo
oi }                                         « o primeiro } virou texto para o echo

Agrupar para redirecionar tudo junto

Outro uso: mandar a saída de vários comandos para o mesmo arquivo de uma vez.

$ { echo "Relatório de frutas"; wc -l frutas.txt; } > relatorio.txt
$ cat relatorio.txt
Relatório de frutas
7 frutas.txt
Chaves { } × parênteses ( )

Parênteses também agrupam, mas rodam o bloco num subshell, uma cópia do shell: um cd ou uma variável criada lá dentro não chegam ao seu terminal. As chaves rodam no shell atual. Os detalhes estão em Subshells e Grupos.

O cd falhou, mas o script seguiu em frente e listou a pasta errada. Corrija isso:

Missão: mude a linha do cd para que, se ele falhar, o script mostre Pasta não encontrada: Fotos (use $1) e termine com exit 1. Use || e um grupo { …; }. Depois teste também com o argumento Imagens.

#!/usr/bin/env bash

Com a correção, a saída real fica assim:

$ bash lista.sh Fotos
lista.sh: linha 2: cd: Fotos: Arquivo ou diretório inexistente

$ echo $?
1
$ bash lista.sh Imagens
Arquivos em Imagens:
ferias.jpg  perfil.png

&: rodar sem esperar

Um & sozinho no fim do comando é outra coisa: ele manda o comando rodar em segundo plano. O Bash não espera ele terminar e devolve o prompt na hora.

$ sleep 2 &
[1] 33816                         « [1] = número do job; 33816 = PID (no seu será outro)
$ echo "O terminal continua livre"
O terminal continua livre
$ echo fim
fim
[1]+  Concluído                 sleep 2     « aviso de que o job terminou

Não confunda: & (um) = segundo plano; && (dois) = "e então". Segundo plano, fg, bg e wait são assunto de Jobs.

Quebra de linha × ;

Num script, cada linha é um comando, e a quebra de linha faz o papel do ;. Estas duas formas são iguais:

Uma linhaVárias linhas (num script)
cd /tmp; ls; pwdcd /tmp
ls
pwd
{ echo a; echo b; }{
  echo a
  echo b
}

Você também pode quebrar a linha depois de && ou ||: o Bash percebe que falta algo e mostra o prompt de continuação >. Isso deixa linhas longas mais legíveis.

$ ls Documentos &&
> echo "deu certo"
acesso.log  alunos.csv  notas.txt  projetos  relatorio.odt
deu certo

Quando não funciona

"erro de sintaxe próximo ao token inesperado `&&'" 
$ && ls
bash: erro de sintaxe próximo ao token inesperado `&&'

O que aconteceu: o operador precisa de um comando dos dois lados. Aqui não havia nada antes do &&. O mesmo acontece com ;; digitado por engano (ls ;;): o ;; só existe dentro do case.

Como resolver: confira se há um comando antes e depois de cada operador. "Token" é cada pedaço que o Bash separa na linha.

Apareceu > e o terminal ficou esperando

O que aconteceu: a linha terminou com &&, || ou um { sem }. O Bash está esperando o resto.

Como resolver: digite o que falta (o próximo comando, ou }), ou aperte Ctrl+C para desistir da linha.

"erro de sintaxe próximo ao token inesperado `}'" ou "{echo: comando não encontrado" 
$ {echo oi;}
bash: erro de sintaxe próximo ao token inesperado `}'

O que aconteceu: faltou o espaço depois do {. Para o Bash, {echo é uma palavra qualquer, e o } apareceu sem um { de verdade aberto.

Como resolver: { echo oi; }: espaço depois de {, ; antes de }.

A mensagem de "senão" apareceu mesmo com tudo certo

O que aconteceu: é a armadilha do a && b || c: o b falhou e o c rodou.

Como confirmar: rode só a && b e olhe o echo $?. Se for diferente de 0, o problema está no b.

Como resolver: troque por um if.

Um comando rodou mesmo depois de um erro 
$ cd nada || echo "não deu" && echo "e este?"
bash: cd: nada: Arquivo ou diretório inexistente
não deu
e este?

O que aconteceu: o echo "não deu" deu certo, então o && seguinte rodou. Ou você usou ; onde queria &&.

Como resolver: leia a linha da esquerda para a direita, perguntando "qual foi o último código?". Se a lógica ficou confusa, separe em linhas ou use if.

Resumo

  • ; roda o próximo sempre; && só se o anterior deu 0; || só se o anterior falhou.
  • Os operadores são lidos da esquerda para a direita, olhando o código do último comando que rodou.
  • a && b || c roda c também quando b falha: não é um if.
  • { a; b; } agrupa: espaço depois do { e ; antes do }.
  • cd pasta || exit 1 é o jeito mais simples de um script parar no erro. Um & sozinho roda em segundo plano.
