Bash Depurar

Depurar (em inglês, debug, "tirar os insetos") é descobrir por que o script não faz o que você esperava. O Bash não tem um depurador gráfico, mas tem algo muito eficiente: ele pode mostrar cada comando, já com as variáveis trocadas pelos valores, antes de executá-lo. Na maioria das vezes, o erro salta aos olhos na primeira leitura.

Você vai aprender
  • A checar só a sintaxe, sem rodar nada, com bash -n.
  • A ler o rastro de bash -x / set -x: o que significam o + e o ++.
  • A pôr arquivo e número da linha no rastro com PS4, e a mandar o rastro para um arquivo.
  • A rodar um script passo a passo e a inspecionar variáveis com declare -p.
  • A reconhecer os erros clássicos: "token inesperado", "EOF inesperado", ^M e variável vazia.

O método em 4 passos

Antes das ferramentas, o roteiro. Quase todo problema de script se resolve assim:

  1. Leia a mensagem de erro inteira. Em scripts, o Bash diz o arquivo e a linha: fruta.sh: linha 5: ….
  2. Cheque a sintaxe com bash -n script.sh.
  3. Veja o que realmente rodou com bash -x script.sh.
  4. Reduza: rode só o comando suspeito no terminal, com os valores que o rastro mostrou.

E, antes de tudo isso (ou junto), passe o script no ShellCheck, que acha muitos desses erros sem rodar nada.

Só a sintaxe: bash -n

A opção -n (noexec, "não executar") faz o Bash ler o script inteiro e procurar erros de escrita, sem rodar nenhum comando. É seguro mesmo para scripts que apagam arquivos.

bash
Um novo Bash, que vai ler o arquivo.
-n
Só ler e checar a gramática. Nada é executado.
script.sh
O arquivo a checar.

Primeiro, um script que está certo: media.sh, que calcula a média das notas de alunos.csv.

$ bash -n media.sh
$ echo $?
0                                              « nenhuma mensagem e código 0: a sintaxe está certa

"Sintaxe certa" não quer dizer "script certo": bash -n não sabe se um arquivo existe, se uma variável está vazia ou se um comando está escrito errado (ehco é um nome válido de comando, que só falha ao rodar). Ele pega gramática: if sem fi, aspas sem par, parênteses abertos.

#!/usr/bin/env bash
if [[ -f frutas.txt ]]; then
  echo "achei"
echo "fim"

$ bash -n sem-fi.sh
sem-fi.sh: linha 5: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 2
$ echo $?
2

Leia a mensagem com atenção: o arquivo tem 4 linhas, e o erro é na "linha 5", ou seja, depois do fim. O Bash chegou ao fim do arquivo ainda esperando o fi do if aberto na linha 2. A mensagem diz as duas coisas.

Missão: existe um script quebrado.sh na pasta da Ana. Sem executá-lo, peça ao Bash para checar só a sintaxe e leia a mensagem: em que linha o if foi aberto? (Se quiser, veja o arquivo com cat -n quebrado.sh.)

Ver cada comando: bash -x

A Ana fez um script que diz quantas vezes uma fruta aparece na lista. Ele não dá erro nenhum, mas a resposta está errada:

#!/usr/bin/env bash
# fruta.sh — diz quantas vezes uma fruta aparece na lista
fruta=$1
total=$(grep -c "$frtua" frutas.txt)
if [ $total -gt 0 ]; then
  echo "$fruta aparece $total vezes"
else
  echo "não tem $fruta"
fi

$ bash fruta.sh uva
uva aparece 7 vezes                            « só tem uma uva na lista!
$ bash fruta.sh kiwi
kiwi aparece 7 vezes                           « e nenhum kiwi

A opção -x (xtrace, "rastrear a execução") faz o Bash mostrar cada comando depois das expansões, ou seja, com as variáveis já trocadas pelos valores, logo antes de rodá-lo:

$ bash -x fruta.sh uva
+ fruta=uva
++ grep -c '' frutas.txt                       « aqui! o grep recebeu um texto vazio
+ total=7
+ '[' 7 -gt 0 ']'
+ echo 'uva aparece 7 vezes'
uva aparece 7 vezes

A segunda linha entrega o erro: o grep procurou '' (texto vazio), que casa com todas as 7 linhas. Por quê? Porque o script usa $frtua, com as letras trocadas, uma variável que não existe. Olhando só o código, era fácil não ver; no rastro, o valor vazio aparece na cara.

Como ler o rastro

Você vêSignifica
+ comandoUm comando do script, já com variáveis e curingas expandidos.
++ comandoUm comando rodando um nível abaixo: dentro de $( ), de um pipe em $( ) ou de um subshell. Cada nível acrescenta um +.
'texto'As aspas simples são acrescentadas pelo rastro para mostrar onde cada argumento começa e termina. '' é um argumento vazio.
Linha sem +Saída normal do script (o que ele imprime).
'[' 7 -gt 0 ']'O [ é um comando como outro qualquer, e cada parte é um argumento.

Repare na ordem: ++ grep aparece antes de + total=7, porque o Bash precisa rodar o $( ) primeiro para saber o valor a atribuir.

Com o nome corrigido para $fruta, o rastro passa a mostrar ++ grep -c uva frutas.txt, e a resposta fica certa:

Esse erro tinha prevenção

Com set -u (Modo Estrito), o script teria parado com frtua: variável não associada, na linha exata. E o ShellCheck avisaria que frtua nunca recebeu valor.

Só um trecho: set -x e set +x

Em scripts grandes, o rastro inteiro é longo demais. Ligue-o só em volta da parte suspeita, dentro do script: set -x liga, set +x desliga.

#!/usr/bin/env bash
nome=Ana
set -x
pasta=~/Documentos
qtd=$(ls "$pasta" | wc -l)
set +x
echo "$nome tem $qtd itens em $pasta"

$ bash trecho-x.sh
+ pasta=/home/ana/Documentos                   « o ~ já aparece expandido
++ ls /home/ana/Documentos
++ wc -l                                       « as duas partes do pipe dentro do $( )
+ qtd=5
+ set +x                                       « o próprio set +x aparece, e o rastro para
Ana tem 5 itens em /home/ana/Documentos

A linha nome=Ana não aparece, porque veio antes do set -x. Você pode também ligar o rastro no terminal (set -x) para ver como o Bash expande um comando seu, e desligar com set +x.

Arquivo e linha no rastro: PS4

O + do começo de cada linha vem da variável PS4 (o quarto prompt do Bash; o PS1 é o do terminal). Mudando o PS4, cada linha do rastro pode dizer de onde veio:

PS4='…'
O texto impresso antes de cada comando rastreado. Aspas simples, para as variáveis serem lidas a cada linha, e não uma vez só.
${BASH_SOURCE}
O arquivo do script que está rodando (útil quando um script faz source de outro).
${LINENO}
O número da linha.
${FUNCNAME[0]:-}
(Opcional) O nome da função atual; :- evita erro com set -u fora de funções.
$ PS4='+ ${BASH_SOURCE}:${LINENO}: ' bash -x fruta.sh uva
+ fruta.sh:3: fruta=uva
++ fruta.sh:4: grep -c '' frutas.txt
+ fruta.sh:4: total=7
+ fruta.sh:5: '[' 7 -gt 0 ']'
+ fruta.sh:6: echo 'uva aparece 7 vezes'
uva aparece 7 vezes

Agora você vai direto à linha 4. Escrever PS4=… bash -x script na mesma linha muda o PS4 só para esse comando. Para usar sempre, ponha export PS4='+ ${BASH_SOURCE}:${LINENO}: ' no seu ~/.bashrc, ou dentro do script, antes do set -x.

O primeiro caractere do PS4 é repetido

O Bash repete o primeiro caractere do PS4 para mostrar o nível (+, ++, +++). Por isso, comece o PS4 com +; se começar com espaço, os níveis ficam invisíveis.

O rastro num arquivo: BASH_XTRACEFD

O rastro sai na saída de erro, misturado com as mensagens do script. Para separar, abra um descritor para um arquivo e diga ao Bash para usá-lo com a variável BASH_XTRACEFD (xtrace file descriptor):

#!/usr/bin/env bash
exec 3> rastro.log
BASH_XTRACEFD=3
set -x
fruta=uva
grep -c "$fruta" frutas.txt

$ bash debug-fd.sh
1                                              « na tela, só a saída do script
$ cat rastro.log
+ fruta=uva
+ grep -c uva frutas.txt                       « o rastro foi para o arquivo
exec 3> rastro.log
Abre o arquivo rastro.log no canal 3, para o script inteiro.
BASH_XTRACEFD=3
O rastro do -x vai para o canal 3, em vez do 2.

Ver as linhas como estão escritas: set -v

A opção -v (verbose, "falador") mostra cada linha do script como ela foi lida, antes de qualquer expansão. É útil para erros de sintaxe, porque mostra até onde o Bash conseguiu ler:

$ bash -v sem-then.sh
#!/usr/bin/env bash
if [[ -f frutas.txt ]]
  echo "achei"
fi
sem-then.sh: linha 4: erro de sintaxe próximo ao token inesperado `fi'
sem-then.sh: linha 4: `fi'

Passo a passo com trap … DEBUG

O evento DEBUG do trap roda antes de cada comando. Com um read dentro dele, o script espera um Enter a cada passo, como um depurador:

#!/usr/bin/env bash
trap 'read -rp "[linha $LINENO] $BASH_COMMAND   (Enter) " < /dev/tty' DEBUG
nome=Ana
qtd=$(wc -l < frutas.txt)
echo "$nome tem $qtd frutas"

$ bash passo.sh
[linha 3] nome=Ana   (Enter)                   « o script espera você apertar Enter
[linha 4] qtd=$(wc -l < frutas.txt)   (Enter)
[linha 5] echo "$nome tem $qtd frutas"   (Enter)
Ana tem 7 frutas
$BASH_COMMAND
O comando que vai rodar, como está escrito (sem expandir).
< /dev/tty
Lê do teclado de verdade, mesmo se a entrada do script estiver redirecionada.

Enquanto ele espera, você pode até abrir outro terminal e olhar os arquivos que o script criou até ali.

Olhar dentro das variáveis: declare -p

echo "$x" esconde detalhes: espaços no fim, caracteres invisíveis, se é array. O declare -p (print) mostra a variável exatamente como o Bash a guarda, em forma de comando:

$ cores=(azul verde); declare -A idade=([Ana]=29)
$ declare -p cores idade
declare -a cores=([0]="azul" [1]="verde")      « -a: array indexado
declare -A idade=([Ana]="29" )                 « -A: array associativo
$ declare -p PATH HOME
declare -x PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
declare -x HOME="/home/ana"                    « -x: exportada (variável de ambiente)

Ele brilha com caracteres invisíveis. Veja uma variável que veio de um arquivo do Windows, com um \r escondido no fim:

$ nome=$'Ana\r'
$ echo "[$nome]"
]Ana                                           « o \r volta o cursor e o ] cobre o [
$ declare -p nome
declare -- nome=$'Ana\r'                       « aqui o \r aparece com todas as letras

Mensagens de depuração e caller

Um echo de depuração que se desliga sozinho

O jeito mais antigo de depurar é espalhar echo pelo script. Faça isso do jeito certo: na saída de erro (para não misturar com o resultado) e só quando você pedir, com uma variável DEBUG:

#!/usr/bin/env bash
set -euo pipefail
debug() {
  if [[ -n ${DEBUG:-} ]]; then
    printf 'DEBUG: %s\n' "$*" >&2
  fi
}
debug "começando, argumentos: $*"
echo "trabalhando"
debug "terminei"

$ bash dbg2.sh x
trabalhando                                    « normal: nenhuma mensagem extra
$ DEBUG=1 bash dbg2.sh x
DEBUG: começando, argumentos: x
trabalhando
DEBUG: terminei
Não escreva [[ … ]] && echo como última linha da função

A versão "curta" debug() { [[ -n ${DEBUG:-} ]] && echo "DEBUG: $*" >&2; } devolve 1 quando DEBUG está vazia (o código do [[ ]]). Com set -e, a primeira chamada a debug mata o script sem mensagem nenhuma. Use if, como acima.

Quem me chamou? caller

Dentro de uma função, o comando interno caller diz de qual linha e arquivo ela foi chamada. Com um número (caller 0, caller 1…), ele sobe na pilha de chamadas e mostra também o nome da função:

#!/usr/bin/env bash
erro() {
  echo "erro: $1 (chamado na linha $(caller))" >&2
}
copiar() {
  cp "$1" ~/backup/ 2>/dev/null || erro "não copiei $1"
}
copiar nada.txt
echo "---"
caminho() {
  local i
  for ((i = 0; ; i++)); do
    caller "$i" || break
  done
}
a() { b; }
b() { caminho; }
a

$ bash quem.sh
erro: não copiei nada.txt (chamado na linha 6 quem.sh)   « a linha do "|| erro", dentro de copiar
---
17 b quem.sh                                   « caminho foi chamado na linha 17, dentro de b
16 a quem.sh                                   « b foi chamado na linha 16, dentro de a
18 main quem.sh                                « a foi chamado na linha 18, no corpo do script

"main" é como o Bash chama o corpo do script, fora de funções. Essa lista de chamadas (a pilha) é o que outras linguagens mostram num erro; com caller, você monta a sua.

Erros clássicos e como achá-los

"erro de sintaxe próximo ao token inesperado" 
$ cat sem-then.sh
#!/usr/bin/env bash
if [[ -f frutas.txt ]]
  echo "achei"
fi
$ bash sem-then.sh
sem-then.sh: linha 4: erro de sintaxe próximo ao token inesperado `fi'
sem-then.sh: linha 4: `fi'

O que aconteceu: um token é uma "peça" do comando (palavra-chave, operador). O Bash achou um fi onde esperava outra coisa: faltou o then (ou o ; antes dele, quando está na mesma linha). O erro de verdade costuma estar antes da linha apontada.

Como resolver: confira os pares: if … then … fi, for/while … do … done, case … in … esac, e o ; antes de then/do quando estão na mesma linha. Variantes do mesmo erro: token inesperado `done', `else', `}', `('.

"encontrado EOF inesperado enquanto procurava por `"' correspondente" 
$ cat aspas.sh
#!/usr/bin/env bash
echo "Olá, mundo
echo "fim"
$ bash -n aspas.sh
aspas.sh: linha 3: encontrado EOF inesperado enquanto procurava por `"' correspondente

O que aconteceu: EOF é end of file, "fim do arquivo". Uma aspa da linha 2 não foi fechada; o Bash leu tudo procurando o par e o arquivo acabou. O mesmo acontece com $( e $(( sem o fechamento: procurava por `)' correspondente.

Como resolver: procure a aspa aberta acima da linha apontada. Um editor com cores ajuda: tudo depois da aspa aberta fica da cor de texto. O ShellCheck também aponta a linha da aspa.

"fim inesperado do arquivo do comando `if'" 
$ bash -n sem-fi.sh
sem-fi.sh: linha 5: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 2

O que aconteceu: um bloco aberto (if, while, { de função…) não foi fechado.

Como resolver: a mensagem diz onde o bloco começou ("na linha 2"). Feche-o com fi/done/}. Indentar o código direito torna esse erro visível na hora.

$'\r', bash\r e ^M: o script veio do Windows 
$ bash windows.sh
Olá
windows.sh: linha 3: cd: $'Documentos\r': Arquivo ou diretório inexistente
$ ./windows.sh
env: ‘bash\r’: Arquivo ou diretório inexistente
env: usa -[v]S para passar opções em linhas shebang

O que aconteceu: no Windows, as linhas terminam com dois caracteres, \r\n (CRLF); no Linux, só com \n. O \r sobrando vira parte do último argumento de cada linha: a pasta procurada é Documentos\r, e o shebang pede um programa chamado bash\r.

Como confirmar:

$ cat -A windows.sh
#!/usr/bin/env bash^M$                         « ^M é o \r; $ marca o fim da linha
echo "OlM-CM-!"^M$
cd Documentos^M$
$ file windows.sh
windows.sh: Bourne-Again shell script, Unicode text, UTF-8 text executable, with CRLF line terminators

Como resolver: tire os \r: sed -i 's/\r$//' windows.sh (ou dos2unix windows.sh, se estiver instalado). No editor, salve com fim de linha "LF". No Git, configure core.autocrlf.

Não deu erro, mas fez a coisa errada (variável vazia)

O que aconteceu: uma variável estava vazia ou com outro valor, como o $frtua do exemplo. Sinais típicos: '' no rastro do -x, mensagens como [: -gt: esperado operador unário ou um comando que "pegou tudo".

Como resolver: rode com bash -x e procure ''; confira a variável com declare -p; ligue set -u para que nomes inexistentes virem erro.

O script para no meio sem mensagem

O que aconteceu: quase sempre é o set -e parando num comando que devolveu 1 sem ser um erro de verdade (grep sem resultado, ((n++)), a função debug curta).

Como resolver: bash -x script.sh: a última linha com + é o comando que parou o script. Para deixar isso permanente, use o trap … ERR de trap e Sinais, que mostra a linha do erro.

Resumo

  • bash -n checa a gramática sem rodar nada; não pega comandos ou valores errados.
  • bash -x (ou set -x … set +x) mostra cada comando já expandido: + é o script, ++ é um nível abaixo, '' é um argumento vazio.
  • PS4='+ ${BASH_SOURCE}:${LINENO}: ' põe arquivo e linha no rastro; BASH_XTRACEFD manda o rastro para um arquivo.
  • trap … DEBUG faz o passo a passo; declare -p mostra variáveis sem disfarce; caller diz quem chamou a função.
  • "token inesperado" e "EOF inesperado": o erro real costuma estar antes da linha apontada. ^M/\r: o arquivo veio do Windows, use sed -i 's/\r$//'.
