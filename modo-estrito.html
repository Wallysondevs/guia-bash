Bash Modo Estrito

Por padrão, o Bash é "bonzinho": se um comando falha, ele mostra o erro e continua para a próxima linha, como se nada tivesse acontecido. Num script que apaga ou copia arquivos, isso é perigoso. O modo estrito é a linha set -euo pipefail no topo do script: ela faz o Bash parar no primeiro erro, reclamar de variáveis que não existem e enxergar falhas no meio de um pipe.

Você vai aprender
  • O que cada parte de set -euo pipefail faz, com um teste antes e depois.
  • As situações em que o set -e não para o script (e por que elas existem).
  • Como usar ${var:-} para conviver com o set -u.
  • O debate: por que o modo estrito é uma rede de segurança, e não um substituto para tratar erros.
  • O que é o "unofficial strict mode" com IFS=$'\n\t', e por que este guia não o recomenda.

O problema: o Bash continua depois do erro

A Ana escreveu um script para limpar uma pasta de arquivos temporários. Por segurança, no lugar do rm -rf * ela deixou só um echo, para ver onde o script teria apagado:

#!/usr/bin/env bash
cd ~/pasta-temporaria
echo "Apagando tudo em: $PWD"
echo "(aqui viria um rm -rf *)"

Só que a pasta pasta-temporaria não existe. Veja o que acontece:

$ bash limpar.sh
limpar.sh: linha 2: cd: /home/ana/pasta-temporaria: Arquivo ou diretório inexistente
Apagando tudo em: /home/ana                    « o cd falhou, então continuamos na pasta pessoal!
(aqui viria um rm -rf *)
$ echo $?
0                                              « e o script ainda diz que deu tudo certo

Leia com calma: o cd falhou (linha 2), o Bash mostrou o erro e seguiu em frente. A pasta atual continuou sendo /home/ana. Se a linha 4 fosse mesmo rm -rf *, a Ana teria apagado a pasta pessoal inteira. E o código de saída do script é 0 ("sucesso"), porque o Bash devolve o código do último comando, o echo, que deu certo.

Isso não é um defeito: o Bash nasceu para ser usado no terminal, onde você vê o erro e decide o que fazer. Num script, ninguém está olhando. O modo estrito muda esse comportamento.

set -e: parar no primeiro erro

O comando interno set liga e desliga opções do shell. A opção -e tem o nome longo errexit (error exit, "sair no erro"): se um comando falhar (código diferente de 0), o script termina na hora, com o código desse comando.

set
Comando interno que liga (-) e desliga (+) opções do shell atual.
-e
Liga o errexit. É o mesmo que set -o errexit. Para desligar: set +e.
#!/usr/bin/env bash
set -e
cd ~/pasta-temporaria
echo "Apagando tudo em: $PWD"
echo "(aqui viria um rm -rf *)"

$ bash limpar-e.sh
limpar-e.sh: linha 3: cd: /home/ana/pasta-temporaria: Arquivo ou diretório inexistente
$ echo $?
1                                              « parou no cd e devolveu o código dele

Agora o script parou na linha 3. Nenhum echo rodou, e o código de saída é 1, o mesmo do cd que falhou. Quem chamou o script (você, outro script ou o cron) fica sabendo que deu errado.

"Falhar" quer dizer "devolver código diferente de 0"

O set -e não lê mensagens de erro: ele olha o código de saída. Por isso, um grep que não encontra nada (código 1) também conta como "falha" e para o script. Você vai ver esse caso daqui a pouco.

set -u: variável que não existe é erro

Agora outro script da Ana. Ela errou o nome de uma variável: criou pasta e usou psata.

#!/usr/bin/env bash
pasta=Documentos
echo "Arquivos em $psata:"
ls "$psata"

$ bash relatorio.sh
Arquivos em :                                  « $psata virou texto vazio, sem aviso
ls: não foi possível acessar '': Arquivo ou diretório inexistente
$ echo $?
2

Para o Bash, uma variável que não existe vale "nada". Ele não avisa, só troca por vazio. O erro aparece longe da causa, numa mensagem confusa do ls sobre um nome vazio ('').

A opção -u (nome longo nounset, "não definida") faz o Bash parar quando você usa uma variável que nunca recebeu valor:

#!/usr/bin/env bash
set -u
pasta=Documentos
echo "Arquivos em $psata:"
ls "$psata"

$ bash relatorio-u.sh
relatorio-u.sh: linha 4: psata: variável não associada     « aponta o nome e a linha exatos
$ echo $?
1

A mensagem "variável não associada" (em inglês, unbound variable) diz exatamente qual nome e qual linha. Com -u, o script sempre termina nesse erro, mesmo sem -e.

Vazia não é o mesmo que não definida

nome="" cria a variável com valor vazio: o set -u aceita. Ele só reclama de nomes que nunca receberam valor (ou que foram apagados com unset). Os parâmetros $1, $2… também contam: se o script foi chamado sem argumentos, $1 não existe.

Conviver com o -u: ${var:-}

Às vezes é normal uma variável não existir: um argumento opcional, ou uma variável de ambiente como DEBUG que só às vezes é definida. Veja o que o -u faz com um argumento que não veio:

#!/usr/bin/env bash
set -u
nome=$1
echo "Olá, $nome!"

$ bash saudar.sh
saudar.sh: linha 3: $1: variável não associada
$ echo $?
1
$ bash saudar.sh Bruno
Olá, Bruno!

A solução é a expansão ${var:-padrão}: "o valor de var; se não existir ou estiver vazia, use padrão". Com o padrão vazio, ${var:-}, você diz ao Bash: "sei que pode não existir, trate como vazio".

${1:-visitante}
O primeiro argumento; se não veio, a palavra visitante.
${DEBUG:-}
O valor de DEBUG; se não existe, texto vazio, sem erro.
#!/usr/bin/env bash
set -u
nome=${1:-visitante}
echo "Olá, $nome!"
if [[ -z ${DEBUG:-} ]]; then
  echo "(DEBUG desligado)"
fi
vazia=()
echo "argumentos: $# ${@}; itens: ${#vazia[@]} ${vazia[@]}"

$ bash saudar2.sh
Olá, visitante!
(DEBUG desligado)
argumentos: 0 ; itens: 0                      « "$@" e um array vazio não dão erro

A última linha mostra uma boa notícia: $@ sem argumentos e um array vazio (${vazia[@]}) não disparam o -u. bash 4.4+ No Bash 4.3 e anteriores (e no Bash 3.2 do macOS), "${vazia[@]}" com set -u dá "variável não associada"; lá, a saída é ${vazia[@]+"${vazia[@]}"}.

set -o pipefail: erro no meio do pipe

Num pipe, o código de saída é o do último comando. Os erros do meio somem:

$ cat compras.txt | wc -l
cat: compras.txt: Arquivo ou diretório inexistente
0
$ echo $?
0                                              « o wc deu certo, então o pipe "deu certo"

O arquivo nem existe, mas o pipe devolveu 0, porque o wc contou zero linhas sem problema. Nem o set -e veria esse erro.

A opção pipefail ("falha do pipe") muda a regra: o código do pipe passa a ser o do último comando que falhou (o mais à direita com código diferente de 0). Se todos deram certo, continua 0. Ela não tem letra curta: o nome vai depois de -o (option).

$ set -o pipefail
$ cat compras.txt | wc -l
cat: compras.txt: Arquivo ou diretório inexistente
0
$ echo $?
1                                              « agora o erro do cat aparece no código

A saída na tela é a mesma; o que mudou foi o código. É ele que o set -e e o if enxergam.

Quer saber o código de cada parte?

Logo depois do pipe, o array PIPESTATUS guarda o código de cada comando, da esquerda para a direita. Ele é sobrescrito pelo próximo comando (até por um echo $?), então leia na hora: cat compras.txt | wc -l; echo "${PIPESTATUS[@]}" mostra 1 0. Mais em Tratar Erros.

Missão: ligue o pipefail neste terminal e, por último, rode cat compras.txt | wc -l. O arquivo não existe: o pipe deve terminar com código 1. (Se quiser comparar, rode o pipe uma vez antes de ligar a opção e veja echo $?.)

Juntando tudo: set -euo pipefail

As três opções costumam vir juntas, numa linha só, logo depois do shebang. As letras curtas podem ser agrupadas, como em ls -la:

set -euo pipefail
set
Liga opções do shell que está rodando o script.
-e
errexit: um comando falhou → o script termina com o código dele.
-u
nounset: usou variável que não existe → erro e fim.
-o pipefail
O pipe falha se qualquer parte falhar. O o está grudado em -eu, e o nome pipefail é o argumento dele.

A linha é exatamente igual a estas três, escritas por extenso (mais fáceis de ler para quem está começando):

#!/usr/bin/env bash
set -o errexit    # = set -e
set -o nounset    # = set -u
set -o pipefail

Para conferir quais opções estão ligadas, use set -o (a lista completa) ou a variável $-, que guarda as letras ativas:

$ bash -euo pipefail -c 'echo $-; set -o | grep pipefail'
ehuBc                                          « e (errexit) e u (nounset) aparecem nas letras
pipefail       	on

Esse exemplo mostra outra forma de ligar as opções: na linha de comando do bash. Também funciona no shebang (#!/bin/bash -e), mas aí a opção se perde quando alguém roda bash script.sh, porque o shebang é ignorado. Prefira o set dentro do script.

Missão: coloque set -euo pipefail na segunda linha do script e clique em Rodar. O script vai terminar sem mostrar nada! Descubra o motivo na seção "Quando não funciona" mais abaixo e conserte, para que ele mostre Kiwis: 0.

#!/usr/bin/env bash
n=$(grep -c kiwi frutas.txt)
echo "Kiwis: $n"

#!/usr/bin/env bash
set -euo pipefail
n=$(grep -c kiwi frutas.txt || true)
echo "Kiwis: $n"

Quando o set -e não para o script

Esta é a parte que mais confunde. O set -e foi pensado para não atrapalhar os testes: se você escreve if grep …, o "não achei" do grep é uma resposta, não um erro. Por isso, o Bash ignora falhas em vários lugares. Veja todos de uma vez:

#!/usr/bin/env bash
set -e

if grep -q kiwi frutas.txt; then
  echo "tem kiwi"
fi
echo "1) falha dentro do if: o script continua"

grep -q kiwi frutas.txt && echo "tem kiwi"
echo "2) falha antes do &&: o script continua"

grep -q kiwi frutas.txt || echo "não tem kiwi"
echo "3) falha antes do ||: o script continua"

! grep -q banana frutas.txt
echo "4) comando com ! na frente: o script continua"

while grep -q kiwi frutas.txt; do :; done
echo "5) falha na condição do while: o script continua"

grep -q kiwi frutas.txt
echo "6) falha solta: esta linha NUNCA aparece"

$ bash excecoes.sh
1) falha dentro do if: o script continua
2) falha antes do &&: o script continua
não tem kiwi
3) falha antes do ||: o script continua
4) comando com ! na frente: o script continua
5) falha na condição do while: o script continua
$ echo $?
1                                              « só o grep "solto" (caso 6) parou o script

Não há kiwi em frutas.txt, então todo grep -q kiwi devolve 1. Mesmo assim, só o último parou o script. A regra do Bash é: o -e não age quando o comando que falhou está sendo testado.

Condição de while/untilwhile read -r l; doNão

A pegadinha das funções

Uma função chamada dentro de um if (ou antes de &&/||) roda inteira com o -e desligado. Um erro no meio dela não para nada:

#!/usr/bin/env bash
set -e

copiar() {
  cp nada.txt destino.txt     # falha aqui...
  echo "copiar: terminei"     # ...mas esta linha roda?
}

if copiar; then
  echo "cópia OK"
fi
echo "--- agora chamando sem if ---"
copiar
echo "nunca chega aqui"

$ bash funcao-e.sh
cp: não foi possível obter estado de 'nada.txt': Arquivo ou diretório inexistente
copiar: terminei                               « dentro do if, o cp falhou e a função seguiu
cópia OK                                       « e ainda devolveu 0 (código do último echo)!
--- agora chamando sem if ---
cp: não foi possível obter estado de 'nada.txt': Arquivo ou diretório inexistente
$ echo $?
1                                              « fora do if, o -e funcionou

A primeira chamada é a mais traiçoeira: o cp falhou, a função continuou, e como o último comando dela (echo) deu certo, ela devolveu 0. O if achou que a cópia foi feita. A solução é a função checar os próprios erros (cp nada.txt destino.txt || return 1), como você vai ver em Tratar Erros.

A pegadinha do local x=$(…)

#!/usr/bin/env bash
set -e

contar() {
  local linhas=$(wc -l < compras.txt)
  echo "contar: $linhas linhas (o local escondeu a falha)"
  local total
  total=$(wc -l < compras.txt)
  echo "contar: nunca chega aqui"
}
contar

$ bash local-e.sh
local-e.sh: linha 5: compras.txt: Arquivo ou diretório inexistente
contar:  linhas (o local escondeu a falha)     « a linha 5 falhou e o script seguiu
local-e.sh: linha 8: compras.txt: Arquivo ou diretório inexistente
$ echo $?
1                                              « a linha 8 parou o script

Na linha 5, o código que o -e vê é o do comando local, que conseguiu criar a variável (código 0). O erro do $( ) se perde. Separando em duas linhas (7 e 8), a atribuição total=$(…) fica sozinha e devolve o código do $( ). Vale o mesmo para export x=$(…), declare x=$(…) e readonly x=$(…). O ShellCheck avisa esse caso (aviso SC2155).

Dentro de $( ): shopt -s inherit_errexit

A substituição de comando roda num subshell, e esse subshell não herda o -e:

$ cat subst-e.sh
#!/usr/bin/env bash
set -e
echo "Resultado: $(false; echo 'continuei dentro do $( )')"
$ bash subst-e.sh
Resultado: continuei dentro do $( )            « o false não parou o subshell

A opção inherit_errexit (herdar o errexit), ligada com shopt -s, faz o $( ) herdar o -e. bash 4.4+

$ cat atrib-e.sh
#!/usr/bin/env bash
set -e
shopt -s inherit_errexit
resultado=$(false; echo "x")
echo "fim"
$ bash atrib-e.sh
$ echo $?
1                                              « o subshell parou no false, e a atribuição falhou

Repare: com inherit_errexit, o subshell parou no false e devolveu 1. Como era uma atribuição simples, o script também parou. Se o $( ) estivesse no meio de um echo, o subshell pararia, mas o echo de fora rodaria normalmente (com o texto vazio).

O debate: o modo estrito é bom ou ruim?

Programadores experientes discordam sobre o set -e. Os dois lados têm razão em parte:

A favorContra
Um erro esquecido não vira desastre (o cd que falha antes do rm).As exceções (funções em if, local, $( )) dão a falsa sensação de que tudo está protegido.
O -u pega erros de digitação em nomes de variáveis na hora.Comandos que devolvem 1 como resposta (grep sem resultado, ((n++)) com n=0, diff com diferenças) matam o script sem mensagem nenhuma.
O script devolve um código de erro de verdade para quem chamou (cron, CI, outro script).O comportamento mudou entre versões do Bash e difere de outros shells.
Custa uma linha.O script para em silêncio: muitas vezes a única pista é o código de saída.

A posição deste guia: use set -euo pipefail nos seus scripts, como rede de segurança. Mas continue checando os erros que importam, com if, || e mensagens claras (Tratar Erros), e mostre de onde veio a falha com um trap … ERR. Uma rede de segurança não é um plano de voo.

O "unofficial strict mode" e o IFS=$'\n\t'

Na internet, você vai achar esta receita, chamada de unofficial bash strict mode ("modo estrito não oficial"):

#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'

A terceira linha muda o IFS (Internal Field Separator, "separador interno de campos"): a lista de caracteres que o Bash usa para quebrar variáveis sem aspas em palavras. O padrão é espaço, tab e quebra de linha. A receita tira o espaço, para que um nome como Área de trabalho não vire três pedaços. Veja o que ela muda de verdade:

#!/usr/bin/env bash
pasta="Área de trabalho"
echo "--- IFS padrão, sem aspas:"
for p in $pasta; do echo "[$p]"; done
IFS=$'\n\t'
echo "--- IFS=\$'\n\t', sem aspas:"
for p in $pasta; do echo "[$p]"; done
frutas=(banana maçã uva)
echo "--- \"\${frutas[*]}\" com o IFS novo:"
echo "${frutas[*]}"
linha="Ana 29 Recife"
read -r nome idade cidade <<< "$linha"
echo "--- read com o IFS novo: nome=[$nome] idade=[$idade]"

$ bash ifs.sh
--- IFS padrão, sem aspas:
[Área]
[de]
[trabalho]                                     « o problema que a receita quer evitar
--- IFS=$'\n\t', sem aspas:
[Área de trabalho]                             « resolvido…
--- "${frutas[*]}" com o IFS novo:
banana
maçã
uva                                            « …mas ${a[*]} agora junta com quebra de linha
--- read com o IFS novo: nome=[Ana 29 Recife] idade=[]   « …e o read parou de separar por espaço

A crítica: o IFS global muda o comportamento de read, "$*", "${a[*]}" e de todo comando do script, inclusive em código copiado de outro lugar que esperava o IFS normal. E ele esconde o problema real, que é a falta de aspas. A solução certa é a mais simples:

  • Use aspas sempre: for p in "$pasta", "$@", "${a[@]}".
  • Quando precisar de outro separador, mude o IFS só para um comando: IFS=, read -r nome idade cidade nota. Fora dessa linha, o IFS continua o de sempre.

Formas de ligar o modo estrito: qual usar?

FormaExemploQuando usar
Linha curta no scriptset -euo pipefailO padrão. Vale mesmo se rodarem bash script.sh.
Por extensoset -o errexit -o nounset -o pipefailQuando o script será lido por iniciantes.
No shebang#!/bin/bash -eEvite: bash script.sh ignora o shebang e a opção some. E env não aceita opções extras de forma portável.

Quando não funciona

O script terminou sem mostrar nada 
$ cat contar-kiwi.sh
#!/usr/bin/env bash
set -euo pipefail
n=$(grep -c kiwi frutas.txt)
echo "Kiwis: $n"
$ bash contar-kiwi.sh
$ echo $?
1

O que aconteceu: não há kiwi; o grep -c imprime 0, mas devolve o código 1 ("não achei"). A atribuição n=$(…) devolve esse 1, e o -e encerra o script calado.

Como confirmar: rode o script com bash -x contar-kiwi.sh (veja Depurar): a última linha + mostra o comando que estava rodando.

Como resolver: diga que essa falha é esperada: n=$(grep -c kiwi frutas.txt || true). O || true transforma o código em 0. Com a correção, o script mostra Kiwis: 0.

Um ((contador++)) mata o script 
$ cat aritm-e.sh
#!/usr/bin/env bash
set -e
n=0
((n++))
echo "n vale $n"
$ bash aritm-e.sh
$ echo $?
1

O que aconteceu: ((expressão)) devolve 1 quando o resultado é zero. n++ devolve o valor antigo (0) e só depois soma, então o código é 1.

Como resolver: use ((++n)) (devolve o valor novo), n=$((n + 1)) (uma atribuição, sempre 0) ou ((n++)) || true. Veja Contas.

"variável não associada" num argumento opcional 
$ bash saudar.sh
saudar.sh: linha 3: $1: variável não associada

O que aconteceu: com set -u, $1 sem argumento é uma variável que não existe.

Como resolver: dê um padrão: nome=${1:-visitante}, ou teste antes com if [[ $# -eq 0 ]] e mostre uma mensagem de uso (Tratar Erros).

Com pipefail, | head dá erro 141 
$ set -o pipefail
$ seq 1 200000 | head -n 1
1
$ echo "${PIPESTATUS[@]}"
141 0

O que aconteceu: o head leu uma linha e saiu. O seq ainda tentava escrever no pipe, recebeu o sinal SIGPIPE ("cano quebrado") e morreu com código 141 (128 + 13, o número do sinal; veja trap e Sinais). Com pipefail, o pipe inteiro "falha". Com pouca saída (como seq 1 10), o seq termina antes e o erro não aparece; por isso o problema é intermitente.

Como resolver: se o corte é intencional, aceite a falha: seq 1 200000 | head -n 1 || true, ou deixe o próprio comando parar sozinho (sed -n 1p e awk 'NR==1' leem tudo e não quebram o cano).

Eu liguei set -e no terminal e ele fechou

O que aconteceu: o set -e vale para o shell em que você o roda. No terminal, o primeiro comando que falhar (até um ls nada) encerra o shell, e a janela fecha.

Como resolver: use o modo estrito só dentro de scripts. Para testar no terminal, abra um shell filho antes (bash) ou use bash -c 'set -e; …'.

Resumo

  • Sem opções, o Bash continua depois de um erro e o script pode devolver 0 mesmo tendo falhado.
  • set -e para no primeiro comando "solto" que falha; set -u para em variáveis inexistentes; set -o pipefail faz o pipe falhar se qualquer parte falhar.
  • O -e é ignorado em testes (if, while, &&, ||, !), em funções chamadas nesses lugares, em local x=$(…) e dentro de $( ) sem inherit_errexit.
  • Use ${var:-} para variáveis opcionais e || true para falhas esperadas.
  • O modo estrito é uma rede de segurança: continue tratando os erros importantes com if/|| e mensagens claras. Prefira aspas a mudar o IFS global.
