Bash trap e Sinais

Um sinal é um aviso curto que o sistema (ou outro programa) manda para um processo: "pare", "o terminal fechou", "aperte o freio". O comando trap (armadilha) deixa o seu script capturar esses avisos e rodar um código antes de reagir. O uso mais importante é simples: limpar a bagunça (arquivos temporários, travas) sempre que o script terminar, dê certo ou dê errado.

Você vai aprender
  • O que são os sinais mais comuns (INT, TERM, HUP, KILL…) e de onde eles vêm.
  • A apagar arquivos temporários com mktemp + trap … EXIT, o padrão mais útil desta aula.
  • A perguntar "Tem certeza?" quando alguém aperta Ctrl+C.
  • A mostrar onde o script falhou com trap … ERR, $LINENO e $BASH_COMMAND.
  • A listar, desfazer e ignorar traps (trap -p, trap - SINAL, trap '' SINAL), e por que o KILL não pode ser capturado.

O que é um sinal

Quando você aperta Ctrl+C no terminal, você não "digita" nada para o programa: o terminal manda a ele o sinal INT (interrupt, interromper). O comportamento padrão da maioria dos sinais é matar o processo. Por isso o Ctrl+C para um script no meio do caminho, deixando para trás o que ele não terminou de fazer.

Cada sinal tem um nome e um número. O comando interno kill -l (list) mostra todos:

$ kill -l

 6) SIGABRT	 7) SIGBUS	 8) SIGFPE	 9) SIGKILL	10) SIGUSR1

O prefixo SIG é opcional: SIGINT, INT e 2 são o mesmo sinal. Você só precisa conhecer alguns:

Além dos sinais de verdade, o trap do Bash conhece quatro eventos do próprio shell, que não vêm de fora:

EventoQuando o trap roda
EXIT (ou 0)Quando o shell/script termina, por qualquer motivo: fim do arquivo, exit, erro com set -e, Ctrl+C, TERM.
ERRQuando um comando falha (as mesmas regras do set -e).
DEBUGAntes de cada comando simples.
RETURNQuando uma função (ou um source) termina.

A sintaxe do trap

trap 'COMANDOS' SINAL [SINAL…]
trap
Comando interno: "quando chegar este sinal, rode isto".
'COMANDOS'
O código a rodar, entre aspas simples (o motivo está mais abaixo). Pode ser o nome de uma função.
SINAL
Um ou mais nomes: EXIT, INT, TERM…

O primeiro exemplo é no próprio terminal. Pedimos para o shell dizer "recebi TERM" e mandamos o sinal para ele mesmo ($$ é o número do processo do shell atual, o PID):

$ trap 'echo recebi TERM' TERM
$ kill -TERM $$
recebi TERM                                    « o trap rodou
$ echo "ainda estou aqui"
ainda estou aqui                               « e o shell não morreu: o trap substituiu o padrão

Repare na última linha: quando você captura um sinal, o comportamento padrão (morrer) não acontece mais. Se você quer que o script termine, o trap precisa ter um exit.

Limpar ao sair: mktemp + trap … EXIT

Scripts muitas vezes precisam de um arquivo de rascunho. Dois cuidados: o nome deve ser único (para dois scripts não usarem o mesmo arquivo) e o arquivo precisa ser apagado no fim, mesmo se o script falhar.

Criar o arquivo temporário: mktemp

mktemp (make temporary) cria um arquivo vazio com nome aleatório em /tmp, só com permissão para você, e mostra o nome. Você guarda esse nome numa variável:

$ mktemp
/tmp/tmp.Cj1guHJHnV                            « os X do modelo viram letras aleatórias
$ mktemp -d
/tmp/tmp.4UDv9VHo11                            « -d: cria uma pasta em vez de um arquivo
$ mktemp /tmp/relatorio.XXXXXX.txt
/tmp/relatorio.Rxae7c.txt                      « modelo próprio: os XXXXXX são trocados
$ mktemp -t backup.XXXX
/tmp/backup.qpGT                               « -t: o modelo vai para a pasta temporária ($TMPDIR ou /tmp)

Os nomes mudam a cada vez; é justamente essa a ideia.

Apagar sempre: trap … EXIT

#!/usr/bin/env bash
set -euo pipefail
tmp=$(mktemp)
trap 'rm -f -- "$tmp"; echo "limpeza: apaguei $tmp" >&2' EXIT
echo "trabalhando com $tmp"
sort frutas.txt > "$tmp"
uniq -c "$tmp"
ls nada.txt
echo "nunca chega aqui"
tmp=$(mktemp)
Cria o arquivo e guarda o nome dele em tmp.
trap '…' EXIT
Registra a limpeza logo depois de criar o arquivo. Ela vai rodar quando o script terminar, seja como for.
rm -f -- "$tmp"
Apaga o arquivo. -f não reclama se ele já sumiu; -- protege contra nomes estranhos.
ls nada.txt
Um erro de propósito: com set -e, o script para aqui.
$ bash tmp1.sh
trabalhando com /tmp/tmp.UBwMIbL0Uy
      3 banana
      1 laranja
      2 maçã
      1 uva
ls: não foi possível acessar 'nada.txt': Arquivo ou diretório inexistente
limpeza: apaguei /tmp/tmp.UBwMIbL0Uy           « o trap rodou depois do erro
$ echo $?
2                                              « o código do erro (o do ls) é mantido
$ ls /tmp                                      « nada aparece: a pasta ficou vazia

O script falhou na linha do ls, e mesmo assim o rascunho foi apagado. O código de saída continuou sendo o do erro (2): o trap de EXIT não "engole" a falha, a não ser que você chame exit com outro número dentro dele.

Por que aspas simples no trap?

Com aspas simples, $tmp só é lido quando o trap roda. Com aspas duplas, ele é trocado pelo valor na hora em que você escreve o trap. Aqui daria no mesmo, mas se a variável mudar depois (ou ainda estiver vazia), as aspas duplas apagariam o arquivo errado. Prefira sempre aspas simples. O ShellCheck avisa (SC2064).

Uma função de limpeza

Quando há várias coisas a desfazer, escreva uma função e passe o nome dela ao trap. Uma pasta temporária (mktemp -d) simplifica: tudo vai dentro dela e um rm -rf limpa de uma vez.

#!/usr/bin/env bash
set -euo pipefail

trabalho=$(mktemp -d)
limpar() {
  rm -rf -- "$trabalho"
}
trap limpar EXIT

# … o resto do script usa "$trabalho/arquivo1", "$trabalho/arquivo2" …

Missão: este script cria ~/rascunho.txt e falha antes de apagá-lo. Acrescente, logo depois da linha rascunho=…, um trap de EXIT que apague o arquivo e mostre limpeza feita na saída de erro. Rode: o erro do ls continua, mas o rascunho deve sumir.

#!/usr/bin/env bash
set -euo pipefail
rascunho=~/rascunho.txt
sort frutas.txt > "$rascunho"
uniq -c "$rascunho"
ls nada.txt
echo "fim"

#!/usr/bin/env bash
set -euo pipefail
rascunho=~/rascunho.txt
trap 'rm -f -- "$rascunho"; echo "limpeza feita" >&2' EXIT
sort frutas.txt > "$rascunho"
uniq -c "$rascunho"
ls nada.txt
echo "fim"

Ctrl+C: perguntar "Tem certeza?"

Um script longo pode querer confirmar antes de parar. Capture o INT com uma função que pergunta:

#!/usr/bin/env bash
perguntar() {
  echo
  read -rp "Tem certeza que quer parar? [s/N] " resp
  if [[ $resp == [sS] ]]; then
    echo "Saindo a pedido."
    exit 130
  fi
  echo "Continuando..."
}
trap perguntar INT

for i in 1 2 3 4 5; do
  echo "passo $i de 5"
  sleep 1
done
echo "Terminei."

Esta sessão foi feita num terminal de verdade, apertando Ctrl+C duas vezes (o terminal mostra ^C):

$ bash contagem.sh
passo 1 de 5
passo 2 de 5
^C                                             « primeiro Ctrl+C
Tem certeza que quer parar? [s/N] n
Continuando...
passo 3 de 5
passo 4 de 5
^C                                             « segundo Ctrl+C
Tem certeza que quer parar? [s/N] s
Saindo a pedido.
$ echo $?
130
echo
Pula uma linha, porque o ^C deixa o cursor no meio.
read -rp "…" resp
Pergunta e guarda a resposta (read).
[[ $resp == [sS] ]]
Aceita s ou S. Qualquer outra coisa (até Enter vazio) é "não", como indica o N maiúsculo em [s/N].
exit 130
Sai com o código combinado para Ctrl+C: 128 + 2 (o número do INT).

Sem o trap, o primeiro Ctrl+C já mata o script, e o código também é 130:

$ bash semtrap.sh
passo 1 de 5
passo 2 de 5
^C
$ echo $?
130
O trap espera o comando atual terminar

O Bash só roda o trap entre um comando e outro. Aqui funcionou rápido porque o Ctrl+C também interrompe o sleep (os dois recebem o sinal). Mas um kill -TERM mandado só para o script, enquanto ele espera um sleep 300, só é atendido depois dos 300 segundos. Para reagir na hora, rode o comando demorado em segundo plano e espere com wait: sleep 300 & wait $! (veja Jobs).

Mandar sinais: kill

Apesar do nome, kill não só "mata": ele manda um sinal para um processo, identificado pelo PID. Sem opção, manda TERM.

kill PID
Manda TERM: "termine, por favor".
kill -HUP PID
Escolhe o sinal pelo nome (também vale -SIGHUP, -s HUP ou -1).
kill -TERM $$
Manda para o próprio shell. $! é o PID do último comando posto em segundo plano.

Para ver vários sinais sendo capturados, a Ana fez um script que fica rodando por uns segundos e responde a cada um:

#!/usr/bin/env bash
# vigia.sh — fica rodando e reage a sinais
trap 'echo "[vigia] HUP: relendo a configuração"' HUP
trap 'echo "[vigia] USR1: estou vivo, PID $$"' USR1
trap 'echo "[vigia] TERM: encerrando com calma"; exit 0' TERM
echo "[vigia] começando, PID $$"
for ((i = 1; i <= 30; i++)); do
  sleep 0.2
done
echo "[vigia] acabou o tempo"

Ela roda o vigia em segundo plano (&) e manda os sinais com kill. As mensagens do vigia aparecem misturadas com os prompts, porque ele escreve no mesmo terminal enquanto ela digita:

$ bash vigia.sh &
[1] 46726                                      « número do job e PID do vigia
$ sleep 0.5
[vigia] começando, PID 46726
$ kill -HUP $!
$ sleep 0.5
[vigia] HUP: relendo a configuração
$ kill -USR1 $!
$ sleep 0.5
[vigia] USR1: estou vivo, PID 46726
$ kill $!                                      « sem opção = TERM
$ wait $!
[vigia] TERM: encerrando com calma
$ echo $?
0                                              « o trap saiu com exit 0

E se ninguém capturar? O código 128 + N

Quando um processo morre por causa de um sinal, o Bash informa o código 128 + número do sinal. Com isso, quem chamou sabe que não foi um erro comum:

CódigoSinalSituação típica
129HUP (1)O terminal fechou.
130INT (2)Ctrl+C.
137KILL (9)kill -9, ou o sistema matou por falta de memória.
141PIPE (13)Pipe quebrado (… | head).
143TERM (15)kill comum.
#!/usr/bin/env bash
trap 'echo "EXIT: limpando"' EXIT
echo "vou me mandar um TERM"
kill -TERM $$
echo "depois do kill"

$ bash term1.sh
vou me mandar um TERM
EXIT: limpando                                 « o TERM não foi capturado, mas o EXIT rodou
$ echo $?
143                                            « 128 + 15

Uma boa notícia do Bash: mesmo morrendo por um sinal que você não capturou (como TERM ou INT), ele roda o trap de EXIT antes. Por isso, para limpeza, trap limpar EXIT sozinho costuma bastar. Em outros shells (como o dash, que é o sh do Debian/Ubuntu) isso não é garantido; lá, escreva trap limpar EXIT INT TERM.

O KILL não pode ser capturado

#!/usr/bin/env bash
trap 'echo "peguei o KILL?"' KILL
echo "trap aceito? código $?"
trap -p KILL
kill -KILL $$
echo "depois"

$ bash kill9.sh
trap aceito? código 0                          « o Bash não reclama…
trap -- 'echo "peguei o KILL?"' SIGKILL        « …e até lista o trap…
$ echo $?
137                                            « …mas ele nunca roda

O KILL (e o STOP) são tratados pelo próprio sistema operacional, sem passar pelo programa. É a garantia de que sempre dá para parar um processo travado, mas também significa que nenhuma limpeza acontece. Por isso, use kill -9 só depois de tentar kill (TERM) e esperar um pouco.

Onde o script falhou? trap … ERR

Com set -e, o script para em silêncio. O evento ERR roda quando um comando falha, e duas variáveis dizem onde:

$LINENO
O número da linha que está rodando. Dentro do trap de ERR, é a linha do comando que falhou.
$BASH_COMMAND
O texto do comando que estava rodando.
$?
No começo do trap, o código do comando que falhou.
set -E
(errtrace) Faz o trap de ERR valer também dentro de funções e de $( ). Sem ele, erros dentro de funções não disparam o trap.
#!/usr/bin/env bash
set -eEuo pipefail
trap 'echo "${0##*/}: erro na linha $LINENO: \"$BASH_COMMAND\" devolveu $?" >&2' ERR

contar() {
  grep -c kiwi frutas.txt
}
echo "começando"
contar
echo "fim"

$ bash err1.sh
começando
0                                              « o grep -c imprime 0, mas devolve 1
err1.sh: erro na linha 6: "grep -c kiwi frutas.txt" devolveu 1
$ echo $?
1

Agora a falha silenciosa ganhou endereço: linha 6, dentro da função contar, o grep devolveu 1. Repare no -E grudado em set -eEuo pipefail: sem ele, o trap não veria o erro dentro da função.

Missão: acrescente, na linha 3 (a que está em branco), um trap de ERR que mostre erro na linha N na saída de erro, usando $LINENO. Rode: deve aparecer erro na linha 5, a linha do cp.

#!/usr/bin/env bash
set -euo pipefail

echo "copiando..."
cp nada.txt copia.txt
echo "pronto"

#!/usr/bin/env bash
set -euo pipefail
trap 'echo "erro na linha $LINENO" >&2' ERR
echo "copiando..."
cp nada.txt copia.txt
echo "pronto"

DEBUG e RETURN

O evento DEBUG roda antes de cada comando. Serve para acompanhar o script passo a passo:

#!/usr/bin/env bash
trap 'echo "  [linha $LINENO] vai rodar: $BASH_COMMAND"' DEBUG
nome=Ana
total=$(wc -l < frutas.txt)
echo "$nome tem $total frutas"

$ bash debug.sh
  [linha 3] vai rodar: nome=Ana
  [linha 4] vai rodar: total=$(wc -l < frutas.txt)
  [linha 5] vai rodar: echo "$nome tem $total frutas"
Ana tem 7 frutas

Repare que o $BASH_COMMAND mostra o comando antes das expansões ($nome ainda aparece como $nome). Para ver os valores trocados, use set -x. Os dois estão em Depurar, inclusive um "passo a passo" que espera Enter antes de cada linha.

O evento RETURN roda quando uma função termina. Definido dentro da função, vale só para ela:

#!/usr/bin/env bash
saudar() {
  trap 'echo "  (saindo de ${FUNCNAME[0]})"' RETURN
  echo "Olá, $1"
}
saudar Ana
saudar Bruno

$ bash retorno.sh
Olá, Ana
  (saindo de saudar)
Olá, Bruno
  (saindo de saudar)

Na prática, RETURN é raro: ele serve para desfazer algo que a função mudou (voltar de um cd, religar uma opção).

Ver, desfazer e ignorar traps

ComandoO que faz
trap -p (ou só trap)Lista os traps definidos, no formato de comando (dá para copiar e colar).
trap -p INTMostra só o trap de INT.
trap - INTRemove o trap: INT volta ao comportamento padrão.
trap '' INTIgnora o sinal: Ctrl+C não faz nada. Programas que o script chamar também vão ignorá-lo.
trap -lLista os nomes de sinais (igual a kill -l).
$ trap 'echo tchau' EXIT
$ trap -p
trap -- 'echo tchau' EXIT
$ trap - EXIT
$ trap -p                                      « nada listado: nenhum trap

Ignorar um sinal é útil para proteger um trecho que não pode ser interrompido pela metade (por exemplo, enquanto troca um arquivo de configuração pelo novo):

#!/usr/bin/env bash
trap '' INT
echo "Ctrl+C desligado durante a parte crítica"
trap -p INT
trap - INT
echo "de volta ao normal:"
trap -p INT
echo "(nada listado = comportamento padrão)"

$ bash ignora.sh
Ctrl+C desligado durante a parte crítica
trap -- '' SIGINT
de volta ao normal:
(nada listado = comportamento padrão)

Formas de limpar: qual usar?

FormaProblema / vantagemUse quando
rm "$tmp" no fim do scriptNão roda se o script falhar, sair antes ou levar Ctrl+C.Nunca como única limpeza.
rm antes de cada exitFácil esquecer um; repetição.Evite.
trap limpar EXITRoda sempre (menos com KILL). No Bash, cobre também INT e TERM.O padrão.
trap limpar EXIT INT TERMNecessário em sh/dash. No Bash, a limpeza pode rodar duas vezes (use rm -f, que não se importa).Scripts POSIX.

Quando não funciona

"especificação de sinal inválida" 
$ trap 'echo x' NADA
bash: trap: NADA: especificação de sinal inválida
$ echo $?
1

O que aconteceu: o nome do sinal está errado. Um erro comum é inverter a ordem: trap EXIT 'rm …' (o sinal tem que vir depois do comando).

Como resolver: confira o nome com trap -l e escreva trap 'COMANDOS' SINAL.

O trap apagou o arquivo errado (ou nada)

O que aconteceu: o trap foi escrito com aspas duplas antes de a variável receber valor: trap "rm -f $tmp" EXIT seguido de tmp=$(mktemp). O trap ficou rm -f , sem nome.

Como confirmar: rode trap -p EXIT no script: você vê o comando exatamente como ficou guardado.

Como resolver: use aspas simples e defina o trap depois do mktemp.

Definir o trap duas vezes apagou o primeiro

O que aconteceu: cada sinal tem um trap. trap 'rm -f a' EXIT e depois trap 'rm -f b' EXIT deixa só o segundo.

Como resolver: use uma função limpar que apaga tudo, ou guarde os arquivos numa pasta de mktemp -d e apague a pasta.

O kill não fez o script parar na hora

O que aconteceu: o script estava esperando um comando demorado (sleep, wget…) em primeiro plano, e o Bash só roda traps entre comandos.

Como resolver: espere o comando com cmd & wait $!: o wait é interrompido pelo sinal e o trap roda na hora. Se o processo está mesmo travado, kill -9 PID (sem limpeza).

O trap de ERR não disparou dentro da função

O que aconteceu: sem set -E (errtrace), funções, $( ) e subshells não herdam o trap de ERR.

Como resolver: acrescente -E: set -eEuo pipefail. Lembre também que o ERR segue as exceções do set -e: falhas dentro de if ou antes de || não o disparam (Modo Estrito).

Resumo

  • Sinais são avisos ao processo: INT (Ctrl+C), TERM (kill), HUP (terminal fechou), KILL (não capturável). Quem morre por sinal sai com 128 + N.
  • trap 'cmd' SINAL troca o comportamento padrão pelo seu código; para terminar, o trap precisa de exit.
  • O padrão mais útil: tmp=$(mktemp) + trap 'rm -f -- "$tmp"' EXIT, com aspas simples.
  • trap … ERR com $LINENO e $BASH_COMMAND (e set -E) mostra onde o script falhou; DEBUG roda antes de cada comando.
  • trap -p lista, trap - SINAL desfaz, trap '' SINAL ignora.
