Bash Formas de Executar

Existe mais de um jeito de rodar um script, e eles não são equivalentes. Alguns abrem um Bash novo, separado do seu; outro executa as linhas dentro do próprio terminal em que você está. Essa diferença explica um dos mistérios mais comuns de quem começa: "coloquei um cd no script e a minha pasta não mudou".

Você vai aprender
  • As seis formas: ./script.sh, bash script.sh, source (e o ponto .), pelo PATH, bash -c e exec.
  • Qual precisa de chmod +x e qual roda num processo separado.
  • Por que o cd e as variáveis de um script "somem" quando ele termina, e como usar source quando você quer que fiquem.
  • O que são $0 e $BASH_SOURCE.

Conceito: processo pai e processo filho

Cada programa que roda no computador é um processo, com um número de identificação, o PID (process ID). O terminal em que você digita é um processo bash. A variável especial $$ guarda o PID do Bash atual.

Quando você roda um script do jeito "normal", o seu Bash cria um Bash filho: um processo novo, que lê o script, executa e termina. O filho recebe uma cópia do ambiente do pai, mas tudo o que ele muda (pasta atual, variáveis) morre com ele. É como mandar alguém fazer um serviço em outra sala: ele pode arrumar a sala dele, mas a sua continua igual.

  ./vai.sh  (processo filho)                 source vai.sh  (mesmo processo)

  seu bash (PID 25786)                       seu bash (PID 25786)
     │                                          │
     └──► bash filho (PID 25791)                └──► lê vai.sh e executa
            cd ~/Documentos                            cd ~/Documentos
            cor=azul                                   cor=azul
            termina ✗ (leva tudo junto)             você continua em Documentos, cor=azul

Vamos provar com um script que muda de pasta, cria uma variável e mostra o próprio PID:

#!/usr/bin/env bash
# vai.sh — entra em Documentos e cria uma variável
cd ~/Documentos
cor=azul
echo "Dentro do script: estou em $PWD, cor=$cor, PID $$"

Os números de PID abaixo mudam a cada vez que você roda; o que importa é comparar se são iguais ou diferentes.

Forma 1: ./script.sh

É a forma que você viu em Seu Primeiro Script. O sistema lê o shebang (#!/usr/bin/env bash) e inicia o interpretador indicado. Por isso exige a permissão de execução.

./
O caminho: o arquivo está na pasta atual.
vai.sh
O script. Precisa ter o x (chmod +x) e um shebang.
$ echo "Meu shell: PID $$"
Meu shell: PID 25786
$ chmod +x vai.sh
$ ./vai.sh
Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 25791     « outro PID: é um filho
$ pwd
/home/ana                                                                « você não saiu do lugar
$ echo "cor=$cor"
cor=                                                                     « a variável não existe aqui

Dentro do script, o cd funcionou: o $PWD mostra Documentos. Mas isso aconteceu no processo filho (PID 25791). Quando ele terminou, a pasta e a variável dele sumiram. O seu terminal (PID 25786) continua em /home/ana, e $cor está vazia.

Isso é uma proteção, não um defeito

Imagine se cada script que você roda pudesse mudar a sua pasta, apagar suas variáveis ou trocar o seu PATH. Rodar em processo separado garante que o script não bagunça o seu terminal.

Forma 2: bash script.sh

Aqui é você quem chama o Bash e entrega o arquivo para ele ler. O sistema não precisa "executar" o arquivo, só o Bash precisa lê-lo. Por isso não precisa de chmod +x, e o shebang é ignorado (quem vai ler já foi escolhido: o bash).

bash
Inicia um Bash novo (um processo filho).
vai.sh
O arquivo que ele vai ler e executar. Basta poder lê-lo.
$ ls -l vai.sh
-rw-rw-r-- 1 ana ana 156 out 15 10:30 vai.sh       « sem x
$ ./vai.sh
bash: ./vai.sh: Permissão negada
$ bash vai.sh
Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 25789     « funcionou, mesmo sem x
$ pwd
/home/ana

Continua sendo um filho (PID diferente), então o cd também não fica. É a forma ideal para testar um script rapidinho, para rodar arquivos de um pendrive (que não guarda permissões) e para escolher o interpretador na hora (bash -x vai.sh, para ver cada linha; veja Depurar).

sh script.sh não é a mesma coisa

sh pode ser outro shell. No Debian e no Ubuntu, é o dash, que não entende recursos do Bash como [[ ]]:

$ bash teste-sh.sh
Ana começa com A
$ sh teste-sh.sh
teste-sh.sh: 3: [[: not found          « o dash não conhece [[

Se o script é de Bash, rode com bash ou com ./. Veja POSIX sh e Bashismos.

Forma 3: source script.sh ou . script.sh

source (em inglês, "fonte", no sentido de "puxar de") manda o seu próprio Bash ler o arquivo e executar cada linha, como se você tivesse digitado. Não há processo filho. Então tudo o que o script muda, fica.

source
Comando interno do Bash: "leia este arquivo e execute aqui mesmo".
vai.sh
O arquivo. Não precisa de x nem de shebang.
$ source vai.sh
Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 25786     « o MESMO PID do seu shell
$ pwd
/home/ana/Documentos                                                    « agora você mudou de pasta
$ echo "cor=$cor"
cor=azul                                                                « e a variável ficou

O PID é o mesmo do terminal (25786): não houve filho. O cd e o cor=azul aconteceram no seu shell.

O ponto . é o mesmo comando, com um nome mais curto e mais antigo (vem do sh original; source é o nome do Bash). Repare no espaço depois do ponto:

$ cd
$ unset cor
$ . vai.sh
Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 25786
.
O comando "ponto", igual ao source. Funciona também no sh.
vai.sh
O arquivo. Não confunda . vai.sh (ponto, espaço, nome) com ./vai.sh (caminho).

Para que serve, na prática

  • Recarregar a configuração do terminal depois de editar: source ~/.bashrc.
  • Carregar variáveis de um arquivo de configuração, dentro de um script ou no terminal.
  • Carregar funções de uma "biblioteca" (veja Funções).
# config.sh — configurações do projeto (para carregar com source)
PROJETO="site"
PASTA="$HOME/Documentos/projetos/site"

$ source config.sh
$ echo "Projeto $PROJETO em $PASTA"
Projeto site em /home/ana/Documentos/projetos/site

Esse arquivo não tem shebang nem x: ele não foi feito para ser executado, e sim para ser carregado.

exit num arquivo carregado com source fecha o seu terminal

Como as linhas rodam no seu shell, um exit lá dentro encerra o seu shell: a janela do terminal fecha. Num arquivo feito para source, use return para sair mais cedo.

Missão: o arquivo vai.sh está na pasta da Ana. Rode-o primeiro com bash vai.sh e confira com pwd que você não saiu do lugar. Depois rode-o de um jeito que deixe você dentro de Documentos e com a variável cor valendo azul.

Forma 4: pelo nome, via PATH

Se o script está numa pasta do PATH (como ~/bin ou ~/.local/bin), você roda só pelo nome, de qualquer pasta. Por dentro, é igual ao ./: precisa de x, usa o shebang, e roda num processo filho.

$ mkdir -p ~/bin; mv quem.sh ~/bin/
$ source ~/.profile                « o .profile põe ~/bin no PATH se ela existir
$ quem.sh
$0          = /home/ana/bin/quem.sh
BASH_SOURCE = /home/ana/bin/quem.sh

O $0, que você vai ver logo abaixo, mostra o caminho completo onde o Bash achou o script. Como o PATH funciona por dentro está em PATH e Onde os Comandos Moram.

Forma 5: bash -c 'comandos'

Não precisa nem de arquivo: o -c (de command) entrega um texto com comandos para um Bash novo executar. É muito usado quando outro programa precisa rodar um comando de shell (o find -exec, o xargs, o sudo, o cron).

bash
Um Bash novo (filho).
-c
"O próximo argumento é o código a executar".
'echo "$0 recebeu: $1 e $2"'
O código, entre aspas simples para o seu shell não trocar os $ antes da hora.
meuteste
O primeiro argumento depois do código vira o $0 (o "nome" do mini-script).
maçã uva
Os seguintes viram $1, $2…
$ bash -c 'echo "Olá de um bash novo, PID $$"'
Olá de um bash novo, PID 26035
$ bash -c 'echo "$0 recebeu: $1 e $2"' meuteste maçã uva
meuteste recebeu: maçã e uva
$ bash -c 'cd /tmp; pwd'; pwd
/tmp                                   « o filho foi para /tmp
/home/ana                              « você continua em casa

Forma 6: exec

exec não cria filho: ele troca o processo atual pelo comando. O Bash que rodou o exec deixa de existir, e o comando novo assume o lugar dele, com o mesmo PID. Tudo o que vinha depois do exec nunca roda:

$ bash -c 'echo antes; exec echo "agora sou o echo"; echo "isto nunca roda"'
antes
agora sou o echo                       « a terceira parte sumiu: o bash virou o echo

No terminal, o uso mais comum é exec bash: troca o seu shell por um Bash novinho (relendo o ~/.bashrc), sem empilhar um filho em cima do outro. Compare com digitar só bash:

$ echo "PID: $$"
PID: 36609
$ bash                                 « abre um filho por cima
$ echo "PID: $$"
PID: 36610
$ exit                                 « sai do filho e volta ao pai
exit
$ echo "PID: $$"
PID: 36609
$ exec bash                            « troca o shell, mesmo PID
$ echo "PID: $$"
PID: 36609

Em scripts, exec aparece no fim de "scripts de partida", que preparam o ambiente e depois se transformam no programa principal (exec python3 app.py). O exec também serve para redirecionar o próprio script, assunto de Descritores de Arquivo.

Não rode exec de algo que termina, direto no terminal

exec ls no terminal mostra a lista e fecha a janela: o seu shell virou o ls, e o ls terminou.

Quem sou eu? $0 e $BASH_SOURCE

Dentro de um script, $0 guarda como o script foi chamado, e ${BASH_SOURCE[0]} guarda o arquivo que está sendo lido. Quase sempre são iguais. A diferença aparece com source:

#!/usr/bin/env bash
echo "\$0          = $0"
echo "BASH_SOURCE = ${BASH_SOURCE[0]}"

O \$ com barra é só para o echo mostrar o texto $0 literalmente, antes do valor.

$ ./quem.sh
$0          = ./quem.sh
BASH_SOURCE = ./quem.sh
$ bash quem.sh
$0          = quem.sh                « exatamente o que você digitou depois do bash
BASH_SOURCE = quem.sh
$ source quem.sh
$0          = bash                   « com source, $0 é o seu shell!
BASH_SOURCE = quem.sh                « mas BASH_SOURCE continua sendo o arquivo
$ echo $0
bash

Por isso, para mensagens de uso (Uso: $0 ARQUIVO), o $0 está ótimo. Para descobrir "em que arquivo estou", use ${BASH_SOURCE[0]}. Comparando os dois, um arquivo sabe se foi rodado direto ou carregado com source:

#!/usr/bin/env bash
saudar() { echo "Olá, $1!"; }
if [[ ${BASH_SOURCE[0]} == "$0" ]]; then
  echo "Rodando direto: vou testar a função"
  saudar teste
fi

$ ./biblioteca.sh
Rodando direto: vou testar a função
Olá, teste!
$ source biblioteca.sh                « carregado: o if não rodou, só a função foi criada
$ saudar Ana
Olá, Ana!

Brinque: rode o script e veja o $0. Depois acrescente uma linha echo "Primeiro argumento: $1" e mude o argumento no campo. (O simulador roda com bash quem.sh.)

#!/usr/bin/env bash
echo "\$0          = $0"
echo "BASH_SOURCE = ${BASH_SOURCE[0]}"

Antes de rodar: bash -n e bash -x

Duas opções do bash que você vai usar muito. Elas têm uma aula própria, Depurar; aqui, só para conhecer:

  • bash -n script.sh (de noexec): só confere a sintaxe, sem executar nada. Silêncio e código 0 = nenhum erro de escrita encontrado.
  • bash -x script.sh (de xtrace): executa mostrando cada comando, já com as variáveis trocadas, numa linha que começa com +.
$ bash -n vai.sh; echo $?
0
$ bash -x vai.sh
+ cd /home/ana/Documentos
+ cor=azul
+ echo 'Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 26044'
Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 26044

Quando não funciona

"O cd do meu script não funciona" 
$ ./vai.sh
Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 25791
$ pwd
/home/ana

O que aconteceu: funcionou, mas no processo filho, que já terminou. A sua pasta é do seu shell, e um filho não muda o pai.

Como resolver: rode com source vai.sh. Ou, se for algo que você usa sempre, crie uma função ou um alias no ~/.bashrc: eles rodam no seu shell.

"Permissão negada" com ./, mas bash script.sh funciona 
$ ./vai.sh
bash: ./vai.sh: Permissão negada

O que aconteceu: falta o x. O bash vai.sh não precisa dele, porque só lê o arquivo.

Como resolver: chmod +x vai.sh. Se o arquivo está num pendrive ou disco do Windows, o chmod pode não ter efeito; use bash vai.sh.

O terminal fechou sozinho

O que aconteceu: você rodou com source (ou .) um script que tem exit, ou rodou exec de um comando que termina. O exit encerrou o seu próprio shell.

Como resolver: rode scripts "normais" com ./ ou bash; deixe o source para arquivos de configuração. Num arquivo feito para source, troque exit por return.

[[: not found ou erros estranhos que não acontecem no terminal 
$ sh teste-sh.sh
teste-sh.sh: 3: [[: not found

O que aconteceu: o script foi rodado pelo sh (que no Debian/Ubuntu é o dash), e não pelo Bash. Também acontece quando o shebang é #!/bin/sh.

Como resolver: rode com bash teste-sh.sh ou ./teste-sh.sh, e use #!/usr/bin/env bash no shebang.

A variável do script não aparece no terminal (e não deu erro) 
$ bash vai.sh
Dentro do script: estou em /home/ana/Documentos, cor=azul, PID 25789
$ echo "cor=$cor"
cor=

O que aconteceu: nada saiu errado: variáveis do filho não voltam para o pai. Nem com export: o export só passa do pai para os filhos, nunca o contrário (veja Variáveis, Escopo e export).

Como resolver: source vai.sh, ou faça o script mostrar o valor e capture com cor=$(./script.sh) (Substituição de Comando).

Resumo

  • ./script.sh e o nome pelo PATH precisam de x e usam o shebang; bash script.sh não precisa de x.
  • Essas três formas rodam num processo filho: cd e variáveis do script somem quando ele termina.
  • source (ou .) executa no seu shell: o que o arquivo muda, fica. Nada de exit nesses arquivos.
  • bash -c '…' roda um código curto num Bash novo; exec troca o shell atual pelo comando.
  • $0 é como o script foi chamado; ${BASH_SOURCE[0]} é o arquivo sendo lido.
