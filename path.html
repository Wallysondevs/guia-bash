Bash PATH e Onde os Comandos Moram

Quando você digita ls, o Bash precisa descobrir o que é ls e onde ele está. A resposta passa por uma lista de pastas guardada na variável PATH (em inglês, "caminho"). Entender essa busca explica o "comando não encontrado", permite rodar seus próprios scripts pelo nome, de qualquer pasta, e resolve o mistério do comando que "sumiu" depois de mudar de lugar.

Você vai aprender
  • A ordem em que o Bash procura um nome: alias, palavra-chave, função, comando interno e, por fim, o PATH.
  • Ler o PATH pasta por pasta, e descobrir onde um comando está (type, which, command -v).
  • O que é a tabela hash e quando usar hash -r.
  • Colocar ~/bin ou ~/.local/bin no PATH, no começo ou no fim, e deixar isso permanente.
  • Os erros "comando não encontrado", "interpretador incorreto" e "Permissão negada".

A pergunta que o Bash faz a cada comando

Pegue a primeira palavra de um comando, como ls em ls -l. O Bash procura esse nome em vários lugares, sempre na mesma ordem, e usa o primeiro que encontrar:

  1. é um ALIAS?               alias ll='ls -alF'          (veja alias.html)
  2. é uma PALAVRA-CHAVE?      if, for, while, [[ …        (parte da linguagem)
  3. é uma FUNÇÃO?             saudar() { … }              (veja funcoes.html)
  4. é um COMANDO INTERNO?     cd, echo, type, read…       (builtin: vem dentro do Bash)
  5. está na tabela HASH?      lembrança de buscas anteriores
  6. está numa pasta do PATH?  /usr/local/bin, /usr/bin, …  (programas: arquivos no disco)
  ─────────────────────────────────────────────────────────────
  nada disso → "bash: nome: comando não encontrado"   (código 127)

Os quatro primeiros vivem dentro do Bash, na memória. Só o último passo vai ao disco procurar um arquivo. Por isso cd e echo respondem mesmo se o disco estiver com problemas, e por isso uma função chamada ls passaria na frente do programa ls.

Se o nome tiver uma barra (./backup.sh, /usr/bin/ls, ~/bin/oi), não há busca nenhuma: o Bash roda exatamente aquele arquivo.

Perguntando ao Bash: type

O comando interno type diz em qual dos passos um nome cai, com uma frase para cada caso:

$ type ls
ls está apelidada para `ls --color=auto'      « 1. alias
$ type if
if é uma palavra-chave do shell                « 2. palavra-chave
$ saudar() { echo "Olá, $1"; }
$ type saudar
saudar é uma função                            « 3. função (e mostra o corpo)
saudar ()
{
    echo "Olá, $1"
}
$ type cd
cd é um comando interno do shell               « 4. builtin
$ type cp
cp é /usr/bin/cp                               « 6. um arquivo numa pasta do PATH
$ type nada
bash: type: nada: não encontrado
$ echo $?
1

Com -t (de type, tipo), a resposta vem numa palavra só, em inglês, ótima para scripts:

$ type -t ls cd if saudar cp
alias
builtin
keyword
function
file

Todos os candidatos: type -a

Um mesmo nome pode existir em vários passos. O -a (all, todos) lista todos, na ordem da busca. O primeiro é o que roda:

$ type -a echo
echo é um comando interno do shell     « este é o que roda
echo é /usr/bin/echo                   « existe também como programa
echo é /bin/echo
$ type -a ls
ls está apelidada para `ls --color=auto'
ls é /usr/bin/ls
ls é /bin/ls

Por que /usr/bin/ls e /bin/ls? Nos sistemas atuais, /bin é só um atalho (link) para /usr/bin; é o mesmo arquivo, encontrado por duas pastas do PATH.

A ordem vale até para nomes "sagrados". Um alias passa na frente da palavra-chave, e uma função passa na frente do comando interno:

$ alias if='echo apelido'
$ type -a if
if está apelidada para `echo apelido'
if é uma palavra-chave do shell
$ unalias if                            « nunca faça isso de verdade :)

A variável PATH, pasta por pasta

O PATH é uma variável comum, com uma lista de pastas separadas por dois-pontos:

$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

Fica mais fácil de ler com uma pasta por linha. O tr troca cada : por uma quebra de linha:

$ echo "$PATH" | tr ':' '\n'
/usr/local/sbin
/usr/local/bin
/usr/sbin
/usr/bin
/sbin
/bin
PastaO que mora lá
/usr/local/sbin, /usr/local/binProgramas instalados à mão pelo administrador (fora do gerenciador de pacotes). Vêm primeiro para poder substituir os do sistema.
/usr/sbin, /sbinProgramas de administração (system binaries), como useradd e fdisk.
/usr/bin, /binA maioria dos programas: ls, cp, grep, python3… Hoje, /bin e /sbin são atalhos para as pastas de /usr.
~/bin, ~/.local/binSeus próprios scripts e programas instalados só para você (por exemplo, com pip install --user). Entram no PATH quando você coloca (veja abaixo).
/snap/bin, /usr/games, /opt/…/binAparecem em algumas distros, conforme o que está instalado.

A busca vai da esquerda para a direita e para no primeiro arquivo executável com aquele nome. Se dois programas têm o mesmo nome, ganha o da pasta que aparece antes. Guarde isso: é o segredo de "no começo × no fim".

Onde está o programa? which, command -v, type -P

Três comandos respondem "onde está", cada um com um jeito:

$ which ls
/usr/bin/ls                      « só olha o PATH: ignora o alias
$ command -v ls
alias ls='ls --color=auto'       « diz o que vai rodar de fato
$ command -v cp
/usr/bin/cp
$ command -v cd
cd                               « comando interno: só o nome
$ type -P ls
/usr/bin/ls                      « -P: só o PATH, como o which
$ type -P cd
$ echo $?
1                                « cd não é um arquivo do PATH

Rodar o seu script pelo nome

A Ana escreveu um script e quer chamá-lo como se fosse um comando qualquer, de qualquer pasta. Ela cria a pasta ~/bin e o arquivo:

$ mkdir -p ~/bin
$ printf '#!/usr/bin/env bash\necho "Bom dia, $USER!"\n' > ~/bin/bomdia
$ cat ~/bin/bomdia
#!/usr/bin/env bash
echo "Bom dia, $USER!"
$ bomdia
bash: bomdia: comando não encontrado
$ echo $?
127

Faltam duas coisas. Primeiro, o arquivo precisa da permissão de execução (veja formas de executar). Com o caminho completo, já dá para rodar:

$ chmod +x ~/bin/bomdia
$ ~/bin/bomdia
Bom dia, ana!

Segundo, para rodar só pelo nome, a pasta precisa estar no PATH. Acrescentamos ~/bin no começo da lista:

PATH=
Vamos dar um valor novo ao PATH…
"$HOME/bin
…que começa com a pasta nova (use $HOME; o ~ dentro de aspas não é expandido)…
:
…o separador…
$PATH"
…e depois tudo o que já estava lá. Sem isso, você apagaria a lista antiga!
$ PATH="$HOME/bin:$PATH"
$ echo $PATH
/home/ana/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
$ bomdia
Bom dia, ana!

O PATH já é uma variável exportada, então não precisa de export: os programas e scripts chamados a partir deste shell também recebem a lista nova. Mas a mudança vale só para este terminal; tornar permanente está mais abaixo.

Missão: já existe o script ~/bin/oi, mas oi dá "comando não encontrado". Dê permissão de execução a ele, coloque ~/bin no começo do PATH (sem perder o resto!) e rode digitando só oi.

No começo ou no fim?

Como a busca para no primeiro que encontra, a posição decide quem ganha quando há nomes repetidos. Para ver, a Ana cria um script com o mesmo nome de um programa do sistema, date:

$ printf '#!/usr/bin/env bash\necho "o date da Ana"\n' > ~/bin/date
$ chmod +x ~/bin/date
$ PATH="$PATH:$HOME/bin"              « ~/bin no FIM
$ date +%Y
2026                                  « ganhou o /usr/bin/date
$ type -a date
date é /usr/bin/date
date é /bin/date
date é /home/ana/bin/date

Num terminal novo, com ~/bin no começo:

$ PATH="$HOME/bin:$PATH"              « ~/bin no COMEÇO
$ date +%Y
o date da Ana                         « ganhou o script dela
$ type -a date
date é /home/ana/bin/date
date é /usr/bin/date
date é /bin/date
$ /usr/bin/date +%Y
2026                                  « o caminho completo sempre acha o original
PosiçãoVantagemRisco
No começo: PATH="$HOME/bin:$PATH"Você pode substituir um programa do sistema por uma versão sua (é o padrão do .profile do Debian/Ubuntu).Um script seu com nome repetido (test, date) "esconde" o original sem você perceber.
No fim: PATH="$PATH:$HOME/bin"Os programas do sistema sempre ganham; mais seguro.Seu script com nome repetido nunca roda pelo nome.

Nos dois casos, a regra de ouro é: dê nomes únicos aos seus scripts. Antes de batizar, pergunte type -a nome-pensado; se a resposta for "não encontrado", o nome está livre.

Por que nunca colocar . no PATH

O ponto quer dizer "a pasta atual". Com ele no PATH, você rodaria backup.sh sem o ./. Parece prático, mas imagine que você baixou uma pasta da internet que traz um arquivo chamado ls:

$ PATH=".:$PATH"
$ cd baixado
$ ls
Te peguei! (eu não sou o ls de verdade)

Você só quis listar a pasta, e rodou um programa desconhecido, com as suas permissões. Poderia ser algo que apaga arquivos ou rouba senhas. Mesmo com o ponto no fim, um erro de digitação (sl em vez de ls) pode rodar uma armadilha. Por isso nenhuma distro coloca . no PATH, e você digita ./script.sh: o ./ diz "eu sei que é este arquivo, desta pasta".

Cuidado também com o PATH vazio por engano

Uma entrada vazia no PATH (dois-pontos no começo, no fim ou dobrados, como em PATH=":/usr/bin" ou PATH="$PATH:") também quer dizer "a pasta atual". É o mesmo risco do ., escondido.

A tabela hash: o atalho da memória

Procurar um programa em várias pastas toma tempo. Por isso o Bash anota onde achou cada programa, numa tabela chamada hash (um tipo de índice), e das próximas vezes vai direto. O comando interno hash mostra essa tabela:

$ hash
hash: tabela de hash está vazia
$ bomdia
Bom dia, ana!
$ hash
número	comando
   1	/home/ana/bin/bomdia          « usado 1 vez, achado nesta pasta
$ type bomdia
bomdia está na tabela hash (/home/ana/bin/bomdia)

(Essa sessão começou num terminal novo, com ~/bin já no PATH: por isso a tabela estava vazia.) Na maior parte do tempo você nem percebe que ela existe. Ela só aparece quando um programa muda de pasta. Na sessão abaixo, o PATH da Ana tem ~/.local/bin e ~/bin. Ela usa o bomdia e depois o move para ~/.local/bin:

$ bomdia
Bom dia, ana!
$ mv ~/bin/bomdia ~/.local/bin/
$ bomdia
bash: /home/ana/bin/bomdia: Arquivo ou diretório inexistente     « procurou no lugar antigo!
$ echo $?
127
$ type -a bomdia
bomdia é /home/ana/.local/bin/bomdia                              « o arquivo está aqui

O arquivo está numa pasta do PATH, mas o Bash nem procurou: foi direto ao endereço anotado, que não existe mais. Repare que a mensagem mostra o caminho completo antigo; isso é a assinatura de um hash desatualizado. A solução é esquecer as anotações:

hash
O comando que mexe na tabela.
-r
reset: esvazia a tabela inteira. O Bash volta a procurar no PATH na próxima vez.
$ hash -r
$ bomdia
Bom dia, ana!
$ hash
número	comando
   1	/home/ana/.local/bin/bomdia     « anotado no lugar novo

Para esquecer só um nome, use hash -d bomdia (delete). E duas coisas limpam a tabela sozinhas: mudar o PATH (qualquer atribuição a ele) e abrir um terminal novo. O mesmo problema acontece quando você instala um programa novo numa pasta que vem antes no PATH (por exemplo, uma versão mais nova em /usr/local/bin): o shell aberto continua usando a antiga até um hash -r.

Missão: o script bomdia acabou de ser movido de ~/bin para ~/.local/bin, e as duas pastas estão no PATH. Digite bomdia e veja o erro. Faça o Bash esquecer o endereço antigo e rode bomdia de novo.

Tornar permanente

Como toda variável, o PATH mudado no terminal volta ao normal quando você fecha a janela. Para valer sempre, a mudança precisa estar num arquivo de inicialização (veja arquivos de inicialização).

No Debian e no Ubuntu: basta criar a pasta

O ~/.profile da Ana (e o de toda conta nova no Debian/Ubuntu) já tem este trecho:

# inclui a pasta bin pessoal no PATH, se existir
if [ -d "$HOME/bin" ] ; then
    PATH="$HOME/bin:$PATH"
fi
if [ -d "$HOME/.local/bin" ] ; then
    PATH="$HOME/.local/bin:$PATH"
fi

Ou seja: se a pasta ~/bin ou ~/.local/bin existir, ela entra no começo do PATH. Como o .profile é lido no login, a pasta nova passa a valer depois de sair da sessão e entrar de novo (ou reiniciar). Até lá, use o PATH=… no terminal.

Em qualquer sistema: no .bashrc, sem repetir

Se o seu sistema não tem esse trecho (ou você não quer esperar o próximo login), coloque no fim do ~/.bashrc uma versão que só acrescenta a pasta se ela ainda não estiver na lista:

case ":$PATH:" in
    *":$HOME/.local/bin:"*) ;;
    *) PATH="$HOME/.local/bin:$PATH" ;;
esac
":$PATH:"
O PATH com dois-pontos extras nas pontas, para que toda pasta fique "entre dois-pontos", inclusive a primeira e a última.
*":$HOME/.local/bin:"*)
Se a pasta já aparece na lista: não faz nada (;;).
*) PATH=…
Senão, acrescenta no começo.

Com o teste, ler o arquivo várias vezes não duplica a pasta (na sessão abaixo, ~/bin já estava no PATH de antes):

$ source ~/.bashrc
$ source ~/.bashrc
$ echo "$PATH" | tr ':' '\n'
/home/ana/.local/bin            « entrou uma vez só
/home/ana/bin
/usr/local/sbin
/usr/local/bin
/usr/sbin
/usr/bin
/sbin
/bin
SistemaOnde colocar o PATH pessoal
Debian, Ubuntu, MintJá vem no ~/.profile: crie ~/bin ou ~/.local/bin e entre de novo na sessão.
Fedora, RHELO ~/.bashrc padrão já coloca ~/.local/bin e ~/bin no PATH, com um teste parecido com o acima.
ArchNada vem pronto: acrescente o case acima no ~/.bashrc (ou no ~/.bash_profile).
macOS (Bash)No ~/.bash_profile, que é o arquivo lido em cada aba.

Quando não funciona

"comando não encontrado" (código 127) 
$ ls -l backup.sh
-rwxrwxr-x 1 ana ana 45 out 15 09:15 backup.sh
$ backup.sh
bash: backup.sh: comando não encontrado
$ ./backup.sh
Fazendo backup...

O que aconteceu: o nome não tem barra, então o Bash procurou nas pastas do PATH, e a pasta atual não está lá (ainda bem, veja acima). Outras causas comuns: erro de digitação; programa não instalado; script numa pasta que não está no PATH.

Como confirmar: type -a nome (o Bash conhece?), echo "$PATH" | tr ':' '\n' (a pasta está na lista?), ls -l caminho/do/arquivo (o arquivo existe?).

Como resolver: rode com o caminho (./backup.sh), mova o script para ~/bin, ou instale o programa. No Ubuntu, o terminal costuma sugerir o pacote ("O comando 'x' não foi encontrado, mas pode ser instalado com: sudo apt install …"); essa ajuda vem de um programa à parte, o command-not-found, e não existe em todas as distros.

Nenhum comando funciona mais: ls, cat… "comando não encontrado" 
$ PATH=~/scripts
$ ls
bash: ls: comando não encontrado
$ cat frutas.txt
bash: cat: comando não encontrado
$ echo $PATH
/home/ana/scripts

O que aconteceu: faltou o :$PATH no fim. O PATH virou uma pasta só, e as pastas do sistema sumiram da lista. O echo e o cd continuam funcionando porque são comandos internos.

Como resolver: no terminal, devolva uma lista básica: PATH=/usr/local/bin:/usr/bin:/bin (ou simplesmente feche e abra o terminal). Se o erro estiver no .bashrc ou no .profile, conserte a linha para PATH="$HOME/scripts:$PATH"; enquanto isso, chame o editor pelo caminho completo: /usr/bin/nano ~/.bashrc.

"Arquivo ou diretório inexistente" com o caminho completo de um programa que existe 
$ bomdia
bash: /home/ana/bin/bomdia: Arquivo ou diretório inexistente

O que aconteceu: o programa mudou de pasta, e o Bash usou o endereço antigo anotado na tabela hash.

Como resolver: hash -r.

"interpretador incorreto: Arquivo ou diretório inexistente" 
$ head -n 1 ~/.local/bin/rotina.sh
#!/bin/bassh
$ rotina.sh
bash: /home/ana/.local/bin/rotina.sh: /bin/bassh: interpretador incorreto: Arquivo ou diretório inexistente
$ echo $?
126

O que aconteceu: o script foi encontrado, mas a primeira linha (o shebang, #!) aponta para um programa que não existe: /bin/bassh, com dois "s". A mensagem confunde porque diz "inexistente", mas o que não existe é o interpretador, não o script. O código 126 quer dizer "achei, mas não consegui executar".

Como resolver: corrija a primeira linha para #!/usr/bin/env bash (ou #!/bin/bash). Confira com head -n 1 arquivo.

"env: ‘bash\r’: Arquivo ou diretório inexistente" 
$ dos.sh
env: ‘bash\r’: Arquivo ou diretório inexistente
env: usa -[v]S para passar opções em linhas shebang
$ echo $?
127

O que aconteceu: o script foi salvo no Windows (ou num editor configurado para ele), com fim de linha \r\n. O \r invisível grudou no nome do interpretador: o env procurou um programa chamado "bash\r". A segunda linha é uma dica do env que não tem a ver com o problema.

Como confirmar: file dos.sh diz "with CRLF line terminators"; head -n 1 dos.sh | od -c mostra o \r.

Como resolver: tire os \r: sed -i 's/\r$//' dos.sh (ou dos2unix dos.sh, se estiver instalado).

"Permissão negada" (código 126) 
$ semx.sh
bash: /home/ana/.local/bin/semx.sh: Permissão negada
$ echo $?
126

O que aconteceu: o arquivo está numa pasta do PATH, mas não tem permissão de execução. Quando não acha nenhum executável, o Bash ainda tenta o arquivo sem permissão que encontrou, e o sistema recusa.

Como resolver: chmod +x ~/.local/bin/semx.sh.

Meu script não faz nada: dei a ele o nome de um comando que já existe 
$ ls -l test
-rwxrwxr-x 1 ana ana 43 out 15 10:30 test
$ test
$ echo $?
1                                   « o script deveria escrever "meu teste rodou"
$ type -a test
test é um comando interno do shell
test é /usr/bin/test
test é /bin/test

O que aconteceu: a Ana chamou o script de test, mas test é um comando interno (o mesmo que [ ], veja testes). Comandos internos vêm antes do PATH na busca, então o script nunca roda pelo nome. Sem argumentos, o test interno só devolve 1, sem escrever nada. O mesmo acontece com echo, time, kill, printf…

Como resolver: renomeie o script para algo único (teste-ana, meu-teste) e confira antes com type -a. Para rodar o atual, use o caminho: ./test.

Exercícios

1. Sem perder o que já estava

Complete para colocar ~/scripts no começo do PATH:

PATH="$HOME/scripts"

2. O comando sumiu

Você moveu um programa de pasta e agora o Bash diz que ele não existe, mostrando o caminho antigo. Complete:

hash

3. Testar se um programa existe, num script

Complete o comando padrão para isso:

if git >/dev/null; then echo "tem git"; fi

4. Existe alias ls='ls --color=auto', uma função ls e o programa /usr/bin/ls. O que roda quando você digita ls?

5. Por que não se coloca . no PATH?

6. A mensagem bash: ./x.sh: /bin/bassh: interpretador incorreto: Arquivo ou diretório inexistente quer dizer:

Resumo

  • Ordem da busca: alias → palavra-chave → função → comando interno → tabela hash → pastas do PATH, da esquerda para a direita. Com uma barra no nome, não há busca.
  • type -a mostra todos os candidatos; em scripts, teste com command -v.
  • Acrescente pastas sem apagar a lista: PATH="$HOME/bin:$PATH". No começo substitui programas do sistema; no fim, não. Nunca ..
  • Programa que mudou de pasta e "sumiu": hash -r.
  • Permanente: ~/.profile (Debian/Ubuntu, basta criar a pasta) ou um case no ~/.bashrc que não repete a pasta.
  • 127 = não encontrado; 126 = encontrado, mas não executou (permissão ou shebang errado).
