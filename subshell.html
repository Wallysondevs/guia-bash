Bash Subshells e Grupos

Um subshell é uma cópia do shell que roda um pedaço do seu código e depois some, levando junto tudo o que mudou lá dentro. Entender quando o Bash cria essa cópia explica uma das dúvidas mais comuns de quem escreve scripts: "por que minha variável voltou a zero depois do while?".

Você vai aprender
  • A diferença entre agrupar com ( … ) (subshell) e com { …; } (grupo no mesmo shell).
  • Quem cria subshells sem você pedir: pipes, $( ) e &.
  • A pegadinha cmd | while read … e as três saídas: < <( ), < arquivo e shopt -s lastpipe.
  • $$ × $BASHPID, BASH_SUBSHELL e o exit dentro de ( ).
  • Subshell × export: o que um processo filho herda, e o custo de subshells dentro de laços.

A cópia que some

Imagine que você entrega a um colega uma fotocópia do seu caderno. Ele risca, anota, arranca páginas da cópia… e no fim joga a cópia fora. O seu caderno continua igual. Um subshell é isso: o Bash faz uma cópia de si mesmo, com as mesmas variáveis, funções e a mesma pasta atual. O que acontece na cópia não volta para o original.

Isso pode ser exatamente o que você quer (mexer "num rascunho" sem bagunçar o shell) ou uma armadilha (você queria guardar um resultado e ele sumiu com a cópia).

( … ) × { …; }

O Bash tem duas formas de juntar vários comandos num bloco:

( cd Documentos; nome=Bruno )
Parênteses: os comandos rodam num subshell, a cópia. As mudanças ficam lá dentro.
{ cd Documentos; nome=Bruno; }
Chaves: os comandos rodam no shell atual. É só um agrupamento; as mudanças ficam valendo.

Veja a diferença com a mesma sequência de comandos. Primeiro com parênteses:

$ nome=Ana
$ ( cd Documentos; nome=Bruno; pwd; echo "dentro: $nome" )
/home/ana/Documentos
dentro: Bruno
$ pwd; echo "fora: $nome"
/home/ana                          « o cd não voltou do subshell
fora: Ana                          « a variável também não

Agora com chaves:

$ { cd Documentos; nome=Bruno; pwd; echo "dentro: $nome"; }
/home/ana/Documentos
dentro: Bruno
$ pwd; echo "fora: $nome"
/home/ana/Documentos               « o cd valeu: o prompt mudou de pasta
fora: Bruno                        « e a variável foi trocada de verdade

Dentro do bloco, as duas formas se comportam igual. A diferença aparece depois: o ( ) joga fora o cd e a variável; o { } mantém.

A sintaxe das chaves é mais exigente

O ( e o ) são operadores do shell: podem ficar colados nos comandos. Já { e } são palavras reservadas, como if e fi. Por isso:

  • precisa de espaço depois do {;
  • o último comando precisa terminar com ; (ou quebra de linha) antes do }.
$ {echo oi; }
bash: {echo: comando não encontrado   « sem espaço, o Bash procura um comando chamado "{echo"
$ { echo oi }
>                                  « sem o ;, o } virou argumento do echo e o Bash espera o fechamento

No segundo caso, o Bash mostra o prompt de continuação > porque o grupo ainda não fechou. Aperte Ctrl+C e escreva { echo oi; }.

Quem cria subshells

Os parênteses são a forma explícita. Mas o Bash também cria subshells sozinho, em lugares que nem sempre parecem:

ConstruçãoO que roda num subshell
( comandos )Tudo o que está dentro dos parênteses
$( comandos ) e crasesO que está dentro da substituição de comando
cmd1 | cmd2 | cmd3Cada parte do pipe, inclusive a última (a não ser com lastpipe, abaixo)
comando &O comando em segundo plano (jobs)
<( comandos ) / >( comandos )O que está dentro da substituição de processo

Não criam subshell: { …; }, if, for, while, case, funções chamadas normalmente, (( )) e [[ ]].

$ x=1; echo "$(x=2; echo $x)"; echo $x
2                                  « dentro do $( ), x valia 2…
1                                  « …mas aqui fora continua 1

A pegadinha: cmd | while read

Esta é a armadilha clássica. A Ana quer somar números que vêm de um comando:

$ total=0
$ printf "%s\n" 10 20 30 | while read n; do total=$((total + n)); done
$ echo "total: $total"
total: 0                           « ué? cadê o 60?

O que aconteceu: o while está depois de um |, então rodou num subshell. Lá dentro, total chegou a 60. Quando o pipe acabou, o subshell sumiu, e com ele o 60. O echo lá fora vê o total original, que é 0. Não há mensagem de erro: o código de saída é 0 e o resultado está simplesmente errado.

  shell principal (total=0)
     │
     ├── subshell 1: printf "%s\n" 10 20 30 ──┐
     │                                        │ pipe
     └── subshell 2: while read … total=60 ◄──┘   ← some no fim do pipe
     │
  echo "total: $total"  →  0

Saída 1: done < <( comando )

Em vez de colocar o comando antes do while com um pipe, coloque-o depois do done, com uma substituição de processo. Assim o while roda no shell principal; quem vai para o subshell é o printf, que não guarda nada:

while read n; do …; done
O laço, agora no shell atual.
<
"A entrada do laço vem de…" (redirecionamento comum).
<(printf "%s\n" 10 20 30)
…a saída deste comando. É a substituição de processo. Repare no espaço entre os dois <.
$ total=0
$ while read n; do total=$((total + n)); done < <(printf "%s\n" 10 20 30)
$ echo "total: $total"
total: 60

Saída 2: done < arquivo

Se os dados estão num arquivo, nem precisa de comando: while read -r linha; do …; done < frutas.txt. Essa é a forma da aula Ler Arquivos Linha a Linha.

Saída 3: shopt -s lastpipe bash 4.2+

A opção lastpipe ("último do pipe") faz a última parte de um pipe rodar no shell atual. Ela só tem efeito quando o controle de jobs está desligado, ou seja, em scripts:

#!/usr/bin/env bash
shopt -s lastpipe
total=0
printf "%s\n" 10 20 30 | while read -r n; do
  total=$((total + n))
done
echo "total: $total"

$ bash soma.sh
total: 60

No terminal interativo, a mesma opção não faz nada, porque lá o controle de jobs está ligado (o m em $-):

$ shopt -s lastpipe
$ total=0
$ printf "%s\n" 10 20 30 | while read n; do total=$((total + n)); done
$ echo "total: $total"
total: 0                           « no terminal, o lastpipe é ignorado
$ echo $-
himBHs                             « o m = controle de jobs ligado

Em que shell eu estou? $$, $BASHPID e BASH_SUBSHELL

Duas variáveis parecem iguais, mas não são:

  • $$: o PID do shell principal. Num subshell, ela continua mostrando o PID do principal (é herdada na cópia).
  • $BASHPID: o PID do processo Bash atual, de verdade. Num subshell, muda.
$ echo "$$ $BASHPID"
48767 48767                        « no shell principal, os dois são iguais
$ ( echo "$$ $BASHPID" )
48767 48770                        « no subshell, $$ não muda; $BASHPID mostra a cópia

E BASH_SUBSHELL conta quantos níveis de subshell há entre você e o shell principal:

$ echo "$BASH_SUBSHELL"
0
$ ( echo "$BASH_SUBSHELL"; ( echo "$BASH_SUBSHELL" ) )
1
2                                  « um subshell dentro de outro
$ echo "$(echo $BASH_SUBSHELL)"
1                                  « o $( ) também é subshell
$ echo x | { read v; echo "nível $BASH_SUBSHELL, pid $BASHPID"; }
nível 1, pid 48775                 « o { } depois de um pipe também

Repare no último: as chaves sozinhas não criam subshell, mas aqui elas estão depois de um |, e é o pipe que cria.

Use $$ para nomes de arquivos temporários do script (/tmp/relatorio.$$) e $BASHPID quando precisar saber em que processo um trecho está rodando, por exemplo para depurar.

exit dentro de ( )

Um exit dentro de um subshell encerra só o subshell. O script continua, e o código do exit vira o $? do bloco. Dentro de chaves, o exit encerra o script inteiro.

#!/usr/bin/env bash
( echo "dentro do subshell"; exit 3 )
echo "o script continua; o subshell saiu com $?"
{ echo "dentro do grupo"; exit 4; }
echo "esta linha nunca aparece"

$ bash sair.sh
dentro do subshell
o script continua; o subshell saiu com 3
dentro do grupo
$ echo $?
4                                  « o exit 4 do grupo encerrou o script

Isso pega muita gente de surpresa com o set -e e com funções de erro: um morrer() { echo "$1" >&2; exit 1; } chamado dentro de $( ) ou de um pipe só encerra aquele subshell. Veja Tratar Erros.

Subshell × export: o que é herdado

Um subshell é uma cópia: ele vê todas as variáveis, inclusive as que não foram exportadas, e todas as funções. Já um programa novo (outro bash, um script rodado com ./script.sh ou bash script.sh, um python…) só recebe as variáveis exportadas (o "ambiente").

$ cor=azul
$ ( echo "subshell: $cor" )
subshell: azul                     « a cópia vê tudo
$ bash -c 'echo "outro bash: $cor"'
outro bash:                        « um programa novo não vê variáveis comuns
$ export cor
$ bash -c 'echo "outro bash: $cor"'
outro bash: azul                   « exportada, passa para os filhos
Subshell ( ), $( ), pipe, &Programa novo (bash -c, ./script.sh)
Variáveis comunsVê (cópia)Não vê
Variáveis exportadasVêVê
FunçõesVêSó com export -f
Aliases, opções (set, shopt)VêNão (começa do zero)
Mudanças voltam para quem chamou?NãoNão

A última linha é a regra de ouro: nenhum filho muda o pai. Nem o export faz uma variável "voltar"; ele só faz a variável ir para os filhos. Mais sobre isso em Variáveis, Escopo e export. É também por isso que um script com cd não muda a pasta do seu terminal (a menos que você o rode com source, veja Formas de Executar).

O custo dos subshells em laços

Criar um subshell é rápido, mas não é de graça: o sistema precisa copiar o processo. Uma vez, não se nota. Mil vezes num laço, já aparece:

#!/usr/bin/env bash
TIMEFORMAT="%R s"
echo "1000 vezes com \$( ):"
time for i in {1..1000}; do x=$(echo "$i"); done
echo "1000 vezes sem subshell:"
time for i in {1..1000}; do x=$i; done
echo "1000 vezes com printf -v:"
time for i in {1..1000}; do printf -v x "%s" "$i"; done

$ bash custo.sh
1000 vezes com $( ):
0,638 s                            « um subshell por volta
1000 vezes sem subshell:
0,002 s
1000 vezes com printf -v:
0,007 s

A mesma tarefa ficou umas 300 vezes mais lenta só por causa do $( ). Em laços grandes, prefira o que roda no próprio shell:

Em vez de (cria subshell/processo)Prefira (no próprio shell)
x=$(echo "$i")x=$i
x=$(printf '%03d' "$i")printf -v x '%03d' "$i" (veja printf)
n=$(expr $n + 1)(( n++ ))
base=$(basename "$f")base=${f##*/} (expansão de parâmetros)
cat arquivo | while read …while read …; done < arquivo

Fora de laços, não se preocupe: clareza vale mais do que milissegundos.

Quando não funciona

A variável "voltou" ao valor antigo depois do laço (não apareceu erro nenhum) 
$ printf "%s\n" 10 20 30 | while read n; do total=$((total + n)); done
$ echo "total: $total"
total: 0

O que aconteceu: o laço estava depois de um | e rodou num subshell.

Como confirmar: coloque echo "$BASH_SUBSHELL" dentro do laço: se mostrar 1 ou mais, é subshell.

Como resolver: done < <(comando), done < arquivo ou, em script, shopt -s lastpipe.

"{echo: comando não encontrado" 
$ {echo oi; }
bash: {echo: comando não encontrado

O que aconteceu: faltou o espaço depois de {. Como resolver: { echo oi; }.

O Bash mostra > e fica esperando 
$ { echo oi }
>

O que aconteceu: faltou o ; antes do }; o } virou argumento do echo e o grupo não fechou. Como resolver: Ctrl+C e { echo oi; }.

O script fez cd, mas o terminal continua na mesma pasta

O que aconteceu: o script roda num processo filho, e nenhum filho muda o pai. O mesmo vale para variáveis que o script cria.

Como resolver: se a ideia é mudar o terminal atual, rode com source script.sh (ou . script.sh), ou transforme o trecho numa função no seu ~/.bashrc.

O exit não encerrou o script

O que aconteceu: o exit estava dentro de ( ), de $( ) ou de um pipe, e encerrou só o subshell.

Como resolver: confira o código depois do bloco: ( … ) || exit 1, ou troque os parênteses por chaves quando não precisar isolar nada.

Resumo

  • ( ) roda numa cópia do shell: cd, variáveis e exit ficam lá dentro. { ; } agrupa no shell atual.
  • Pipes, $( ), & e <( ) também criam subshells.
  • cmd | while read perde as variáveis; use done < <(cmd), done < arquivo ou lastpipe em scripts.
  • $$ é o shell principal; $BASHPID é o processo atual; BASH_SUBSHELL conta os níveis.
  • Subshells veem tudo; programas novos só o que foi exportado. Nenhum filho muda o pai.
  • Em laços grandes, evite $( ): printf -v, (( )) e ${ } rodam no próprio shell.
