Bash Boas Práticas

Esta aula junta, numa lista só, os hábitos que fazem um script ser seguro, legível e fácil de manter. Cada item tem o porquê, com uma demonstração real, e um link para a aula onde o assunto é explicado a fundo. No fim, um script "do jeito que todo mundo escreve no começo" é refatorado passo a passo.

Você vai aprender
  • Um checklist de 20 hábitos, do shebang ao ShellCheck, cada um com o motivo.
  • Por que aspas, -- e printf protegem contra nomes de arquivo "estranhos".
  • Como organizar um script com constantes, funções e main "$@".
  • Quando o Bash deixa de ser a ferramenta certa.
  • A refatorar um script real, entendendo cada mudança.

Por que se preocupar?

A maioria dos scripts funciona no dia em que é escrita, com os arquivos de teste de quem escreveu. Eles quebram depois: com um nome de arquivo com espaço, uma pasta que não existe, uma variável vazia, outra pessoa rodando de outra pasta. As boas práticas são a experiência acumulada de quem já passou por isso. Veja o script da Ana com uma lista de compras chamada lista de compras.txt:

$ f="lista de compras.txt"
$ wc -l textos/$f
wc: textos/lista: Arquivo ou diretório inexistente
wc: de: Arquivo ou diretório inexistente
wc: compras.txt: Arquivo ou diretório inexistente
0 total
$ wc -l "textos/$f"
2 textos/lista de compras.txt                  « com aspas, um nome só

Duas aspas de diferença. É disso que esta aula trata.

O checklist

1. Comece com o shebang certo

#!/usr/bin/env bash

A primeira linha diz qual programa interpreta o arquivo (Seu Primeiro Script). #!/usr/bin/env bash procura o bash no PATH, o que funciona também em sistemas onde ele não está em /bin (macOS com Homebrew, BSDs, NixOS). #!/bin/bash também é aceitável no Linux. Se o script usa recursos do Bash, nunca ponha #!/bin/sh: no Debian e no Ubuntu, sh é o dash, que não entende [[ ]], arrays etc. (POSIX sh e Bashismos).

2. Ligue o modo estrito, sabendo dos limites

set -euo pipefail

Para no primeiro erro, em variáveis inexistentes e em falhas no meio de pipes. É uma rede de segurança, não uma garantia: há casos em que o -e não age e casos em que ele para o script sem aviso (grep sem resultado, ((n++))). Leia as ressalvas em Modo Estrito e continue tratando os erros importantes.

3. Aspas duplas em toda expansão: "$var", "$(cmd)", "$@"

Sem aspas, o Bash parte o valor nos espaços e expande curingas (*, ?) que estiverem nele. Com aspas, o valor fica inteiro. A regra é simples: sempre aspas, a não ser que você saiba explicar por que não. Para repassar argumentos, "$@" é a única forma que preserva cada um:

#!/usr/bin/env bash
echo 'Com "$@":'
for a in "$@"; do echo "  [$a]"; done
echo 'Com $*:'
for a in $*; do echo "  [$a]"; done

$ bash args.sh "foto de férias.jpg" notas.txt
Com "$@":
  [foto de férias.jpg]                         « dois argumentos, como foram passados
  [notas.txt]
Com $*:
  [foto]                                       « o nome da foto virou três pedaços
  [de]
  [férias.jpg]
  [notas.txt]

As exceções seguras: dentro de [[ ]] e numa atribuição simples (a=$b), o Bash não parte nada. Ainda assim, aspas nunca atrapalham. Veja Aspas e Escapes.

4. Use [[ ]] para testes

No Bash, [[ ]] é mais seguro que [ ]: não parte variáveis, aceita &&, ||, padrões (== *.txt) e regex (=~). [ ] só é necessário em scripts sh. Detalhes em Testes.

5. $( ) em vez de crases

$(cmd) se aninha sem confusão ($(dirname "$(pwd)")) e não se mistura com aspas. As crases são da época do Bourne shell. O ShellCheck avisa (SC2006). Veja Substituição de Comando.

6. Variáveis de função são local

Sem local, toda variável criada numa função é global e pode sobrescrever outra com o mesmo nome no resto do script. Declare local no começo da função. E lembre: local x=$(cmd) esconde a falha de cmd; separe em duas linhas (local, return e Saída).

7. Nomes: minúsculas para as suas, MAIÚSCULAS para o ambiente

Variáveis do sistema e de ambiente são em maiúsculas: PATH, HOME, USER, LANG, IFS. Se você usa maiúsculas nas suas, um dia vai sobrescrever uma delas sem querer:

#!/usr/bin/env bash
PATH=~/projeto
echo "Procurando arquivos em $PATH"
ls "$PATH"

$ bash path.sh
Procurando arquivos em /home/ana/projeto
path.sh: linha 4: ls: comando não encontrado   « PATH era a lista de pastas onde os comandos moram

A Ana só queria uma variável com o caminho do projeto. Use minúsculas (pasta, arquivo, total), com _ para separar palavras (pasta_destino). Maiúsculas só para variáveis que você exporta de propósito e, se quiser, para constantes do script (readonly MAX=3). Veja PATH.

8. Não parseie a saída do ls

A saída do ls é feita para pessoas lerem. for f in $(ls) quebra em espaços e o ls pode trocar caracteres estranhos por ?. Para percorrer arquivos, use o curinga direto:

for f in ~/Imagens/*.jpg; do
  [[ -e $f ]] || continue      # se nenhum arquivo casar, o padrão fica literal
  echo "foto: $f"
done

Com shopt -s nullglob, um padrão sem resultado vira "nada" e o [[ -e ]] é dispensável. Para buscar em subpastas, use shopt -s globstar e **/*.jpg, ou o find do próximo item.

9. find -print0 | xargs -0 e while read -d ''

Nomes de arquivo podem conter espaços e até quebras de linha. O único caractere que não pode aparecer num caminho de arquivo é o byte nulo (\0). Por isso, a forma segura de passar listas de arquivos é separá-los com \0:

$ find textos -name '*.txt' | xargs wc -l
  7 textos/frutas.txt
  4 textos/notas.txt
wc: textos/lista: Arquivo ou diretório inexistente   « o xargs separou nos espaços
wc: de: Arquivo ou diretório inexistente
wc: compras.txt: Arquivo ou diretório inexistente
 11 total
$ find textos -name '*.txt' -print0 | xargs -0 wc -l
  7 textos/frutas.txt
  4 textos/notas.txt
  2 textos/lista de compras.txt
 13 total
-print0
O find termina cada nome com \0, em vez de quebra de linha.
xargs -0
O xargs separa a entrada por \0.

Para processar cada arquivo num laço do próprio Bash, leia com read -d '' (o delimitador vazio é o \0):

$ while IFS= read -r -d '' arq; do echo "achei: [$arq]"; done < <(find textos -name '*.txt' -print0)
achei: [textos/frutas.txt]
achei: [textos/notas.txt]
achei: [textos/lista de compras.txt]

IFS= preserva espaços no começo e no fim, -r preserva barras invertidas. O <(…) é uma substituição de processo. Mais em Ler Arquivos Linha a Linha.

10. Temporários com mktemp e limpeza com trap

tmp=$(mktemp)
trap 'rm -f -- "$tmp"' EXIT

Nunca use nomes fixos como /tmp/relatorio.txt: dois scripts (ou duas cópias do mesmo) usariam o mesmo arquivo, e outro usuário poderia criá-lo antes de você. mktemp cria um nome único e o trap … EXIT apaga mesmo se o script falhar (trap e Sinais). E, sempre que der, dispense o temporário: uma variável ou um pipe resolvem muitos casos.

11. printf para dados, echo só para texto fixo

O echo trata alguns valores como opções e, com -e, interpreta barras invertidas. Com dados que vêm de fora (nomes de arquivo, entradas do usuário), o resultado é imprevisível:

$ x="-n"
$ echo "$x"                                     « nada aparece: o echo achou que -n era uma opção
$ printf '%s\n' "$x"
-n
$ x='C:\novo\teste'
$ echo -e "$x"
C:
ovo	este                                      « \n virou quebra de linha e \t virou tab
$ printf '%s\n' "$x"
C:\novo\teste

printf '%s\n' "$valor" mostra o valor exatamente como é. O formato vai no primeiro argumento, e os dados nunca são interpretados. Veja printf e echo.

12. -- antes de nomes de arquivo

Se um arquivo se chama -l, um curinga o entrega ao comando, que o lê como opção:

$ mkdir truque && cd truque
$ touch -- -l a.txt b.txt
$ ls *
-rw-rw-r-- 1 ana ana 0 out 15 10:30 a.txt     « o arquivo "-l" virou a opção -l do ls!
-rw-rw-r-- 1 ana ana 0 out 15 10:30 b.txt
$ ls -- *
a.txt
b.txt
-l
$ ls ./*
./a.txt
./b.txt
./-l

O -- diz "acabaram as opções; o resto são nomes". Com rm * e um arquivo chamado -rf, isso deixa de ser curiosidade. Use cp -- "$a" "$b", rm -- "$f", ou prefixe os curingas com ./.

13. readonly para constantes

$ readonly MAX_TENTATIVAS=3
$ MAX_TENTATIVAS=5
bash: MAX_TENTATIVAS: a variável permite somente leitura
$ echo $?
1

Valores que não devem mudar (caminhos, limites, o nome do script) ficam no topo, como readonly. Quem lê o script acha as configurações num lugar só, e um erro de digitação que tentasse mudá-las vira erro na hora.

14. Organize em funções e termine com main "$@"

#!/usr/bin/env bash
set -euo pipefail

readonly PROG=${0##*/}

uso()  { printf 'Uso: %s ARQUIVO\n' "$PROG"; }
erro() { printf '%s: erro: %s\n' "$PROG" "$1" >&2; exit "${2:-1}"; }

main() {
  [[ $# -eq 1 ]] || { uso >&2; exit 2; }
  # … o trabalho …
}

main "$@"

Com tudo dentro de funções, o script lê de cima para baixo como um índice: constantes, ajudantes, main. A última linha chama main com todos os argumentos. Uma vantagem extra: o Bash só começa a executar depois de ler o arquivo inteiro até essa linha, então editar o script enquanto ele roda não causa comportamento estranho.

15. Mensagem de uso e -h

Todo script que recebe argumentos deve dizer como usá-lo: quando chamado errado (no canal de erro, código 2) e quando pedido com -h/--help (no canal normal, código 0). Veja getopts.

16. Erros no canal 2, com o nome do script

echo "$PROG: erro: …" >&2. Assim, quem redireciona a saída recebe só dados, e o erro diz quem reclamou (Tratar Erros).

17. Códigos de saída que significam algo

0 sucesso, 1 erro, 2 uso errado; 64–78 se quiser detalhar. Nunca termine um script que falhou com 0, e nunca use números acima de 125 (Tratar Erros).

18. Valide antes de agir

Confira argumentos, arquivos ([[ -f ]], [[ -r ]]) e programas (command -v) no início, antes de criar ou apagar qualquer coisa. E sempre cd … || exit.

19. Passe no ShellCheck

Ele pega quase tudo desta lista automaticamente. Ligue no editor e rode antes de cada commit (ShellCheck).

20. Comente o porquê, não o quê

# soma 1 em n não ajuda ninguém. # o servidor conta a partir de 1 ajuda. Ponha no topo um comentário dizendo o que o script faz e como usar.

Antes × depois: refatorando um script

A Ana escreveu este script para contar as linhas dos arquivos .txt de uma pasta. A pasta textos tem frutas.txt, notas.txt e lista de compras.txt.

Depois

#!/usr/bin/env bash
# relatorio.sh — conta as linhas dos arquivos .txt de uma pasta
set -euo pipefail

readonly PROG=${0##*/}

uso() {
  printf 'Uso: %s PASTA\n' "$PROG"
  printf 'Mostra quantas linhas tem cada arquivo .txt de PASTA.\n'
}

erro() {
  printf '%s: erro: %s\n' "$PROG" "$1" >&2
  exit "${2:-1}"
}

main() {
  if [[ $# -ne 1 ]]; then
    uso >&2
    exit 2
  fi
  local pasta=$1
  [[ -d $pasta ]] || erro "'$pasta' não é uma pasta" 66

  local arquivos=("$pasta"/*.txt)
  [[ -e ${arquivos[0]} ]] || erro "nenhum .txt em '$pasta'" 66

  printf 'Relatório de %s:\n' "$pasta"
  local arq linhas
  for arq in "${arquivos[@]}"; do
    linhas=$(wc -l < "$arq")
    printf '%s: %s linhas\n' "${arq##*/}" "$linhas"
  done
}

main "$@"

Quando não usar Bash

O Bash é ótimo para colar programas: rodar comandos, mexer em arquivos, automatizar o que você faria no terminal. Ele fica ruim quando o problema é processar dados. Sinais de que é hora de trocar por Python (ou outra linguagem de uso geral):

SinalPor que o Bash sofre
O script passou de 200–300 linhasSem módulos, tipos ou testes fáceis, fica difícil de manter.
Contas com números decimaisO Bash só faz contas com inteiros; você vai depender de bc e awk (Contas).
Estruturas aninhadas (listas de listas, JSON, objetos)Os arrays do Bash são de um nível só. JSON exige o jq.
Ler formatos de verdade (CSV com aspas, XML, HTML)cut -d, quebra com "Silva, Ana". Use uma biblioteca.
Rede, APIs, banco de dadosDá para usar curl, mas tratar respostas e erros vira um quebra-cabeça.
Desempenho com muitos dadosCada comando externo num laço cria um processo novo; milhares de voltas ficam lentas.
Precisa rodar no Windows sem WSLPython roda nativamente.

Não é tudo ou nada: muitos projetos usam um script Bash pequeno que prepara o ambiente e chama um programa em Python que faz o trabalho pesado.

Quando não funciona

Funciona no meu teste, quebra com o arquivo do colega

O que aconteceu: quase sempre é falta de aspas ou parsing do ls: o nome do colega tem espaço, acento, * ou começa com -.

Como confirmar: crie arquivos de teste "maldosos": touch 'com espaço.txt' -- '-começa-com-traço.txt' e rode o script com bash -x.

Como resolver: itens 3, 8, 9 e 12 do checklist; passe no ShellCheck.

"comando não encontrado" para comandos básicos (ls, cp)

O que aconteceu: o script atribuiu um valor à variável PATH (às vezes num laço como for PATH in …).

Como resolver: renomeie a variável para minúsculas (item 7).

Depois do set -euo pipefail, o script parou de funcionar

O que aconteceu: o modo estrito revelou erros que já existiam (variável vazia) ou parou num comando que devolve 1 normalmente (grep, diff).

Como resolver: rode com bash -x, ache a última linha e trate o caso: ${var:-}, || true ou um if. Veja Modo Estrito.

Resumo

  • Shebang #!/usr/bin/env bash, set -euo pipefail com ressalvas, e ShellCheck sempre.
  • Aspas em toda expansão ("$var", "$@"), [[ ]], $( ), local e nomes em minúsculas.
  • Arquivos: curingas em vez de ls, -print0/-0/read -d '', -- antes dos nomes, mktemp + trap.
  • printf para dados; readonly para constantes; funções e main "$@"; uso, erros no canal 2 e códigos de saída com significado.
  • Quando o problema é processar dados complexos, troque o Bash por Python.
