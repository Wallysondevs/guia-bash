Bash: Ler Arquivos Linha a Linha

Ler um arquivo linha por linha é uma das tarefas mais comuns em scripts: processar uma lista de tarefas, um log, uma planilha CSV. O jeito certo no Bash é uma linha que parece mágica, while IFS= read -r linha; do … done < arquivo. Nesta aula você vai entender cada pedaço dela, e por que tirar qualquer um deles causa defeitos.

Você vai aprender
  • A receita while IFS= read -r linha, parte por parte, e o papel do < depois do done.
  • Como não perder a última linha quando o arquivo não termina com quebra de linha.
  • Como separar campos de um CSV (IFS=,) e pular o cabeçalho.
  • Como ler a saída de um comando sem perder variáveis (< <(cmd) × cmd | while).
  • Como ler dois arquivos ao mesmo tempo (read -u 3) e quando usar mapfile.

Por que não usar for?

Na aula do for você viu que for linha in $(cat alunos.csv) partiu "Porto Alegre" em dois. O for percorre palavras. Para percorrer linhas, o Bash tem o comando read (veja Ler do Teclado), que lê exatamente uma linha a cada chamada. Coloque o read como condição de um while e você tem um laço que dá uma volta por linha e para quando o arquivo acaba.

A receita

$ cd Documentos
$ while IFS= read -r linha; do
>   echo "Tarefa: $linha"
> done < notas.txt
Tarefa: Comprar café
Tarefa: Ligar para o João             « a linha inteira, com os espaços
Tarefa: Estudar Bash
Tarefa: Fazer backup das fotos
while
Repete enquanto a condição der certo (código 0).
IFS=
Esvazia a variável IFS só para este read. Assim ele não apaga espaços do começo e do fim da linha. Explicado logo abaixo.
read
Lê uma linha da entrada e guarda na variável. Devolve 0 se leu uma linha, e 1 quando o arquivo acaba. É isso que encerra o laço.
-r
De raw ("cru"): não trata a barra invertida \ como especial. Explicado abaixo.
linha
O nome da variável que recebe a linha (sem a quebra de linha do final). Pode ser qualquer nome.
; do … done
O corpo, que roda uma vez para cada linha.
< notas.txt
Redireciona o arquivo para a entrada do laço inteiro. Explicado abaixo.

Contando as linhas enquanto lê:

$ n=0
$ while IFS= read -r linha; do
>   ((n++))
>   echo "$n. $linha"
> done < notas.txt
1. Comprar café
2. Ligar para o João
3. Estudar Bash
4. Fazer backup das fotos
$ echo "Total: $n tarefas"
Total: 4 tarefas                      « a variável sobreviveu ao laço (guarde isso)

Por que o < fica depois do done?

O redirecionamento vale para o comando while … done todo. O arquivo é aberto uma vez, antes da primeira volta, e cada read continua de onde o anterior parou: o primeiro lê a linha 1, o segundo a linha 2, e assim por diante.

Se você colocasse o arquivo no próprio read (while read -r linha < notas.txt), o arquivo seria reaberto a cada volta, e o read leria sempre a primeira linha: um laço infinito mostrando "Comprar café".

Por que IFS=?

A variável IFS (Internal Field Separator, "separador interno de campos") diz quais caracteres separam palavras. O padrão é espaço, tab e quebra de linha. O read usa o IFS para cortar os espaços das pontas da linha. Veja a diferença num arquivo com recuo:

$ printf '%s\n' 'sem recuo' '    quatro espaços antes' '  dois antes e dois depois  ' > recuo.txt
$ while read linha; do echo "[$linha]"; done < recuo.txt
[sem recuo]
[quatro espaços antes]                « os espaços do começo sumiram
[dois antes e dois depois]            « os das duas pontas sumiram
$ while IFS= read -r linha; do echo "[$linha]"; done < recuo.txt
[sem recuo]
[    quatro espaços antes]            « linha intacta
[  dois antes e dois depois  ]

Os colchetes no echo estão ali só para você ver onde a linha começa e termina. Em arquivos de configuração, código ou poesia, o recuo importa; por isso a receita sempre leva IFS=.

IFS= colado no read não muda o IFS do script

Uma atribuição escrita logo antes de um comando (VAR=valor comando) vale só durante aquele comando. Depois do read, o IFS volta ao normal sozinho.

Por que -r?

Sem -r, o read trata \ como "escape": a barra some, e uma barra no fim da linha junta a linha seguinte. Com caminhos do Windows, expressões regulares ou qualquer texto com barras, isso estraga os dados:

$ printf '%s\n' 'C:\novo\temp' 'linha que continua \' 'aqui' > barras.txt
$ cat barras.txt
C:\novo\temp
linha que continua \
aqui
$ while IFS= read linha; do echo "[$linha]"; done < barras.txt
[C:novotemp]                          « as barras sumiram
[linha que continua aqui]             « duas linhas viraram uma
$ while IFS= read -r linha; do echo "[$linha]"; done < barras.txt
[C:\novo\temp]                        « com -r, tudo chega como está
[linha que continua \]
[aqui]

Não há motivo para ler um arquivo sem -r. O ShellCheck avisa quando você esquece (aviso SC2162).

A última linha sem quebra de linha

Todo arquivo de texto "bem formado" termina com uma quebra de linha (\n). Mas arquivos criados em alguns editores, no Windows ou por programas descuidados às vezes não têm essa última quebra. Veja o arquivo sem-fim.txt, com cat -A, que mostra um $ onde cada linha termina:

$ printf 'banana\nuva\nkiwi' > sem-fim.txt
$ cat -A sem-fim.txt
banana$
uva$
kiwi                                  « sem $: falta a quebra (e o próximo prompt aparece colado aqui)
$ wc -l sem-fim.txt
2 sem-fim.txt                         « o wc conta quebras de linha: só 2!
$ while IFS= read -r linha; do echo "[$linha]"; done < sem-fim.txt
[banana]
[uva]                                 « cadê o kiwi?

O que aconteceu: ao ler kiwi, o read chegou ao fim do arquivo antes de achar a quebra. Ele guarda kiwi na variável, mas devolve 1 ("o arquivo acabou"). O while vê o 1 e termina sem rodar o corpo.

A correção é dizer: "continue se o read deu certo ou se ele trouxe algum texto":

$ while IFS= read -r linha || [[ -n $linha ]]; do echo "[$linha]"; done < sem-fim.txt
[banana]
[uva]
[kiwi]                                « agora sim
IFS= read -r linha
Tenta ler uma linha. Na última, sem quebra, devolve 1, mas linha vale kiwi.
||
"Ou": se o da esquerda falhar, tenta o da direita (veja ; && ||).
[[ -n $linha ]]
"A variável não está vazia?" (non-zero length). Verdadeiro para kiwi; falso quando o arquivo realmente acabou e o read não trouxe nada.

Quando o arquivo vem de fora (do usuário, de outro sistema), use esta versão completa. É ela que a missão abaixo e os projetos do guia usam.

Separar campos: IFS=, read -r nome idade cidade nota

O read pode guardar cada pedaço da linha numa variável diferente. Ele corta a linha usando os caracteres do IFS. Num CSV, o separador é a vírgula, então você passa IFS=,:

$ while IFS=, read -r nome idade cidade nota; do
>   echo "$nome tem $idade anos, mora em $cidade e tirou $nota"
> done < alunos.csv
nome tem idade anos, mora em cidade e tirou nota      « o cabeçalho também foi lido!
Ana tem 29 anos, mora em Recife e tirou 9.5
Bruno tem 34 anos, mora em Curitiba e tirou 7.0
Carla tem 22 anos, mora em Salvador e tirou 8.5
Diego tem 41 anos, mora em Manaus e tirou 6.0
Elisa tem 27 anos, mora em Porto Alegre e tirou 10.0  « o espaço não atrapalha: só a vírgula separa
IFS=,
Só a vírgula separa campos (só durante este read).
nome idade cidade nota
Quatro variáveis: o 1º campo vai para nome, o 2º para idade, e assim por diante.

E se houver mais campos que variáveis? A última variável fica com o resto da linha, vírgulas incluídas:

$ while IFS=, read -r nome resto; do echo "$nome → $resto"; done < alunos.csv
nome → idade,cidade,nota
Ana → 29,Recife,9.5
…
Elisa → 27,Porto Alegre,10.0          « (saída encurtada)

Para ignorar um campo, use _ como nome de variável "descartável". E sem IFS=, o separador é o espaço, o que serve para logs. Cada linha do acesso.log tem 8 pedaços separados por espaço:

$ while read -r ip _ _ data pedido caminho _ codigo; do
>   echo "$ip pediu $caminho → $codigo"
> done < acesso.log
192.168.0.10 pediu / → 200
192.168.0.23 pediu /contato → 200
192.168.0.10 pediu /admin → 403
192.168.0.57 pediu /fotos → 404
192.168.0.10 pediu /login → 200
192.168.0.23 pediu / → 200

Pular o cabeçalho

A primeira linha do CSV é o cabeçalho (nome,idade,cidade,nota), não um aluno. Há três jeitos de pulá-la:

1. Ler o cabeçalho antes do laço, agrupando os dois com { } para que usem o mesmo arquivo aberto:

$ {
>   read -r cabecalho
>   while IFS=, read -r nome idade cidade nota; do
>     echo "$nome ($cidade): $nota"
>   done
> } < alunos.csv
Ana (Recife): 9.5                     « o read de fora "gastou" a linha 1
Bruno (Curitiba): 7.0
Carla (Salvador): 8.5
Diego (Manaus): 6.0
Elisa (Porto Alegre): 10.0
$ echo "O cabeçalho era: $cabecalho"
O cabeçalho era: nome,idade,cidade,nota

2. Cortar com tail -n +2 ("da linha 2 em diante"):

$ tail -n +2 alunos.csv | while IFS=, read -r nome _ _ nota; do echo "$nome: $nota"; done
Ana: 9.5
Bruno: 7.0
Carla: 8.5
Diego: 6.0
Elisa: 10.0

3. Pular dentro do laço: [[ $nome == nome ]] && continue (veja break e continue).

Esquecer o cabeçalho dá erro em contas

Se você fizer (( idade > 30 )) sem pular o cabeçalho, na primeira volta idade vale o texto idade. Dentro de (( )), um texto é lido como nome de variável, que aponta para si mesma:

$ bash idade.sh
idade.sh: linha 3: ((: idade: excedido o nível de recursividade da expressão (token de erro é "idade")
Bruno (Curitiba)
Diego (Manaus)

Missão: o script lista todos os alunos. Mude-o para mostrar só quem tem mais de 30 anos, no formato Bruno (Curitiba), e pule o cabeçalho para não dar erro.

#!/usr/bin/env bash
while IFS=, read -r nome idade cidade nota; do
  echo "$nome ($cidade)"
done < Documentos/alunos.csv

#!/usr/bin/env bash
{
  read -r
  while IFS=, read -r nome idade cidade nota; do
    if (( idade > 30 )); then
      echo "$nome ($cidade)"
    fi
  done
} < Documentos/alunos.csv

Ler a saída de um comando: < <(cmd) × cmd | while

Muitas vezes as linhas não vêm de um arquivo, mas de um comando: só as linhas do log com código 200, por exemplo. O jeito que parece óbvio é o pipe. Ele funciona para mostrar coisas, mas veja o que acontece com uma variável:

$ total=0
$ grep ' 200$' acesso.log | while IFS= read -r linha; do
>   ((total++))
> done
$ echo "Acessos com sucesso: $total"
Acessos com sucesso: 0                « deveria ser 4!

O que aconteceu: num pipe, cada parte roda num processo separado. O while do lado direito do | roda numa subshell, uma cópia do shell (veja Subshells). Ele contou até 4, mas na cópia. Quando o pipe terminou, a cópia foi descartada, e o total do seu shell continuou 0.

A solução é inverter: deixar o while no shell atual e trazer o comando para a entrada dele com substituição de processo:

$ total=0
$ while IFS= read -r linha; do
>   ((total++))
> done < <(grep ' 200$' acesso.log)
$ echo "Acessos com sucesso: $total"
Acessos com sucesso: 4                « agora sim
<(grep ' 200$' acesso.log)
Roda o grep e entrega a saída dele como se fosse um arquivo. Veja Substituição de Processo.
< <( … )
O primeiro < é o redirecionamento de sempre ("a entrada vem deste arquivo"); o segundo faz parte do <( ). O espaço entre eles é obrigatório: <<( colado é outra coisa e dá erro de sintaxe.
FormaVariáveis mudadas no laço continuam depois?Use quando
while … done < arquivoSimAs linhas estão num arquivo.
while … done < <(cmd)SimAs linhas vêm de um comando e você precisa de contadores/variáveis depois.
cmd | while … doneNão (subshell)Você só mostra ou grava coisas dentro do laço.
shopt -s lastpipe + cmd | whileSim, mas só em scriptsScripts que preferem a leitura do pipe. No terminal interativo, não tem efeito.

Ler dois arquivos ao mesmo tempo: read -u 3

Até aqui o read sempre leu da entrada padrão (o descritor 0). Você pode abrir outro arquivo num descritor diferente, como o 3, e mandar o read ler dali com -u 3. Assim, dá para andar em dois arquivos ao mesmo tempo, linha a linha:

$ printf '%s\n' Ana Bruno Carla > nomes.txt
$ printf '%s\n' Recife Curitiba Salvador > cidades.txt
$ while IFS= read -r nome && IFS= read -r -u 3 cidade; do
>   echo "$nome mora em $cidade"
> done < nomes.txt 3< cidades.txt
Ana mora em Recife
Bruno mora em Curitiba
Carla mora em Salvador
read -r nome
Lê uma linha da entrada padrão, que é nomes.txt.
&&
Só lê a cidade se conseguiu ler o nome. O laço para quando qualquer um dos arquivos acabar.
read -r -u 3 cidade
Lê uma linha do descritor 3 (unit 3).
3< cidades.txt
Abre cidades.txt no descritor 3, para o laço inteiro.

Descritores são explicados a fundo em Descritores de Arquivo. Aqui basta saber que o 3 é um "cano" extra, que não se mistura com a entrada padrão. E isso resolve um problema bem comum, que está na seção Quando não funciona: perguntar algo ao usuário dentro de um laço que lê arquivo.

A alternativa: mapfile

Se você precisa de todas as linhas de uma vez (para saber quantas são, acessar a terceira, percorrer de trás para frente), o mapfile carrega o arquivo inteiro num array, um item por linha:

$ mapfile -t tarefas < notas.txt
$ echo "São ${#tarefas[@]} tarefas; a terceira é: ${tarefas[2]}"
São 4 tarefas; a terceira é: Estudar Bash             « os índices começam em 0
while IFS= read -rmapfile -t
MemóriaUma linha por vez: serve para arquivos enormes.O arquivo todo na memória.
Separar camposSim, direto no read (IFS=, read -r a b c).Não; cada item é a linha inteira.
AcessoEm ordem, uma vez.Qualquer linha, quantas vezes quiser.
VersãoQualquer shell.bash 4.0+ (não existe no Bash 3.2 do macOS).

Os detalhes estão em mapfile e readarray.

Quando não funciona

A última linha não foi processada

O que aconteceu: o arquivo não termina com quebra de linha (veja a seção acima). wc -l mostra uma linha a menos do que o cat.

Como confirmar: tail -c 1 arquivo | od -c; se não aparecer \n, falta a quebra.

Como resolver: while IFS= read -r linha || [[ -n $linha ]]; do.

O contador volta a 0 depois do laço

O que aconteceu: o laço está do lado direito de um pipe (cmd | while …) e rodou numa subshell.

Como resolver: while … done < <(cmd), ou done < arquivo se os dados já estão num arquivo.

O laço "pula" linhas quando faço uma pergunta dentro dele 
$ while IFS= read -r tarefa; do
>   read -rp "Concluiu '$tarefa'? " resp
>   echo "→ $tarefa: $resp"
> done < notas.txt
→ Comprar café: Ligar para o João             « a "resposta" foi a linha seguinte do arquivo!
→ Estudar Bash: Fazer backup das fotos

O que aconteceu: os dois read leem da mesma entrada, o arquivo. O segundo, que devia esperar o teclado, "comeu" a linha 2. A pergunta nem apareceu: o -p só mostra o texto quando a entrada é o teclado. O mesmo acontece com qualquer comando dentro do laço que leia a entrada padrão (como ssh ou ffmpeg).

Como resolver: leia o arquivo pelo descritor 3, deixando a entrada padrão livre para o teclado:

#!/usr/bin/env bash
while IFS= read -r -u 3 tarefa; do
  read -rp "Concluiu \"$tarefa\"? " resp
  echo "→ $tarefa: $resp"
done 3< Documentos/notas.txt
$ bash tarefas.sh
Concluiu "Comprar café"? sim
→ Comprar café: sim
Concluiu "Ligar para o João"? não
→ Ligar para o João: não
Concluiu "Estudar Bash"? sim
→ Estudar Bash: sim
Concluiu "Fazer backup das fotos"? não
→ Fazer backup das fotos: não

Outra saída é ler a resposta direto do terminal: read -rp "…" resp < /dev/tty.

Missão: este script tem o defeito acima: as respostas viram linhas do arquivo. Corrija-o lendo o arquivo pelo descritor 3. As respostas digitadas já vêm preparadas (sim, não, sim, não).

#!/usr/bin/env bash
while IFS= read -r tarefa; do
  read -rp "Concluiu \"$tarefa\"? " resp
  echo "→ $tarefa: $resp"
done < Documentos/notas.txt

#!/usr/bin/env bash
while IFS= read -r -u 3 tarefa; do
  read -rp "Concluiu \"$tarefa\"? " resp
  echo "→ $tarefa: $resp"
done 3< Documentos/notas.txt
O laço mostra a primeira linha para sempre

O que aconteceu: o arquivo está no read (while read -r linha < arquivo), e não no done. Ele é reaberto a cada volta.

Como resolver: Ctrl+C e mova o redirecionamento: while IFS= read -r linha; do …; done < arquivo.

Linhas com \r no fim (arquivo do Windows)

O que aconteceu: arquivos criados no Windows terminam cada linha com \r\n. O read tira o \n, mas o \r fica na variável. Os sintomas são estranhos: comparações que deveriam dar certo falham, e textos colados depois da variável aparecem "por cima" do começo da linha.

Como confirmar: cat -A arquivo mostra ^M$ no fim das linhas.

Como resolver: limpe dentro do laço com linha=${linha%$'\r'}, ou converta o arquivo antes com tr -d '\r' < win.txt > unix.txt.

Exercícios

1. Complete a receita

Complete para ler lista.txt linha por linha, sem perder espaços nem barras:

while read linha; do echo "$linha"; done lista.txt

2. Campos separados por dois-pontos

O arquivo /etc/passwd separa os campos com :. Complete para guardar o 1º campo em usuario e o resto em resto:

while read -r usuario resto; do echo "$usuario"; done < /etc/passwd

3. Sem subshell

Complete para contar as linhas de ls sem perder o contador:

n=0; while IFS= read -r l; do ((n++)); done

4. O arquivo frutas.txt foi criado com printf 'pera\nfigo'. Quantas linhas while IFS= read -r l; do echo "$l"; done < frutas.txt mostra?

5. Em IFS=, read -r nome idade lendo a linha Elisa,27,Porto Alegre,10.0, quanto vale idade?

6. Depois de total=0; cat log | while read -r l; do ((total++)); done, digitado no terminal, quanto vale $total?

Resumo

  • Para linhas, use while IFS= read -r linha; do … done < arquivo, nunca for linha in $(cat …).
  • IFS= preserva os espaços das pontas; -r preserva as barras; o < no done abre o arquivo uma vez só.
  • || [[ -n $linha ]] salva a última linha quando falta o \n final.
  • IFS=, read -r a b c separa campos; a última variável leva o resto; pule o cabeçalho com um read antes do laço.
  • cmd | while perde as variáveis (subshell); while … done < <(cmd) não perde.
  • read -u 3 lê de outro descritor: dois arquivos juntos, ou perguntas ao usuário dentro do laço. Para tudo num array, mapfile -t.
