Bash Arquivos de Inicialização

Toda vez que um Bash começa, ele pode ler alguns arquivos de configuração antes de mostrar o prompt. É neles que moram seus aliases, o PATH com a sua pasta ~/bin, o formato do prompt e o tamanho do histórico. Saber qual arquivo é lido em qual situação resolve o mistério mais comum do terminal: "coloquei no arquivo e não funcionou".

Você vai aprender
  • O que é um shell de login e um shell interativo, e como descobrir qual é o seu.
  • Quais arquivos cada tipo de shell lê: /etc/profile, ~/.bash_profile, ~/.profile, ~/.bashrc, ~/.bash_logout e BASH_ENV.
  • O .bashrc da Ana linha por linha, incluindo o case $- do topo.
  • Como aplicar uma mudança sem fechar o terminal (source).
  • Como consertar um .bashrc quebrado com bash --norc.

O problema: onde guardar as suas preferências?

A Ana cria um atalho no terminal:

$ alias oi='echo Olá, Ana'
$ oi
Olá, Ana

Funciona. Mas ela fecha a janela, abre outra, e o atalho sumiu:

$ oi
bash: oi: comando não encontrado

Tudo o que você digita vale só para aquele shell. Quando ele termina, as variáveis, aliases e funções vão embora junto. Para que algo valha "sempre", ele precisa estar escrito num arquivo que o Bash lê sozinho quando começa. Esses são os arquivos de inicialização (em inglês, startup files; também chamados de dotfiles, porque o nome começa com ponto e por isso ficam ocultos no ls).

O detalhe é que existem vários arquivos, e o Bash escolhe quais ler conforme o tipo de shell. Então primeiro vamos entender os tipos.

Dois "sim ou não": login e interativo

Todo Bash que começa responde a duas perguntas independentes:

PerguntaSim quando…Não quando…
É interativo?
Uma pessoa está digitando nele?		Você vê um prompt e digita comandos: a janela do terminal, uma sessão ssh.Ele está rodando um script ou um comando passado com bash -c. Ninguém digita nada.
É de login?
É o primeiro shell da sua sessão?		Você acabou de "entrar" com usuário e senha: o terminal de texto (Ctrl+Alt+F3), ssh, su -, bash -l.Você já estava logado e só abriu mais um shell: uma janela de terminal no Linux, um bash digitado dentro de outro.

Combinando as duas respostas, há quatro tipos:

No dia a dia de quem usa Linux com interface gráfica, os dois tipos que importam são os destacados: a janela de terminal (interativo, não-login) e os scripts (não interativo, não-login).

Como saber se o shell é interativo: $-

A variável especial $- guarda as opções ligadas no shell atual, cada uma como uma letra. Se a letra i (de interactive) estiver lá, o shell é interativo.

$ echo $-
himBHs                  « tem um "i": interativo
$ bash -c 'echo $-'
hBc                     « um bash rodando um comando: sem "i"

Cada letra é uma opção: h lembra onde os comandos estão (hash), m é o controle de jobs (monitor), B liga a expansão de chaves, H liga o ! do histórico, s diz que os comandos vêm da entrada padrão e c que vieram de -c. Para a nossa pergunta, só o i interessa. O teste fica assim:

[[ $- == *i* ]]
"O texto de $- tem um i em qualquer posição?" O *i* é um curinga: qualquer coisa, um i, qualquer coisa.
&& echo interativo
Só roda se o teste deu certo (código 0). Veja ; && ||.
$ [[ $- == *i* ]] && echo interativo
interativo

Como saber se o shell é de login: shopt login_shell

O Bash guarda essa resposta numa opção somente leitura chamada login_shell. O comando shopt (shell options) mostra o valor:

$ shopt login_shell
login_shell         	off     « a janela de terminal não é de login
$ bash -l               « -l = --login: abre um bash de login aqui dentro
$ shopt login_shell
login_shell         	on
$ logout                « shell de login termina com logout (ou exit)
$ logout
bash: logout: não é um shell de login: use `exit'

Repare na última linha: de volta ao shell da janela, que não é de login, o logout recusa e manda usar exit. É outra forma de descobrir o tipo. Uma terceira pista: num login de verdade (TTY, ssh), echo $0 mostra -bash, com um hífen na frente; é assim que o programa de login avisa ao Bash que ele é de login.

Os dois testes num script

O script abaixo responde às duas perguntas. Vamos rodá-lo de dois jeitos diferentes:

#!/usr/bin/env bash
if [[ $- == *i* ]]; then
    echo "interativo"
else
    echo "não interativo"
fi
if shopt -q login_shell; then
    echo "de login"
else
    echo "não é de login"
fi
shopt
Mostra ou muda opções do shell.
-q
quiet (quieto): não escreve nada, só devolve o código de saída: 0 se a opção está ligada, 1 se está desligada. Perfeito para o if.
login_shell
A opção que o Bash liga sozinho quando é de login.
$ bash tipo.sh
não interativo          « um bash novo foi criado só para rodar o script
não é de login
$ source tipo.sh
interativo              « o próprio shell da janela leu o arquivo
não é de login

Com bash tipo.sh, nasce um Bash novo para rodar o script, e esse Bash não é interativo. Com source tipo.sh, quem lê o arquivo é o shell em que você está digitando, que é interativo. Essa diferença volta daqui a pouco, quando formos aplicar mudanças no .bashrc.

Quais arquivos cada tipo de shell lê

Agora o mapa completo. Os arquivos em /etc valem para todos os usuários (são do administrador); os que começam com ~/ ficam na sua pasta pessoal e valem só para você.

SHELL DE LOGIN  (TTY, ssh, su -, bash -l, Terminal do macOS)
  1. /etc/profile                  ── que costuma ler também /etc/profile.d/*.sh
  2. o PRIMEIRO destes que existir (só um!):
       ~/.bash_profile  ──►  ~/.bash_login  ──►  ~/.profile
  ao sair:  ~/.bash_logout

SHELL INTERATIVO QUE NÃO É DE LOGIN  (janela de terminal no Linux, "bash" digitado)
  1. /etc/bash.bashrc              ── só onde existe (Debian, Ubuntu, Arch…)
  2. ~/.bashrc

SHELL NÃO INTERATIVO  (scripts, bash -c)
  nenhum arquivo, a não ser o que estiver na variável BASH_ENV

Três detalhes importantes:

  • O shell de login não lê o ~/.bashrc por conta própria. Quem faz isso é o ~/.profile (ou o ~/.bash_profile), que costuma ter um trecho mandando ler o .bashrc. Assim os aliases funcionam também no ssh e no TTY.
  • Da lista ~/.bash_profile → ~/.bash_login → ~/.profile, o Bash lê só o primeiro que existir e para. Se você criar um .bash_profile, o .profile deixa de ser lido.
  • Scripts não leem o .bashrc. Um script não vê os seus aliases nem as variáveis que você criou no .bashrc sem export. Ele herda só as variáveis exportadas do shell que o chamou.

A prova: um "dedo-duro" em cada arquivo

Para ver o mapa funcionando, colocamos um echo no começo do ~/.profile, outro no ~/.bashrc (logo depois do case, na parte que só roda em shell interativo) e criamos um ~/.bash_logout com um terceiro. Depois abrimos cada tipo de shell com as opções -l (login), -i (interativo) e -c (rodar um comando):

$ bash -c true                « não interativo, não-login
$ bash -ic true               « interativo, não-login
>> lendo ~/.bashrc (parte interativa)
$ bash -lc true               « não interativo, de login
>> lendo ~/.profile
$ bash -lic true              « interativo, de login
>> lendo ~/.profile
>> lendo ~/.bashrc (parte interativa)

Linha por linha:

  • bash -c true não leu nada. É assim que seus scripts rodam.
  • bash -ic leu só o .bashrc: é o caso da janela de terminal.
  • bash -lc leu o .profile. O .profile da Ana manda ler o .bashrc, mas como o shell não é interativo, o case do topo do .bashrc o mandou embora antes do nosso echo.
  • bash -lic leu o .profile, e o .profile leu o .bashrc inteiro. É o que acontece num ssh.

E o .bash_logout aparece quando um shell de login termina:

$ bash -lic exit
>> lendo ~/.profile
>> lendo ~/.bashrc (parte interativa)
sair                          « o Bash avisa que está saindo de um shell de login
>> lendo ~/.bash_logout

O .bash_logout serve para "arrumar a casa" ao sair: limpar a tela do TTY, apagar arquivos temporários. Muita gente nem tem esse arquivo, e tudo bem.

O .bash_profile que esconde o .profile

Agora a Ana cria um ~/.bash_profile (muitos tutoriais mandam fazer isso):

$ echo 'echo ">> lendo ~/.bash_profile"' > ~/.bash_profile
$ bash -lc true
>> lendo ~/.bash_profile      « o .profile não foi lido!
$ rm ~/.bash_profile
$ bash -lc true
>> lendo ~/.profile           « sem o .bash_profile, o .profile volta a valer

Como o Bash lê só o primeiro que existir, tudo o que estava no .profile (o ~/bin no PATH, a leitura do .bashrc) parou de valer nos logins. Se você precisa de um .bash_profile, faça-o carregar o .profile:

# carrega o .profile (que por sua vez carrega o .bashrc)
if [ -f ~/.profile ]; then
    . ~/.profile
fi

E o BASH_ENV?

Um shell não interativo não lê arquivo nenhum, exceto um: se a variável BASH_ENV tiver o caminho de um arquivo, o Bash lê esse arquivo antes de rodar o script.

$ echo 'echo ">> lendo env.sh"' > ~/env.sh
$ BASH_ENV=~/env.sh bash -c "echo oi"
>> lendo env.sh
oi
$ bash -c "echo oi"
oi                            « sem BASH_ENV, nada é lido

É um recurso para casos especiais (preparar o ambiente de scripts num servidor de testes, por exemplo). No uso normal você não precisa dele. Se um script se comporta de um jeito estranho só na sua máquina, vale conferir se echo $BASH_ENV está vazio.

Opções que mudam a leitura

bash --norc não lê o ~/.bashrc; bash --noprofile não lê os arquivos de login; bash --rcfile arquivo lê arquivo no lugar do ~/.bashrc. A primeira vai salvar você quando o .bashrc quebrar (veja "Quando não funciona").

O .bashrc da Ana, linha por linha

O rc do nome vem de run commands ("comandos para rodar"), uma tradição dos anos 1960. É o arquivo que você mais vai editar. O da Ana é uma versão curta do que o Debian e o Ubuntu colocam em toda conta nova (o original fica em /etc/skel/.bashrc):

Linhas 4 a 7: o porteiro

case $- in
Compara o texto de $- (as opções do shell) com os padrões abaixo. Veja case.
*i*) ;;
Se tem um i (interativo): não faz nada (;; logo depois do padrão) e segue lendo o arquivo.
*) return;;
Qualquer outro caso: return para de ler o arquivo aqui mesmo e volta para quem chamou.
esac
Fim do case (case de trás para frente).

Por que isso existe, se o .bashrc já é "para shells interativos"? Porque ele pode ser lido por shells que não são interativos: o .profile o carrega num bash -lc, e o Bash também o lê quando é iniciado pelo ssh só para rodar um comando (ssh servidor 'ls'). Nesses casos, um echo no .bashrc sujaria a saída e quebraria programas como scp e rsync. O porteiro garante: se ninguém está digitando, nada daqui roda.

O mesmo teste pode ser escrito como [[ $- != *i* ]] && return. O case é usado porque também funciona em shells mais antigos que não têm [[ ]].

E o .profile?

O .profile da Ana tem duas tarefas:

# ~/.profile: executado pelo shell de login.

# se estiver rodando bash, carrega o .bashrc
if [ -n "$BASH_VERSION" ]; then
    if [ -f "$HOME/.bashrc" ]; then
        . "$HOME/.bashrc"
    fi
fi

# inclui a pasta bin pessoal no PATH, se existir
if [ -d "$HOME/bin" ] ; then
    PATH="$HOME/bin:$PATH"
fi
if [ -d "$HOME/.local/bin" ] ; then
    PATH="$HOME/.local/bin:$PATH"
fi
[ -n "$BASH_VERSION" ]
"A variável BASH_VERSION não está vazia?" O .profile também é lido por outros shells (como o sh); esse teste garante que o .bashrc, que é do Bash, só seja carregado pelo Bash.
[ -f "$HOME/.bashrc" ]
"O arquivo existe?" Evita erro se não existir.
. "$HOME/.bashrc"
O ponto é o mesmo que source: lê o arquivo dentro deste shell.
[ -d "$HOME/bin" ]
"A pasta ~/bin existe?" Se existir, ela entra no começo do PATH (veja PATH).

Coisas que só precisam ser feitas uma vez por sessão e que os programas filhos herdam, como o PATH, ficam no .profile. Coisas do shell interativo (aliases, prompt, histórico) ficam no .bashrc. Como o .profile só é lido no login, a pasta ~/bin criada agora só entra no PATH no próximo login:

$ mkdir -p ~/bin
$ bash -lc 'echo $PATH'                « simula um login novo
/home/ana/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin

O /home/ana/bin apareceu no começo. O /snap/bin no fim foi acrescentado por um arquivo de /etc/profile.d/, que o /etc/profile lê; no seu sistema essa parte pode ser diferente.

Na prática, muita gente põe o PATH no .bashrc

Funciona para o terminal, mas tem um efeito colateral: cada vez que o .bashrc é relido, a pasta é acrescentada de novo. Veja o que acontece depois de três source:

$ echo 'PATH="$HOME/bin:$PATH"' >> ~/.bashrc
$ source ~/.bashrc
$ source ~/.bashrc
$ source ~/.bashrc
$ echo $PATH
/home/ana/bin:/home/ana/bin:/home/ana/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

Não quebra nada, mas polui. Na aula de PATH você vê como adicionar só se a pasta ainda não estiver lá.

Aplicar uma mudança: source

Editar o .bashrc não muda o shell que já está aberto: o arquivo só é lido quando um shell começa. A Ana acrescenta um alias ao arquivo:

$ echo "alias oi='echo Olá, Ana'" >> ~/.bashrc
$ tail -n 2 ~/.bashrc
alias l='ls -CF'
alias oi='echo Olá, Ana'      « está no arquivo…
$ oi
bash: oi: comando não encontrado    « …mas o shell aberto ainda não leu
$ echo $?
127

O código 127 é o "comando não encontrado" (veja código de saída). Para o shell atual ler o arquivo de novo, use source:

source
"Leia este arquivo e execute cada linha aqui, neste shell." (source = fonte.)
~/.bashrc
O arquivo a ler.
$ source ~/.bashrc
$ oi
Olá, Ana
$ echo $?
0

O source não mostra nada quando dá certo. O ponto (. ~/.bashrc) faz exatamente a mesma coisa: é o nome antigo, do padrão POSIX, e funciona até no sh. O source é o nome do Bash, mais fácil de ler.

Missão: acrescente ao fim do ~/.bashrc um alias chamado hoje que rode date +%d/%m/%Y. Use echo "…" >> ~/.bashrc (com dois >, para não apagar o arquivo!). Depois aplique a mudança no shell atual e teste digitando hoje.

Cada sistema, um jeito

As regras do Bash são as mesmas em todo lugar; o que muda é qual tipo de shell o terminal abre e quais arquivos vêm prontos na conta nova. Isso explica por que um tutorial manda editar o .bashrc e outro o .bash_profile.

SistemaA janela de terminal abre…Arquivos que vêm na conta novaArquivo do sistema
Debian, Ubuntu, MintInterativo, não-login → lê o ~/.bashrc.bashrc, .profile (que carrega o .bashrc), .bash_logout/etc/bash.bashrc (lido também no login, pelo /etc/profile)
Fedora, RHELInterativo, não-login → lê o ~/.bashrc.bashrc (que carrega /etc/bashrc), .bash_profile (que carrega o .bashrc), .bash_logout/etc/bashrc, carregado pelo seu .bashrc
ArchInterativo, não-login → lê o ~/.bashrc.bashrc, .bash_profile (que carrega o .bashrc), .bash_logout/etc/bash.bashrc

A receita que funciona em todos: coloque suas preferências no ~/.bashrc e garanta que o arquivo de login (.profile ou .bash_profile) carregue o .bashrc. No macOS com Bash instalado, crie um ~/.bash_profile com esta linha:

[ -r ~/.bashrc ] && . ~/.bashrc

O -r testa se o arquivo existe e pode ser lido (readable). Lembre-se de que o /bin/bash do macOS é a versão 3.2; veja Bash em cada sistema.

Quando não funciona

Coloquei no .bashrc e "não funciona" 
$ oi
bash: oi: comando não encontrado

O que aconteceu: quase sempre é uma destas três coisas: (1) o shell aberto ainda não leu o arquivo; (2) você está num shell de login cujo .profile/.bash_profile não carrega o .bashrc (ssh, macOS, um .bash_profile recém-criado); (3) você está num script, que não lê o .bashrc.

Como confirmar: grep oi ~/.bashrc (está no arquivo?), shopt login_shell (é de login?), ls -a ~ | grep bash_profile (existe um .bash_profile escondendo o .profile?).

Como resolver: source ~/.bashrc; se for login, faça o .bash_profile carregar o .profile ou o .bashrc, como mostrado acima. Num script, não use alias: use uma função ou o comando completo.

Rodei bash ~/.bashrc e apareceu um erro de return 
$ bash ~/.bashrc
/home/ana/.bashrc: linha 6: return: possível retornar (`return') apenas de uma função ou script carregado (com `source')
$ echo $?
0

O que aconteceu: bash arquivo roda o arquivo como um script, num Bash novo e não interativo. O porteiro do topo tentou o return, que só funciona em funções ou em arquivos lidos com source. E mesmo que tivesse rodado tudo, os aliases seriam criados nesse outro Bash, que termina em seguida.

Como resolver: use source ~/.bashrc.

Mensagens de erro toda vez que abro o terminal 
$ bash -ic true
alias ll='ls -alF'
bash: alias: =: não encontrado
bash: alias: ls -l: não encontrado

O que aconteceu: a Ana acrescentou alias ll = 'ls -l', com espaços em volta do =. O Bash entendeu três pedidos separados: "mostre o alias ll" (por isso a primeira linha), "mostre o alias =" e "mostre o alias ls -l".

Como resolver: abra o arquivo (nano ~/.bashrc), escreva sem espaços (alias ll='ls -l'), salve e rode source ~/.bashrc. O erro não impede o resto do arquivo de rodar, por isso o terminal continua utilizável.

"erro de sintaxe: fim inesperado do arquivo" 
$ bash -ic true
bash: /home/ana/.bashrc: linha 24: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 22

O que aconteceu: um if começou na linha 22 e o arquivo acabou sem o fi. Com um erro de sintaxe, o Bash não consegue rodar o bloco quebrado.

Como confirmar: bash -n ~/.bashrc confere a sintaxe sem rodar nada (veja depurar); tail -n 5 ~/.bashrc mostra o fim do arquivo.

Como resolver: feche o bloco (fi, done, esac, } ou a aspa que faltou) e rode source ~/.bashrc.

O terminal abre e fecha na hora

O que aconteceu: alguma linha do .bashrc encerra o shell: um exit esquecido, ou um exec de um programa que não existe. A janela abre, lê o arquivo, o shell termina, a janela fecha. Na simulação abaixo, a Ana acrescentou exit no fim do arquivo; o bash -i termina sem nem mostrar o prompt:

$ echo "exit" >> ~/.bashrc
$ bash -i; echo "código: $?"
código: 0                     « o bash novo leu o .bashrc e saiu na hora

Como resolver: você precisa de um shell que não leia o .bashrc:

  1. Se ainda tem algum terminal aberto, rode bash --norc nele. O prompt vira o padrão do Bash, porque nada foi configurado: 
    $ bash --norc
bash-5.3$ nano ~/.bashrc      « apague a linha com problema, salve
bash-5.3$ exit
  2. Sem terminal aberto: nas preferências do terminal (no GNOME Terminal, em Preferências → perfil → Comando), marque "executar um comando personalizado" com bash --norc; ou abra o .bashrc num editor gráfico (no gerenciador de arquivos, Ctrl+H mostra os arquivos ocultos).
  3. Para voltar ao .bashrc original da distribuição: cp /etc/skel/.bashrc ~/ (você perde suas personalizações; faça uma cópia antes).

Para não passar por isso: antes de mexer, faça uma cópia (cp ~/.bashrc ~/.bashrc.bak) e, depois de editar, teste num Bash novo (bash) sem fechar a janela atual.

Uma variável do .bashrc não chega no script

O que aconteceu: o script não lê o .bashrc; ele só recebe as variáveis exportadas pelo shell que o chamou. Se o .bashrc tem PASTA_BACKUP=~/bkp sem export, o script vê a variável vazia.

Como resolver: export PASTA_BACKUP=~/bkp no .bashrc (ou no .profile), depois source. Veja Variáveis, escopo e export.

Experimente: detectar o tipo de shell

Missão: complete o script para que ele escreva interativo ou não interativo, testando se a variável $- contém a letra i. Clique em Rodar: como o simulador roda bash tipo.sh, a resposta certa é "não interativo".

#!/usr/bin/env bash
# troque o false pelo teste
if [[ $- == *i* ]]; then
    echo "interativo"
else
    echo "não interativo"
fi

Resumo

  • Todo Bash é (ou não) interativo ([[ $- == *i* ]]) e (ou não) de login (shopt login_shell).
  • Login lê /etc/profile e o primeiro de ~/.bash_profile, ~/.bash_login, ~/.profile. Interativo não-login lê ~/.bashrc. Scripts não leem nada (só $BASH_ENV).
  • Preferências do terminal no .bashrc; PATH e variáveis exportadas no .profile; e o arquivo de login deve carregar o .bashrc.
  • Depois de editar, source ~/.bashrc (ou . ~/.bashrc). Nunca bash ~/.bashrc.
  • Faça cópia antes de editar; se quebrar, bash --norc e bash -n ~/.bashrc são seus amigos.
