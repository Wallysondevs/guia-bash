Bash A Ordem das Expansões

Quando você aperta Enter, o Bash não roda a linha do jeito que você digitou. Antes, ele a transforma: troca ~ pela sua pasta, $nome pelo valor, *.txt pela lista de arquivos… Essas trocas acontecem sempre na mesma ordem. Conhecer essa ordem explica de uma vez vários "mistérios" do Bash: por que {1..$n} não funciona, por que uma variável com * vira lista de arquivos e por que as aspas resolvem tanta coisa.

Você vai aprender
  • As etapas, na ordem: palavras e alias → chaves → til → variáveis, contas e $( ) → separação de palavras → curingas → remoção de aspas.
  • A acompanhar uma linha de verdade, etapa por etapa, até o comando final.
  • A usar set -x para ver o comando que o Bash realmente rodou.
  • A explicar (e consertar) os erros clássicos que nascem dessa ordem.

A ideia: o Bash reescreve a sua linha

Pense numa receita com abreviações: "1 xíc. de açúcar". Antes de cozinhar, alguém lê e entende "uma xícara". O Bash faz isso com cada linha. Você escreve abreviações (~, $USER, *.txt, {a,b}), e o Bash as expande (troca pelo texto completo). Só depois disso o comando roda. O programa chamado nunca vê as abreviações; ele recebe o resultado.

Você já conhece cada expansão separada: chaves, curingas, variáveis, contas, substituição de comando e aspas. Esta aula junta tudo e mostra quem vem antes de quem.

O mapa

  linha digitada
       │
  ①  dividir em palavras e operadores   (espaços, | ; & < > ( ), respeitando aspas)
       │    + alias: a 1ª palavra do comando é trocada, se for um alias
       ▼
  ②  chaves              {a,b}  {1..5}
       ▼
  ③  til ─┐
      parâmetros e variáveis   $nome  ${x%.txt}       ← estas quatro (e <( ))
      aritmética               $((2+3))                  acontecem juntas,
      substituição de comando  $(cmd)  `cmd`             da esquerda para a direita
       ▼
  ④  separação de palavras   (só no que veio de ③ e SEM aspas; usa o IFS)
       ▼
  ⑤  curingas                *  ?  [ ]   (só fora de aspas)
       ▼
  ⑥  remoção de aspas        tira as ' " \ que você digitou
       ▼
  redirecionamentos (> < …) e, por fim, o comando roda

Duas regras resumem o mapa:

  • Cada etapa só trabalha com o que sobrou da anterior. O que uma etapa produz não volta para uma etapa que já passou.
  • As aspas valem do começo ao fim. Elas são respeitadas em todas as etapas e só são retiradas na última.

Uma linha acompanhada passo a passo

Vamos preparar duas variáveis e rodar uma linha que usa quase tudo:

$ nome="Ana Paula"
$ frase="olá *"
$ echo {a,b}-$((2+3)) ~ $nome *.txt "$frase"
a-5 b-5 /home/ana Ana Paula frutas.txt olá *

O echo junta os argumentos com um espaço, e isso esconde quantos argumentos ele recebeu. O printf '[%s]\n' mostra cada argumento entre colchetes, um por linha. É a ferramenta perfeita para ver o resultado das expansões:

$ printf '[%s]\n' {a,b}-$((2+3)) ~ $nome *.txt "$frase"
[a-5]
[b-5]
[/home/ana]
[Ana]                « $nome sem aspas virou DOIS argumentos
[Paula]
[frutas.txt]
[olá *]              « "$frase" com aspas: um argumento, e o * ficou intacto

Agora, etapa por etapa. A linha da esquerda é o estado depois de cada uma:

EtapaComo a linha ficaO que mudou
① palavrasecho · {a,b}-$((2+3)) · ~ · $nome · *.txt · "$frase"Seis palavras, separadas pelos espaços que você digitou. echo não é alias, nada a trocar.
② chavesecho a-$((2+3)) b-$((2+3)) ~ $nome *.txt "$frase"{a,b}-… virou duas palavras. Repare: a conta ainda não foi feita, foi copiada para as duas.
③ til, variáveis, contasecho a-5 b-5 /home/ana Ana␣Paula *.txt "olá *"~ → /home/ana; as contas → 5; $nome e $frase → os valores. Ana␣Paula ainda é uma palavra.
④ separaçãoecho a-5 b-5 /home/ana Ana Paula *.txt "olá *"O valor de $nome veio sem aspas: o espaço o partiu em Ana e Paula. O de "$frase" estava entre aspas: não foi partido.
⑤ curingasecho a-5 b-5 /home/ana Ana Paula frutas.txt "olá *"*.txt virou o único arquivo .txt da pasta. O * de "olá *" está entre aspas: não é curinga.
⑥ aspasecho a-5 b-5 /home/ana Ana Paula frutas.txt olá␣*As aspas de "olá *" saem. O echo recebe 7 argumentos (o último é olá *, com espaço).

Veja com os seus olhos: set -x

O set -x liga o "modo rastro" (x de xtrace): antes de rodar cada comando, o Bash mostra uma linha com + e o comando já expandido. É o resultado da etapa ⑥, com aspas recolocadas onde é preciso para você enxergar onde cada argumento começa e termina:

$ set -x
$ echo {a,b}-$((2+3)) ~ $nome *.txt "$frase"
+ echo a-5 b-5 /home/ana Ana Paula frutas.txt 'olá *'      « o comando que realmente rodou
a-5 b-5 /home/ana Ana Paula frutas.txt olá *
$ set +x
+ set +x

set +x desliga (o próprio set +x ainda aparece no rastro). Quando um comando se comporta de um jeito estranho, o set -x é o primeiro lugar para olhar. Ele é visto a fundo em Depurar.

Etapa a etapa, com o que cada uma explica

① Palavras e alias

Primeiro o Bash corta a linha em palavras nos espaços e nos operadores (|, ;, &, >…), sem cortar o que está entre aspas. É aqui que if, for, | e > são reconhecidos. Por isso uma variável nunca vira operador:

$ c="ls -l frutas.txt | wc -l"; $c
ls: não foi possível acessar '|': Arquivo ou diretório inexistente
ls: não foi possível acessar 'wc': Arquivo ou diretório inexistente
-rw-rw-r-- 1 ana ana 47 out 14 16:05 frutas.txt

O | dentro da variável só apareceu na etapa ③, quando os operadores já tinham sido reconhecidos. Para o ls, | e wc são nomes de arquivo. (Para guardar comandos, use funções; veja também eval.)

Ainda na etapa ①, se a primeira palavra de um comando for um alias, ela é trocada pelo texto do alias. Isso acontece quando a linha é lida, antes de qualquer comando dela rodar. Consequência curiosa:

$ alias oi='echo olá'; oi
bash: oi: comando não encontrado        « na hora em que a linha foi lida, o alias não existia
$ oi
olá                                     « na linha seguinte, já existe

② Chaves vêm antes das variáveis

As chaves são a primeira expansão, e são puramente textuais: não sabem o valor de nenhuma variável. Por isso:

$ n=3
$ echo {1..$n}
{1..3}                 « não virou 1 2 3!
$ echo {1..3}
1 2 3

Na etapa ②, o Bash viu {1..$n}. Isso não é uma sequência válida ($n não é número), então as chaves ficaram como estavam. Na etapa ③, o $n virou 3, mas a etapa das chaves já tinha passado. Resultado: o texto {1..3}, literal.

Para sequências com variáveis, use uma ferramenta que leia o valor depois da expansão:

$ seq 1 $n
1
2
3
$ for ((i=1; i<=n; i++)); do echo -n "$i "; done; echo
1 2 3

Do mesmo jeito, o resultado de uma variável nunca passa pelas chaves: com x='{a,b}', echo $x mostra {a,b}.

③ Til, variáveis, contas e $( ): juntos, da esquerda para a direita

Estas expansões formam um mesmo passo. O Bash percorre a linha da esquerda para a direita e resolve cada uma na ordem em que aparece:

$ i=1
$ echo $((i++)) $((i++)) $i
1 2 3                  « cada $(( )) já vê o i alterado pelo anterior

O til só é expandido no começo de uma palavra (ou depois de = e : em atribuições) e fora de aspas:

$ echo \~ "~" ~ ~ana ~root ~/Documentos x~
~ ~ /home/ana /home/ana /root /home/ana/Documentos x~

E o valor de uma variável é colocado como texto; ele não é expandido de novo:

$ y='$HOME'
$ echo $y
$HOME                  « o $ do valor não é procurado outra vez

④ Separação de palavras: só no que veio de uma expansão sem aspas

Depois da etapa ③, o Bash olha só para os pedaços que vieram de expansões ($var, $(cmd), $(( ))) e que estavam sem aspas. Ele os parte em espaço, TAB e quebra de linha (os caracteres da variável IFS). Espaços repetidos viram um só:

$ texto="a   b"
$ echo $texto
a b                    « sem aspas: dois argumentos, "a" e "b"
$ echo "$texto"
a   b                  « com aspas: um argumento, espaços preservados

Um valor vazio sem aspas não vira argumento vazio: ele desaparece.

$ vazio=
$ printf '[%s]\n' $vazio "$vazio" fim
[]                     « este veio do "$vazio" (com aspas)
[fim]                  « o $vazio sem aspas sumiu

Nas atribuições (u=$t) não há separação nem curingas: t="a b"; u=$t guarda os três espaços. Mesmo assim, usar aspas ali não faz mal e evita dúvidas.

⑤ Curingas: depois da separação

Cada palavra que sobrou e tem *, ? ou [ fora de aspas é comparada com os nomes de arquivos. E isso vale também para o que veio de uma variável:

$ x="*"
$ echo $x
Área de trabalho Documentos Downloads frutas.txt Imagens Modelos Música Público Vídeos
$ echo "$x"
*

O * chegou na etapa ③ (valor da variável), sobreviveu à separação e, sem aspas, foi tratado como curinga na ⑤. Com set -x, dá para ver a lista de arquivos no lugar do *:

$ set -x
$ echo $x
+ echo 'Área de trabalho' Documentos Downloads frutas.txt Imagens Modelos Música Público Vídeos
Área de trabalho Documentos Downloads frutas.txt Imagens Modelos Música Público Vídeos
$ echo "$x"
+ echo '*'
*
$ echo $(echo "*.txt")
++ echo '*.txt'        « ++ = comando rodado dentro do $( )
+ echo frutas.txt      « a saída "*.txt" virou curinga
frutas.txt
$ set +x
+ set +x

Repare que o curinga gerou 'Área de trabalho' como um argumento: o resultado da etapa ⑤ não é separado de novo. Já um $arquivo com espaços, sem aspas, é partido na etapa ④, antes:

$ arquivo="notas de aula.txt"
$ touch "$arquivo"
$ set -x
$ rm $arquivo
+ rm notas de aula.txt
rm: não foi possível remover 'notas': Arquivo ou diretório inexistente
rm: não foi possível remover 'de': Arquivo ou diretório inexistente
rm: não foi possível remover 'aula.txt': Arquivo ou diretório inexistente
$ set +x
+ set +x
$ rm "$arquivo"        « com aspas, deu certo (sem mensagem, código 0)

Os curingas têm opções que mudam o que acontece quando nada casa (nullglob, failglob) e o que entra na lista (dotglob, globstar); veja Opções do Shell.

⑥ Remoção de aspas

Por fim, as aspas e barras invertidas que você digitou são retiradas. Elas cumpriram o papel delas (proteger das etapas ② a ⑤) e não chegam ao comando. As aspas que vieram de dentro de uma variável não são retiradas: são parte do valor.

$ echo "$HOME" '$HOME'
/home/ana $HOME        « aspas duplas deixam a etapa ③ agir; simples, não

Experimente

Missão: a variável n já vale 4. Primeiro tente echo {1..$n} e veja o que sai. Depois mostre os números de 1 até n de um jeito que funcione, usando a variável (sem digitar o 4).

Missão: a variável arq guarda o nome relatorio final.txt, que existe na pasta. Ligue o set -x, tente rm $arq e leia o rastro. Depois apague o arquivo do jeito certo, usando a variável.

'…' aspas simplestudonadaO texto deve chegar exatamente como está: '$HOME', regex, código de awk.

Qual usar? Regra prática do Bash: ponha aspas duplas em toda expansão ("$var", "$(cmd)", "${lista[@]}"), a não ser que você queira separação ou curingas. Aspas simples para texto que não deve ser mexido. O ShellCheck avisa quando faltam aspas (aviso SC2086).

Quando não funciona

{1..$n} sai literal 
$ echo {1..$n}
{1..3}

O que aconteceu: as chaves (etapa ②) são expandidas antes das variáveis (etapa ③).

Como resolver: seq 1 "$n" ou for ((i=1; i<=n; i++)). Você vai encontrar na internet eval echo {1..$n}, que funciona porque faz o Bash ler a linha duas vezes; evite (veja eval).

"redirecionamento ambíguo" 
$ arq="meu log.txt"
$ echo oi > $arq
bash: $arq: redirecionamento ambíguo
$ echo oi > "$arq"                     « certo

O que aconteceu: depois das expansões, $arq virou duas palavras (meu e log.txt), e um > só pode ter um destino. O mesmo erro aparece quando a variável está vazia ou quando um curinga casa vários arquivos.

Como resolver: aspas: > "$arq".

O til não vira a pasta pessoal 
$ d="~/Documentos"
$ ls "$d"
ls: não foi possível acessar '~/Documentos': Arquivo ou diretório inexistente

O que aconteceu: o ~ estava entre aspas na atribuição, então ficou como o caractere ~. Depois, ao usar $d, o til não é mais expandido: ele veio de uma variável, e o til não é procurado no resultado da etapa ③.

Como resolver: deixe o til fora das aspas (d=~/Documentos) ou, melhor ainda, use "$HOME", que funciona dentro de aspas: d="$HOME/Documentos".

Uma variável com * listou os arquivos

O que aconteceu: echo $x com x="*", ou echo $(cmd) cuja saída tem *: sem aspas, o valor passa pela etapa ⑤ e vira curinga. Num for f in $(…), além disso, nomes com espaço são partidos na etapa ④.

Como resolver: echo "$x", echo "$(cmd)". Para listas de arquivos, use o curinga direto (for f in *.txt) ou um array (veja Arrays).

Guardei um comando com | numa variável e ele não funciona

O que aconteceu: operadores como |, >, && e ; são reconhecidos na etapa ①. O que vem de uma variável aparece só na ③ e é tratado como texto comum.

Como resolver: transforme o comando numa função: conta() { ls -l frutas.txt | wc -l; }.

Resumo

  • Ordem: palavras/alias → chaves → til, variáveis, contas e $( ) (juntos, da esquerda para a direita) → separação de palavras → curingas → remoção de aspas → redirecionamentos e execução.
  • Uma etapa nunca volta atrás: por isso {1..$n} não funciona e um | dentro de variável não vira pipe.
  • Separação e curingas só atingem o que veio de expansões sem aspas: "$var" chega inteiro.
  • printf '[%s]\n' … mostra os argumentos um a um; set -x mostra o comando final.
  • Na dúvida, aspas duplas em volta de toda expansão.
