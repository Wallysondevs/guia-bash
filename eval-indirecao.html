Bash eval, Indireção e nameref

Às vezes o nome de uma variável só é conhecido quando o script roda: "guarde o total na variável cujo nome veio no argumento", "mostre o valor do campo que o usuário escolheu". O jeito antigo de resolver isso é o eval, que é poderoso e perigoso. O Bash moderno tem jeitos seguros para quase todos os casos: ${!nome}, declare -n, printf -v e arrays associativos.

Você vai aprender
  • O que o eval faz: lê o texto de novo, como se fosse uma linha de comando.
  • Por que ele é perigoso, com uma injeção de verdade (e inofensiva) por um nome de arquivo.
  • Ler uma variável pelo nome com ${!nome} e listar variáveis com ${!prefixo*}.
  • Escrever numa variável pelo nome com printf -v, declare e declare -n (nameref).
  • Quando um array associativo resolve melhor, e quando o eval é aceitável.

O problema: o nome da variável está numa variável

A Ana tem as variáveis cidade=Recife e estado=PE. Um script pergunta "qual campo você quer ver?" e guarda a resposta em campo. Se a resposta for cidade, o script precisa mostrar Recife. Mas $campo devolve só a palavra cidade:

$ campo=cidade
$ cidade=Recife
$ echo "$campo"
cidade                             « o valor de campo é o NOME da outra variável

É como um bilhete que diz "a chave está na gaveta 3": você precisa ler o bilhete e, depois, ir à gaveta. Essa "segunda leitura" se chama indireção.

O que o eval faz

eval ("avaliar") junta seus argumentos num texto e manda o Bash ler esse texto de novo, como uma linha de comando nova, com todas as expansões, aspas, |, ; e >.

Um exemplo onde isso faz diferença: um comando com pipe guardado numa variável. Sem eval, o | não é pipe, é só um caractere dentro do valor:

$ cmd="ls Documentos | head -2"
$ $cmd
ls: opção inválida -- “2”
Tente "ls --help" para mais informações.
$ eval "$cmd"
acesso.log
alunos.csv
  • $cmd: o Bash expandiu a variável e separou as palavras: ls, Documentos, |, head, -2. O ls recebeu tudo como argumento e reclamou do -2. Operadores como | só são reconhecidos antes das expansões (veja A Ordem das Expansões).
  • eval "$cmd": o texto ls Documentos | head -2 foi lido de novo, do zero. Agora o | é um pipe.

E a indireção com eval:

$ eval echo "\$$campo"
Recife
eval
"Leia o resultado de novo, como comando."
echo
O comando que vai rodar na segunda leitura.
"\$$campo"
Na primeira leitura, \$ vira um $ comum e $campo vira cidade: sobra o texto $cidade. Na segunda leitura (a do eval), $cidade vira Recife.

Funciona, mas repare: o eval trata o valor de uma variável como código. Se esse valor vier de fora (um argumento, um nome de arquivo, uma resposta do usuário), quem escreveu o valor escreve código no seu script.

Por que o eval é perigoso: uma injeção

Vamos ver o problema acontecer. A pasta recebidos tem três arquivos que chegaram de fora. Um deles tem um nome "esquisito", e nomes de arquivo no Linux podem ter quase qualquer caractere, inclusive ; e >:

$ ls recebidos
 foto.jpg   notas.txt  'x; echo INVADIDO > aviso.txt'   « o 3º é UM nome de arquivo, com espaços, ; e >

(O ls põe aspas em volta do nome que tem espaços, e um espaço na frente dos outros para alinhar.)

Um script quer guardar cada nome em variáveis numeradas (arquivo_1, arquivo_2…) e usa eval para criar o nome da variável:

#!/usr/bin/env bash
i=0
for f in recebidos/*; do
  i=$((i + 1))
  eval "arquivo_$i=$f"
done
echo "arquivo_1 = $arquivo_1"

$ bash relatorio.sh
arquivo_1 = recebidos/foto.jpg     « parece normal…
$ cat aviso.txt
INVADIDO                           « …mas um arquivo foi criado pelo NOME de outro arquivo!

Com bash -x (veja Depurar) dá para ver o que o eval recebeu na terceira volta:

$ bash -x relatorio.sh
…                                  « encurtado: as duas primeiras voltas
+ i=3
+ eval 'arquivo_3=recebidos/x; echo INVADIDO > aviso.txt'
++ arquivo_3=recebidos/x
++ echo INVADIDO
+ echo 'arquivo_1 = recebidos/foto.jpg'
arquivo_1 = recebidos/foto.jpg

O ; do nome do arquivo encerrou a atribuição, e o resto virou um comando. Aqui ele só escreveu "INVADIDO" num arquivo, mas poderia ser rm -rf ~. E não houve erro nenhum: o script terminou com código 0. Isso se chama injeção de comando.

Regra prática

Nunca passe para o eval um texto que contenha dados de fora (argumentos, nomes de arquivo, entrada do usuário, conteúdo de arquivos ou da internet). Para quase tudo o que se faz com eval, existe uma forma segura, que você vai ver agora.

Ler pelo nome: ${!nome}

A expansão indireta ${!nome} faz a "segunda leitura" sem rodar código nenhum: pega o valor de nome e usa como nome da variável a ler.

${
Início da expansão de parâmetro.
!
"Indireto": use o valor como nome de outra variável.
campo
A variável que guarda o nome (cidade).
}
Fim. O resultado é o valor de $cidade.
$ echo "${!campo}"
Recife

Se o valor não for um nome de variável válido, o Bash dá erro em vez de executar alguma coisa:

$ x=nome-invalido; echo "${!x}"
bash: nome-invalido: nome de variável inválido

Missão: já existem as variáveis cidade, estado e campo. A variável campo guarda o nome de uma das outras duas. Mostre o valor da variável cujo nome está em campo, sem eval e sem escrever o nome dela.

Listar variáveis pelo começo do nome: ${!prefixo*}

Com * ou @ no fim, o ! muda de sentido: ${!cor_*} devolve os nomes de todas as variáveis que começam com cor_. Junte com ${!v} para ver os valores:

$ declare "cor_fundo=azul" "cor_texto=branco"
$ echo "${!cor_*}"
cor_fundo cor_texto
$ for v in ${!cor_@}; do echo "$v = ${!v}"; done
cor_fundo = azul
cor_texto = branco

A diferença entre * e @ é a mesma de $* e $@: entre aspas, "${!cor_@}" dá uma palavra por nome. Como nomes de variáveis não têm espaço, na prática as duas formas se comportam igual.

Escrever pelo nome

Ler era fácil. E para atribuir a uma variável cujo nome está em outra? ${!nome}=valor não existe. Há três ferramentas.

printf -v nome

O printf -v guarda o resultado na variável indicada, em vez de mostrar na tela (veja printf). O nome pode ser montado com outras variáveis, e o valor nunca é executado:

$ printf -v "total_$campo" "%d" 42
$ echo "$total_cidade"
42

O mesmo script da injeção, consertado:

#!/usr/bin/env bash
i=0
for f in recebidos/*; do
  i=$((i + 1))
  printf -v "arquivo_$i" "%s" "$f"
done
echo "arquivo_1 = $arquivo_1"
echo "arquivo_3 = $arquivo_3"

$ bash seguro.sh
arquivo_1 = recebidos/foto.jpg
arquivo_3 = recebidos/x; echo INVADIDO > aviso.txt   « o nome inteiro virou só um valor
$ ls aviso.txt
ls: não foi possível acessar 'aviso.txt': Arquivo ou diretório inexistente   « nada foi executado

declare e local com nome montado

declare "nome=valor" também aceita um nome montado na hora, e dentro de funções o local faz o mesmo. O texto depois do = é só valor, não é lido de novo como comando:

$ declare "cor_$campo=verde"
$ echo "$cor_cidade"
verde

Cuidado: dentro de uma função, declare cria uma variável local. Para criar uma global de dentro de uma função, use declare -g.

nameref: declare -n bash 4.3+

Um nameref (name reference, "referência pelo nome") é uma variável que funciona como um apelido de outra. Tudo o que você lê ou escreve nela, na verdade, lê ou escreve na outra:

$ declare -n ref=cidade
$ echo "$ref"
Recife                             « lê cidade
$ ref=Salvador
$ echo "$cidade"
Salvador                           « escrever em ref mudou cidade

O uso mais comum é numa função que devolve o resultado numa variável escolhida por quem chama, sem $( ) (que criaria um subshell):

$ saudar() {
>   local -n saida=$2
>   saida="Olá, $1"
> }
$ saudar Ana msg
$ echo "$msg"
Olá, Ana
local -n
Cria um nameref local da função (local aceita as mesmas opções de declare).
saida=$2
O apelido aponta para a variável cujo nome veio no 2º argumento (msg).
saida="Olá, $1"
Escrever em saida escreve em msg, lá fora.

Também funciona com arrays: local -n lista=$1 e depois "${lista[@]}" percorre o array cujo nome foi passado. Mais sobre devolver valores em local, return e Saída.

Missão: a função guardar usa eval para pôr um valor na variável cujo nome vem no 1º argumento. Reescreva a função sem eval, com printf -v ou com um nameref (local -n). A saída deve continuar cor = azul.

#!/usr/bin/env bash
guardar() {
  eval "$1=\$2"
}
guardar cor "azul"
echo "cor = $cor"

#!/usr/bin/env bash
guardar() {
  printf -v "$1" '%s' "$2"
}
guardar cor "azul"
echo "cor = $cor"

Muitas vezes, a resposta é um array associativo

Se você está criando idade_Ana, idade_Bruno, idade_Carla… o que você quer, na verdade, é uma variável com várias chaves. É exatamente o que um array associativo faz, sem indireção nenhuma:

$ declare -A idade=([Ana]=29 [Bruno]=34)
$ quem=Bruno
$ echo "${idade[$quem]}"
34

E, para guardar uma lista de nomes de arquivo, um array comum é mais simples que arquivo_1, arquivo_2…: arquivos+=("$f") dentro do laço, e "${arquivos[2]}" para o terceiro.

Quando o eval é aceitável

O eval não é proibido; ele é a ferramenta certa quando o texto a executar é código de verdade, vindo de uma fonte confiável. Os exemplos clássicos são programas que imprimem comandos de shell para você rodar:

$ dircolors -b | head -c 60; echo
LS_COLORS='rs=0:di=01;34:ln=01;36:mh=00:pi=40;33:so=01;35:do

O dircolors -b imprime uma atribuição de LS_COLORS (as cores do ls), e o ~/.bashrc de muitas distribuições roda eval "$(dircolors -b)". O mesmo vale para eval "$(ssh-agent -s)" e para ferramentas como gerenciadores de versão, que pedem um eval "$(ferramenta init bash)".

Se você realmente precisa montar código com um valor de fora, deixe o Bash pôr as aspas por você: ${f@Q} (ou printf '%q') devolve o valor já protegido para ser lido de novo:

$ f="recebidos/x; echo INVADIDO > aviso.txt"
$ echo "${f@Q}"
'recebidos/x; echo INVADIDO > aviso.txt'
$ eval "a=${f@Q}"
$ echo "a = $a"
a = recebidos/x; echo INVADIDO > aviso.txt   « virou só um valor, nada foi executado

Mesmo assim, se houver uma alternativa da tabela acima, prefira ela: é mais fácil de ler e de revisar. O ShellCheck ajuda a encontrar eval e variáveis sem aspas.

Quando não funciona

"expansão indireta inválida" 
$ unset -v nada; echo "[${!nada}]"
bash: nada: expansão indireta inválida

O que aconteceu: a variável que deveria guardar o nome (nada) está vazia ou não existe, então não há para onde apontar.

Como resolver: confira se ela tem valor antes: [[ -n $campo ]] && echo "${!campo}". Com ${!campo:-padrão} você tem um valor padrão quando a variável apontada estiver vazia.

"nome de variável inválido" 
$ x=nome-invalido; echo "${!x}"
bash: nome-invalido: nome de variável inválido
$ declare -n r2=nome-ruim
bash: declare: `nome-ruim': nome de variável inválido para referência de nome

O que aconteceu: nomes de variável só podem ter letras, números e _, e não podem começar com número. Hífen, espaço e ponto não valem.

Como resolver: se o "nome" vem de um dado qualquer (um nome de arquivo, uma resposta), use um array associativo: declare -A dados; dados["nome-ruim"]=1 aceita qualquer texto como chave.

"referência circular de nome" num nameref 
$ zerar() { local -n v=$1; v=0; }
$ v=5
$ zerar v
bash: local: aviso: v referência circular de nome
bash: aviso: v referência circular de nome
bash: aviso: v: excedido o tamanho máximo de nameref (8)

O que aconteceu: o nameref dentro da função se chama v e quem chamou pediu para ele apontar para… v. Ele aponta para si mesmo.

Como resolver: dê ao nameref um nome que dificilmente alguém vai usar fora, por exemplo com o nome da função: local -n _zerar_ref=$1.

Uma variável não foi criada e nenhum erro apareceu

O que aconteceu: com declare "x_$i=…" dentro de uma função, a variável é local e some quando a função termina.

Como resolver: declare -g "x_$i=…", ou printf -v, que cria no escopo atual visível (global, se não houver uma local com o mesmo nome).

Resumo

  • eval lê um texto de novo como comando: dados de fora viram código (injeção).
  • Para ler pelo nome: ${!nome}. Para listar por prefixo: ${!prefixo@}.
  • Para escrever pelo nome: printf -v, declare (-g em funções) ou nameref declare -n/local -n.
  • Muitas variáveis com nomes parecidos? Use um array associativo.
  • eval só com código confiável (eval "$(dircolors -b)"); se precisar proteger um valor, ${var@Q}.
