Bash Agendar Scripts

Um script de backup só é útil se rodar todo dia, inclusive quando você esquece. O Linux tem dois "despertadores" para isso: o veterano cron, presente em todo Unix, e os timers do systemd, nas distribuições modernas. Nesta aula você vai aprender os dois, e principalmente o que muda para um script quando ninguém está olhando: outro ambiente, nenhum terminal, nenhuma tela para mostrar erros.

Você vai aprender
  • A agendar com crontab -e: os 5 campos de tempo, @daily, @reboot.
  • Por que um script que funciona no terminal falha no cron (PATH curto, sem .bashrc, o %) e como testar com env -i.
  • A guardar a saída num log e a impedir duas execuções ao mesmo tempo com flock.
  • A criar um timer do systemd (.service + .timer, OnCalendar=) e a usar systemd-run e at.
Sobre as saídas desta página

O laboratório onde as saídas do guia são conferidas não tem os serviços cron, systemd e atd rodando, e o simulador também não. Por isso, as sessões com crontab, systemctl, journalctl e at são ilustrativas (estão marcadas). Tudo o que dá para rodar de verdade foi conferido: o flock, o ambiente mínimo com env -i, as datas do systemd-analyze calendar e a sintaxe dos arquivos do timer com systemd-analyze verify.

O cron

O cron (do grego chronos, tempo) é um serviço que acorda a cada minuto, lê as tabelas de agendamento e roda o que estiver marcado para aquele minuto. Cada usuário tem a sua tabela, a crontab (cron table). Você não edita o arquivo diretamente: usa o comando crontab.

ComandoO que faz
crontab -eAbre a sua tabela no editor (edit). Ao salvar e sair, o cron confere a sintaxe e passa a usá-la.
crontab -lMostra a tabela (list).
crontab -rApaga a tabela inteira (remove), sem perguntar. Cuidado: o r fica ao lado do e no teclado.
crontab arquivoSubstitui a tabela pelo conteúdo do arquivo.

Sessão ilustrativa, na máquina da Ana, depois de agendar um backup:

$ crontab -l
no crontab for ana                             « (ilustrativo) ainda não há tabela
$ crontab -e
no crontab for ana - using an empty one
crontab: installing new crontab                « (ilustrativo) depois de salvar no editor
$ crontab -l
# m h  dom mon dow   command
30 2 * * * /home/ana/scripts/backup-docs.sh >> /home/ana/logs/backup.log 2>&1

Na primeira vez, o crontab -e pode perguntar qual editor usar (o nano é o mais simples). As mensagens do crontab costumam vir em inglês, mesmo com o sistema em português.

O ambiente mínimo do cron

Este é o motivo número um de "funciona no terminal, mas não no cron". O cron não abre um terminal nem lê o seu ~/.bashrc. Ele roda cada linha com /bin/sh, num ambiente quase vazio. No Debian e no Ubuntu, por exemplo, o comando recebe só algo como:

SHELL=/bin/sh
HOME=/home/ana
LOGNAME=ana
PATH=/usr/bin:/bin

Teste antes, com env -i

Você não precisa esperar até 2:30 para descobrir o problema. O comando env -i roda um programa com o ambiente vazio (ignore environment), e você acrescenta só as variáveis que o cron daria. Este script mostra o ambiente que recebe:

#!/usr/bin/env bash
echo "PATH=$PATH"
echo "HOME=$HOME  SHELL=${SHELL:-}  USER=${USER:-}  LANG=${LANG:-}"
echo "pasta atual: $PWD"
echo "terminal? $([[ -t 1 ]] && echo sim || echo não)"
command -v shellcheck || echo "shellcheck: não encontrado"
type ll 2>&1 | head -1

$ cd /
$ env -i HOME=/home/ana LOGNAME=ana PATH=/usr/bin:/bin SHELL=/bin/sh /bin/sh -c 'bash ~/ambiente.sh'

terminal? não

/home/ana/ambiente.sh: line 7: type: ll: not found « sem LANG, o Bash fala inglês
env -i
Começa com o ambiente vazio.
HOME=… LOGNAME=… PATH=… SHELL=…
Só as variáveis que o cron costuma dar.
/bin/sh -c '…'
Roda a linha como o cron rodaria: com o sh.

(O cron de verdade começa na pasta pessoal; aqui, chamamos de / de propósito, para mostrar que o script não deve depender da pasta atual.) Agora um comando que a Ana instalou em ~/bin, que está no PATH do terminal dela, mas não no do cron:

$ env -i HOME=/home/ana PATH=/usr/bin:/bin /bin/sh -c 'meucomando'
/bin/sh: 1: meucomando: not found              « a mensagem é do dash, o sh do Debian/Ubuntu
$ env -i HOME=/home/ana PATH=/usr/bin:/bin /bin/sh -c '~/bin/meucomando'
meu comando rodou                              « com o caminho completo, funciona

As três soluções para o PATH

  1. Caminhos completos na crontab e no script: /home/ana/bin/meucomando. Descubra o caminho com command -v meucomando no terminal.
  2. Definir o PATH no topo da crontab: PATH=/home/ana/bin:/usr/local/bin:/usr/bin:/bin.
  3. Definir o PATH no começo do script: export PATH="$HOME/bin:/usr/local/bin:$PATH". É a mais robusta, porque vale de onde quer que o script seja chamado.

O % e o ~ na crontab

Dois detalhes da linha da crontab pegam todo mundo:

  • % vira quebra de linha. No campo do comando, o cron troca cada % por uma quebra de linha (o que vem depois do primeiro vira entrada do comando). date +%F não funciona. Escape com barra: date +\%F. Ou, melhor, ponha o comando dentro de um script.
  • ~ funciona no comando, mas não nas variáveis. No comando, quem expande o ~ é o sh, então ~/scripts/backup.sh funciona. Mas as linhas de variáveis da crontab (PATH=~/bin:/usr/bin) são lidas pelo próprio cron, literalmente: nem ~ nem $HOME são expandidos ali. Use caminhos completos nessas linhas.
Na crontabFunciona?
30 2 * * * ~/scripts/backup.shSim (o sh expande o ~).
30 2 * * * $HOME/scripts/backup.shSim (o sh expande $HOME).
PATH=~/bin:/usr/bin:/binNão: o PATH fica com o texto ~/bin.
PATH=/home/ana/bin:/usr/bin:/binSim.
0 0 * * * tar czf /backup/docs-$(date +%F).tgz …Não: o % corta o comando.
0 0 * * * tar czf /backup/docs-$(date +\%F).tgz …Sim.
0 0 * * * [[ -f x ]] && …Não: [[ ]] é do Bash, e a linha roda com sh.

Missão: deixe este script pronto para o cron: ele não pode depender da pasta atual. Use o caminho completo de frutas.txt (com $HOME) e grave o log em $HOME/logs/contagem.log, criando a pasta com mkdir -p se ela não existir.

#!/usr/bin/env bash
total=$(wc -l < frutas.txt)
echo "$(date '+%F %H:%M') frutas: $total" >> contagem.log

#!/usr/bin/env bash
set -euo pipefail
pasta_log="$HOME/logs"
mkdir -p "$pasta_log"
total=$(wc -l < "$HOME/frutas.txt")
echo "$(date '+%F %H:%M') frutas: $total" >> "$pasta_log/contagem.log"

Para onde vai a saída? Logs

No terminal, você vê o que o script escreve. No cron, não há tela. Por padrão, o cron tenta mandar a saída por e-mail para o usuário (variável MAILTO); numa máquina sem servidor de e-mail, ela simplesmente se perde, e com ela as mensagens de erro. Por isso, redirecione sempre:

30 2 * * *  /home/ana/scripts/backup-docs.sh >> /home/ana/logs/backup.log 2>&1
>> …/backup.log
Acrescenta a saída ao log, sem apagar as execuções anteriores (Redirecionamento).
2>&1
Os erros vão para o mesmo lugar. Sem isso, justamente as mensagens de erro se perdem.
MAILTO=""
(No topo da crontab.) Desliga o e-mail, já que tudo vai para o log.

Dentro do script, comece cada linha do log com data e hora, para saber quando cada coisa aconteceu:

log() {
  printf '%s %s\n' "$(date '+%F %T')" "$*"
}
log "backup começou"

Logs crescem para sempre. Apague os antigos de vez em quando, ou use o logrotate do sistema. Outra opção é mandar para o diário do sistema com o comando logger: logger -t backup-docs "backup terminou", e ler com journalctl -t backup-docs.

Não rodar duas vezes: flock

Se o backup das 2:30 ainda está rodando quando chega a hora seguinte (ou alguém o roda à mão ao mesmo tempo), duas cópias podem escrever nos mesmos arquivos. O flock (file lock, "trava de arquivo", do pacote util-linux) resolve: só uma cópia consegue a trava; as outras desistem ou esperam.

#!/usr/bin/env bash
set -euo pipefail
exec 9> /tmp/backup-noturno.lock
if ! flock -n 9; then
  echo "backup-noturno.sh: outra cópia já está rodando; saindo." >&2
  exit 1
fi
echo "[$$] backup começou"
sleep 2
echo "[$$] backup terminou"
exec 9> /tmp/backup-noturno.lock
Abre (e cria) o arquivo de trava no descritor 9, que fica aberto até o script acabar.
flock -n 9
Tenta travar o descritor 9. -n (nonblock): se já estiver travado, desiste na hora, com código 1, em vez de esperar.
if ! … then … exit 1
Não conseguiu a trava: outra cópia está rodando. Avisa e sai.

A trava é solta automaticamente quando o script termina, de qualquer jeito (até com kill -9), porque o sistema fecha o descritor. Não sobra "arquivo de trava" velho bloqueando para sempre. Teste rodando uma cópia em segundo plano e outra logo depois:

$ bash backup-noturno.sh &
[1] 59881
$ sleep 0.5
[59881] backup começou
$ bash backup-noturno.sh
backup-noturno.sh: outra cópia já está rodando; saindo.
$ echo $?
1
$ wait
[59881] backup terminou
$ bash backup-noturno.sh
[59893] backup começou                         « a primeira terminou: a trava está livre
[59893] backup terminou

Também dá para usar o flock direto na crontab, sem mexer no script: flock -n /tmp/backup.lock /home/ana/scripts/backup-docs.sh. Ele trava o arquivo, roda o comando e solta.

Timers do systemd

Nas distribuições com systemd (Debian, Ubuntu, Fedora, Arch…), há uma alternativa ao cron: o timer. Ele usa dois arquivos: um .service, que diz o que rodar, e um .timer com o mesmo nome, que diz quando. Para timers só seus, sem sudo, os arquivos ficam em ~/.config/systemd/user/.

[Unit]
Description=Backup da pasta Documentos

[Service]
Type=oneshot
ExecStart=%h/scripts/backup-docs.sh
[Unit] Description=
Um nome legível, que aparece nas listagens e no log.
Type=oneshot
"Roda uma vez e termina" (não é um serviço que fica no ar).
ExecStart=%h/scripts/…
O comando, com caminho completo. %h é a pasta pessoal (no systemd, o ~ não funciona).
[Unit]
Description=Roda o backup-docs todo dia às 02:30

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true

[Install]
WantedBy=timers.target
OnCalendar=*-*-* 02:30:00
Quando: ano-mês-dia hora:min:seg, com * = qualquer. Todo dia às 2:30.
Persistent=true
Se a máquina estava desligada às 2:30, roda assim que ligar. O cron simplesmente pula a execução perdida.
WantedBy=timers.target
Faz o timer ser ativado sempre que o sistema (ou a sua sessão) iniciar.

Antes de ativar, confira a sintaxe dos dois arquivos com systemd-analyze verify (esta parte foi conferida no laboratório; uma linha de aviso sobre outro serviço do sistema foi omitida):

$ systemd-analyze verify --user ./backup-docs.service ./backup-docs.timer
$ echo $?
0                                              « nenhum problema
$ systemd-analyze verify --user ./backup-docs.timer      « com OnCalendar=todo dia 2h

Timers de usuário e o logout

O systemd de usuário só existe enquanto você tem uma sessão aberta. Para os seus timers rodarem mesmo sem você logado (num servidor, por exemplo), ative o linger uma vez: loginctl enable-linger ana.

Uma vez só, daqui a pouco: systemd-run

Para "rode isto daqui a 10 minutos", sem criar arquivos, use um timer temporário (ilustrativo):

$ systemd-run --user --on-active=10min /home/ana/scripts/backup-docs.sh
Running timer as unit: run-u52.timer           « (ilustrativo) o nome muda a cada vez
Will run service as unit: run-u52.service
$ systemd-run --user --on-calendar='2026-10-15 18:00' /home/ana/scripts/backup-docs.sh

at: uma vez, numa hora marcada (ilustrativo)

O at ("às") roda um comando uma única vez. Ele lê os comandos da entrada e precisa do pacote at com o serviço atd rodando (nem sempre vem instalado):

$ echo "/home/ana/scripts/backup-docs.sh" | at 23:00
warning: commands will be executed using /bin/sh « (ilustrativo)
job 3 at Thu Oct 15 23:00:00 2026
$ atq                                          « lista os agendados
3	Thu Oct 15 23:00:00 2026 a ana
$ atrm 3                                       « cancela o job 3

Formas de dizer a hora: at 23:00, at now + 2 hours, at 9am tomorrow. Como no cron, os comandos rodam com sh e sem terminal.

E um while true; do …; sleep 3600; done?

Parece mais simples, mas um laço com sleep não é um agendador:

  • Morre junto com o terminal (sinal HUP, trap e Sinais) e não volta depois de reiniciar a máquina.
  • Atrasa aos poucos: sleep 3600 conta depois de o trabalho terminar. Se o trabalho leva 2 minutos, ao fim de um dia ele já atrasou 48.
  • Ninguém vê se ele parou. Não há log nem aviso; o cron e o systemd registram cada execução.
  • Ocupa um terminal ou exige truques (nohup, &, disown, veja Jobs).

Ele só faz sentido para algo curto, enquanto você está olhando (por exemplo, "mostre o tamanho da pasta a cada 5 segundos durante a cópia"). Para isso existe até o comando watch -n 5 du -sh pasta.

Checklist de um script agendado

  • Shebang #!/usr/bin/env bash e permissão de execução (chmod +x), ou chame com /usr/bin/bash script.sh.
  • Caminhos completos (ou export PATH=… no topo); nada depende da pasta atual.
  • Nada interativo: sem read, sem perguntas, sem cores (ou só com [[ -t 1 ]], veja Menus e Cores).
  • Saída e erros para um log com data (>> log 2>&1) ou para o journalctl.
  • set -euo pipefail, mensagens de erro claras e código de saída correto (Tratar Erros).
  • flock se duas execuções ao mesmo tempo puderem causar problema.
  • Teste com env -i antes de agendar.

Quando não funciona

Funciona no terminal, não faz nada no cron

O que aconteceu: quase sempre é o ambiente: um programa fora de /usr/bin:/bin, um caminho relativo, um % na linha, um alias.

Como confirmar: redirecione a saída para um log (>> ~/logs/teste.log 2>&1) e leia depois; ou rode o script com env -i HOME="$HOME" PATH=/usr/bin:/bin /bin/sh -c '…'.

Como resolver: caminhos completos, PATH no topo do script, \% na crontab.

"Permission denied" no log do cron

O que aconteceu: o script não tem permissão de execução, ou está numa pasta que o cron não consegue ler.

Como resolver: chmod +x ~/scripts/backup-docs.sh, ou chame com bash na frente: /usr/bin/bash /home/ana/scripts/backup-docs.sh.

Não sei se o cron rodou

Como confirmar (ilustrativo): o cron registra cada execução no log do sistema. Em distros com systemd: journalctl -u cron (Debian/Ubuntu) ou journalctl -u crond (Fedora). Em outras, grep CRON /var/log/syslog. Para timers: systemctl --user list-timers mostra a última e a próxima execução.

O comando da crontab foi cortado no meio

O que aconteceu: um % sem barra (comum em date +%F).

Como resolver: date +\%F, ou mova o comando para um script.

O timer não aparece em list-timers

O que aconteceu: faltou systemctl --user daemon-reload depois de criar os arquivos, ou faltou enable, ou os arquivos estão na pasta errada (precisam ficar em ~/.config/systemd/user/).

Como resolver: confira com systemd-analyze verify --user, depois daemon-reload e enable --now.

Exercícios

1. Todo dia às 7h

Complete os cinco campos para rodar o script todo dia às 7:00:

/home/ana/scripts/bom-dia.sh

2. A cada 10 minutos

Complete o primeiro campo:

* * * * /home/ana/scripts/checar.sh

3. Guardar saída e erros

Complete para acrescentar a saída e os erros ao log:

30 2 * * * /home/ana/scripts/backup.sh >> /home/ana/logs/backup.log

4. O que significa 0 8 * * 1-5?

5. Um script usa o comando meucomando, instalado em ~/bin. No terminal funciona; no cron, dá "not found". Por quê?

6. Para que serve o flock -n num script agendado?

Resumo

  • Cron: crontab -e, cinco campos (minuto, hora, dia, mês, dia da semana) + comando; *, ,, -, / e os atalhos @daily, @reboot…
  • O cron roda com sh, PATH=/usr/bin:/bin, sem .bashrc nem terminal; % precisa de \. Teste com env -i.
  • Sempre >> log 2>&1; use flock -n para não rodar duas vezes.
  • systemd: .service (o quê) + .timer (quando, OnCalendar=), systemctl --user enable --now, log no journalctl; systemd-run --on-active e at para uma vez só.
  • Um laço com sleep não é agendador: morre com o terminal e atrasa.
