Bash POSIX sh e Bashismos

O Bash não é o único shell. Existe um padrão, o POSIX sh, que todo sistema do tipo Unix segue, e há shells mais simples que só sabem esse padrão, como o dash, que é o /bin/sh do Debian e do Ubuntu. Um bashismo é um recurso que só o Bash tem. Nesta aula você aprende a reconhecer os bashismos, ver os erros que eles causam no sh e decidir quando vale a pena escrever um script portável.

Você vai aprender
  • O que é POSIX, e por que #!/bin/sh não quer dizer "Bash".
  • Os bashismos mais comuns e o equivalente POSIX de cada um, com os erros reais do dash.
  • Por que alguns bashismos não dão erro nenhum, só resultado errado.
  • Conferir um script com sh, shellcheck e checkbashisms; o que o bash --posix faz (e não faz).
  • O caso do macOS e quando escrever em POSIX ou em Bash.

Uma língua e seus sotaques

Pense no português: há a norma que todos entendem e há expressões regionais. Se você escreve só com a norma, qualquer pessoa entende. Se usa gírias locais, o texto fica mais expressivo, mas alguém de fora pode não entender.

O POSIX (Portable Operating System Interface) é a "norma": um padrão que define como um shell sh deve se comportar. Todo shell sério (Bash, dash, zsh, ksh, o ash do BusyBox) entende POSIX. O Bash aceita tudo do POSIX e acrescenta muitas "gírias": [[ ]], arrays, {1..5}, $'…'… Esses extras são os bashismos.

Quem é o /bin/sh na sua máquina?

Quando um script começa com #!/bin/sh, ou quando você roda sh script.sh, quem executa é o programa que estiver em /bin/sh. E isso muda de sistema para sistema:

$ readlink -f /bin/sh
/usr/bin/dash                      « na máquina da Ana: é o dash
Sistema/bin/sh é…Bashismo num #!/bin/sh…
Debian, Ubuntu, MintdashDá erro (ou resultado errado)
Fedora, RHEL, Archbash (em modo POSIX)Quase sempre funciona: o erro fica escondido até o script ir para um Debian
Alpine, contêineres pequenosash do BusyBoxDá erro (e o bash nem vem instalado)
macOSUm sh compatível com POSIX (por padrão, o Bash 3.2)Depende do recurso

O dash (Debian Almquist shell) é pequeno e rápido. O Debian o escolheu para o /bin/sh porque o sistema roda milhares de scripts de inicialização e de instalação de pacotes; um shell mais leve deixa tudo mais rápido. O seu terminal continua sendo o Bash: o dash só entra em cena para quem pede sh.

A consequência prática: um script com #!/bin/sh testado no Fedora (onde sh é o Bash) pode quebrar no Ubuntu. Por isso a regra deste guia é simples: se você usa recursos do Bash, escreva #!/usr/bin/env bash (veja Formas de Executar).

Um script com bashismos, rodado no sh

A Ana escreveu este script com #!/bin/sh no topo, mas com dois bashismos dentro:

#!/bin/sh
arquivo=${1:-frutas.txt}
if [[ ! -f $arquivo ]]; then
  echo "não achei $arquivo"
  exit 1
fi
total=$(wc -l < "$arquivo")
echo -e "Arquivo:\t$arquivo"
echo "Linhas: $total"

$ bash contar.sh
Arquivo:	frutas.txt
Linhas: 7
$ ./contar.sh                      « o #!/bin/sh manda para o dash
./contar.sh: 3: [[: not found
-e Arquivo:	frutas.txt
Linhas: 7
$ echo $?
0

Linha por linha do que o dash fez:

  • ./contar.sh: 3: [[: not found: as mensagens do dash são em inglês e têm o formato arquivo: linha: problema. Para ele, [[ é só o nome de um comando que não existe ("não encontrado").
  • O if recebeu o código 127 (comando não encontrado), entendeu "falso" e pulou o bloco. O script seguiu como se o arquivo existisse.
  • -e Arquivo:: o echo do dash não conhece a opção -e e imprimiu o -e como texto. (Ele já interpreta o \t sozinho, sem precisar de -e.)
  • O código de saída foi 0. Nada avisou que algo deu errado.

E o pior caso, com um arquivo que não existe:

$ sh contar.sh nada.txt
contar.sh: 3: [[: not found
contar.sh: 7: cannot open nada.txt: No such file
-e Arquivo:	nada.txt
Linhas:
$ echo $?
0

O teste que deveria parar o script não funcionou, e ele seguiu adiante com dados errados. Num script de backup ou de limpeza, é assim que acontecem os estragos.

A versão POSIX

#!/bin/sh
arquivo=${1:-frutas.txt}
if [ ! -f "$arquivo" ]; then
  echo "não achei $arquivo"
  exit 1
fi
total=$(wc -l < "$arquivo")
printf "Arquivo:\t%s\n" "$arquivo"
echo "Linhas: $total"
  • [[ ! -f $arquivo ]] → [ ! -f "$arquivo" ]: o [ é POSIX; nele, a variável precisa de aspas (veja Testes).
  • echo -e "…\t…" → printf "…\t%s\n" "…": o printf se comporta igual em todo shell (veja printf e echo).
  • ${1:-frutas.txt} e $( ) já eram POSIX: podem ficar.
$ sh contar2.sh
Arquivo:	frutas.txt
Linhas: 7

Missão: deixe o contar.sh portável: troque o [[ ]] por [ ] (com aspas na variável) e o echo -e por printf. A saída deve continuar mostrando Linhas: 7.

Os bashismos mais comuns, no dash

Cada sessão abaixo usa sh -c '…': "rode este trecho no sh". As mensagens começam com sh: 1: (o nome do shell e a linha 1 do trecho).

Testes: [[ ]] e ==

$ sh -c '[[ a == a ]] && echo sim'
sh: 1: [[: not found
$ sh -c '[ a == a ] && echo sim'
sh: 1: [: a: unexpected operator     « no [ do POSIX, a comparação é com um = só
$ sh -c '[ a = a ] && echo sim'
sim

Arrays

$ sh -c 'frutas=(banana uva); echo ${frutas[1]}'
sh: 1: Syntax error: "(" unexpected

O POSIX sh não tem arrays. A única lista que existe é a dos parâmetros posicionais: set -- banana uva; echo "$2" (veja Argumentos). Se o script precisa de arrays de verdade, é sinal de que ele deve ser em Bash.

Chaves, $'…' e echo -e

$ sh -c 'echo {1..5}'
{1..5}                             « sem erro: só não expandiu
$ sh -c 'echo -e "a\tb"'
-e a	b                          « o -e virou texto

O $'…' fica mais fácil de ver num arquivo de uma linha só, aspas.sh, com printf '[%s]\n' $'a\tb':

$ sh aspas.sh
[$a\tb]                           « o dash não entende $'…': sobraram o $ e o \t
$ bash aspas.sh
[a	b]                             « o Bash trocou o \t por um tab de verdade

Estes são os mais traiçoeiros: não dão erro. O resultado só sai diferente. No POSIX: seq 1 5 (ou um while com contador) no lugar de {1..5}; printf no lugar de $'…' e de echo -e.

function, local, source

$ sh -c 'function ola { echo oi; }; ola'
sh: 1: Syntax error: "}" unexpected
$ sh -c 'f() { local x=1; echo $x; }; f'
1                                  « o dash aceita local
$ sh -c 'source ./.profile && echo ok'
sh: 1: source: not found
$ sh -c '. ./.profile && echo ok'
ok
  • A palavra function é do Bash (e do ksh). A forma POSIX é ola() { …; }, que funciona nos dois.
  • local não está no POSIX, mas o dash, o ash e o Bash aceitam. É um bashismo "tolerado", que funciona na prática.
  • source é um apelido do Bash para o . (ponto), que é o comando POSIX.

Redirecionamentos: <<< e &>

$ sh -c 'tr a-z A-Z <<< oi'
sh: 1: Syntax error: redirection unexpected
$ sh -c 'echo oi | tr a-z A-Z'
OI

O &> é ainda pior: no dash, cmd &> arquivo é lido como cmd & (mandar para o segundo plano) seguido de > arquivo (um redirecionamento vazio). O comando roda em segundo plano, o erro aparece na tela e o código é 0:

ls nada &> /dev/null
echo "código: $?"
sleep 0.3

$ sh amb.sh
código: 0
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente

A forma POSIX é > /dev/null 2>&1 (veja Redirecionamento).

Expansões de parâmetro e contas

$ sh -c 'x=abc; echo ${x^^}'
sh: 1: Bad substitution
$ sh -c 'x=banana; echo ${x/an/AN}'
sh: 1: Bad substitution
$ sh -c 'x=banana; echo ${x:1:3}'
sh: 1: Bad substitution
$ sh -c 'echo $((2+3))'
5                                  « a conta $(( )) é POSIX
$ sh -c 'let x=1+1; echo $x'
sh: 1: let: not found
$ sh -c 'for ((i=0;i<2;i++)); do echo $i; done'
sh: 1: Syntax error: Bad for loop variable
$ sh -c 'echo $RANDOM'
                                   « vazio: não existe no POSIX

Do ${ }, o POSIX tem ${x:-padrão}, ${x:=…}, ${x:?…}, ${x:+…}, ${#x} e os cortes ${x#…}, ${x##…}, ${x%…}, ${x%%…}. Substituição (/), fatias (:1:3) e maiúsculas (^^, ,,) são do Bash (veja Expansão de Parâmetros).

Ferramentas para encontrar bashismos

Rodar no sh de verdade

No Debian/Ubuntu, sh script.sh é o teste mais honesto: é o dash que roda. Se você está num Fedora ou Arch, instale o pacote dash e rode dash script.sh.

bash --posix não é um detector

O modo POSIX do Bash (bash --posix ou set -o posix, veja Opções do Shell) muda alguns comportamentos para seguir o padrão, mas continua aceitando os bashismos. É também o que acontece quando o Bash é chamado com o nome sh, como no Fedora:

$ bash --posix -c 'frutas=(a b); echo ${frutas[1]}; [[ a == a ]] && echo sim'
b
sim                                « arrays e [[ ]] funcionaram mesmo no modo POSIX

Por isso um script com #!/bin/sh "testado" num sistema onde sh é o Bash não está testado de verdade.

ShellCheck com #!/bin/sh

O ShellCheck lê a primeira linha. Com #!/bin/sh, ele confere o script contra o POSIX e aponta cada bashismo, com um código SC3xxx:

$ shellcheck contar.sh

In contar.sh line 3:
if [[ ! -f $arquivo ]]; then
   ^-----------------^ SC3010 (warning): In POSIX sh, [[ ]] is undefined.


In contar.sh line 8:
echo -e "Arquivo:\t$arquivo"
     ^-- SC3037 (warning): In POSIX sh, echo flags are undefined.

For more information:
  https://www.shellcheck.net/wiki/SC3010 -- In POSIX sh, [[ ]] is undefined.
  https://www.shellcheck.net/wiki/SC3037 -- In POSIX sh, echo flags are undef...
$ shellcheck contar2.sh
$ echo $?
0                                  « a versão POSIX passou sem avisos

Se o script é para Bash, a correção é a primeira linha (#!/usr/bin/env bash), e não reescrever tudo. Para conferir um arquivo sem shebang, diga o shell: shellcheck -s sh arquivo.

checkbashisms programa à parte

O Debian tem um verificador próprio, o checkbashisms, no pacote devscripts. Ele não está no laboratório do guia, por isso aqui fica só o uso (ilustrativo): checkbashisms contar.sh lista cada linha com um bashismo, como o ShellCheck faz com os SC3xxx.

O caso do macOS

No macOS, a portabilidade vai além do shell. Os pontos que mais quebram scripts feitos no Linux (ilustrativo: o laboratório do guia é Linux):

DiferençaNo Linux (GNU)No macOS
Bash do sistema5.2 ou 5.3/bin/bash 3.2: sem declare -A, mapfile, ${x,,}, |&, ;&, globstar (veja Novidades)
Shell padrão do terminalbashzsh (desde o macOS 10.15)
sed -ised -i 's/a/b/' arqsed -i '' 's/a/b/' arq (o -i exige um sufixo de backup, mesmo vazio)

O Bash é o menor problema: dá para instalar um Bash novo pelo Homebrew e usar #!/usr/bin/env bash, que acha o Bash do Homebrew pelo PATH. As ferramentas BSD são o maior: um script portável para macOS evita opções exclusivas do GNU ou testa o sistema com uname.

Quando escrever POSIX, quando escrever Bash

SituaçãoEscreva emPrimeira linha
Script pessoal, de automação, de projeto, onde o Bash está instaladoBash: aproveite arrays, [[ ]], local…#!/usr/bin/env bash
Script de instalação que pode rodar em qualquer Unix (inclusive Alpine, BSD)POSIX#!/bin/sh
Scripts do sistema no Debian (pacotes, inicialização)POSIX (é a regra do Debian)#!/bin/sh
Imagens Docker mínimasPOSIX (o bash pode nem existir)#!/bin/sh

O erro não é usar bashismos. O erro é usar bashismos com #!/bin/sh. Escolha um dos dois e seja coerente; o ShellCheck confere por você.

Quando não funciona

"[[: not found" ou "Syntax error: "(" unexpected" 
$ ./contar.sh
./contar.sh: 3: [[: not found

O que aconteceu: o script tem bashismos, mas foi rodado pelo dash, por causa do #!/bin/sh ou porque você digitou sh script.sh.

Como confirmar: head -1 script.sh. Mensagens em inglês com arquivo: número: no começo são do dash; as do Bash vêm em português com "linha N".

Como resolver: troque a primeira linha para #!/usr/bin/env bash e rode com ./script.sh ou bash script.sh; ou reescreva em POSIX seguindo a tabela.

"Bad substitution" 
$ sh -c 'x=abc; echo ${x^^}'
sh: 1: Bad substitution

O que aconteceu: uma expansão ${ } que só o Bash conhece. Como resolver: use Bash, ou troque por tr/sed/cut.

Funciona no Fedora e quebra no Ubuntu

O que aconteceu: no Fedora, /bin/sh é o Bash e aceitou os bashismos; no Ubuntu, é o dash.

Como resolver: rode shellcheck (ele usa a primeira linha) e teste com dash script.sh antes de distribuir.

Não deu erro, mas apareceu "-e" ou "{1..5}" na saída

O que aconteceu: bashismos que o dash não entende, mas também não rejeita: echo -e, {1..5}, $'…', $RANDOM, &>.

Como resolver: printf, seq, > arq 2>&1; ou mude para Bash.

Resumo

  • POSIX sh é o padrão comum; bashismos são os extras do Bash. No Debian/Ubuntu, /bin/sh é o dash; no Fedora/Arch, o Bash.
  • Os bashismos mais comuns: [[ ]], == no [, arrays, {1..5}, $'…', echo -e, function, source, <<<, &>, ${x/a/b}.
  • Alguns dão erro; outros (echo -e, {1..5}, &>) só dão resultado errado, com código 0.
  • Teste com sh/dash e com shellcheck; bash --posix não detecta bashismos.
  • Usou recursos do Bash? #!/usr/bin/env bash. Precisa rodar em qualquer lugar? POSIX e #!/bin/sh.
