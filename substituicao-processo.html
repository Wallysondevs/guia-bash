Bash Substituição de Processo

Alguns comandos só aceitam nomes de arquivo: o diff quer dois, o paste quer vários. Mas às vezes o que você quer comparar é a saída de dois comandos. A substituição de processo, <(comando), faz a saída de um comando parecer um arquivo. Sem arquivo temporário, sem faxina depois.

Você vai aprender
  • O que é <(comando) e por que echo <(true) mostra /dev/fd/63.
  • Comparar e juntar saídas de comandos com diff, comm e paste.
  • Ler linhas com while read … done < <(comando) sem perder as variáveis.
  • Mandar a mesma saída para vários comandos com tee >(…) >(…).
  • Quando ela não funciona (sh, variáveis, ordem das saídas) e quando usar pipe ou arquivo temporário.

O problema: comparar duas saídas

A professora da Ana tem a lista oficial da turma em Documentos/alunos.csv e uma lista de chamada que ela digitou, chamada.txt. Ela quer saber quem está numa lista e não está na outra. O diff compara dois arquivos. Só que a lista oficial precisa ser tratada antes: tirar o cabeçalho (tail -n +2), pegar só o nome (cut -d, -f1) e ordenar (sort).

O jeito "à moda antiga" é gravar cada saída num arquivo temporário, comparar e apagar:

Para acompanhar, crie a lista de chamada (ela tem um aluno a mais, o Fabio):

$ printf 'Ana\nBruno\nCarla\nDiego\nElisa\nFabio\n' > chamada.txt
$ tail -n +2 alunos.csv | cut -d, -f1 | sort > /tmp/oficial.txt
$ sort chamada.txt > /tmp/chamada.txt
$ diff /tmp/oficial.txt /tmp/chamada.txt
5a6
> Fabio
$ rm /tmp/oficial.txt /tmp/chamada.txt

Funciona, mas são quatro comandos, dois arquivos para inventar nome e um rm que é fácil esquecer. Com a substituição de processo, é uma linha só:

$ diff <(tail -n +2 alunos.csv | cut -d, -f1 | sort) <(sort chamada.txt)
5a6
> Fabio

Antes de entender essa linha, vamos ver o que o <( ) realmente é.

O que é <(comando)

O nome em inglês é process substitution: o Bash substitui o trecho <(comando) por um nome de arquivo. Atrás desse nome há um cano (um pipe) ligado à saída do comando. Quem abrir esse "arquivo" e ler vai receber o que o comando escreveu.

A melhor forma de ver isso é pedir ao echo para mostrar a palavra depois da substituição:

$ echo <(true)
/dev/fd/63                          « o <(true) virou um nome de arquivo
$ echo <(true) <(true)
/dev/fd/63 /dev/fd/62               « cada <( ) ganha o seu
$ ls -l <(true)
lr-x------ 1 ana ana 64 out 16 09:46 /dev/fd/63 -> pipe:[115729]

Leia a saída assim:

  • /dev/fd/63 quer dizer "o descritor de arquivo número 63 deste processo". fd vem de file descriptor. Os números 0, 1 e 2 você já conhece (entrada, saída e erro); o Bash usa números altos, a partir de 63 e descendo, para não colidir com os seus. Veja Descritores de Arquivo.
  • O ls -l mostra que esse "arquivo" é um link para pipe:[115729]: um cano anônimo, o mesmo tipo de cano que o | cria. O número entre colchetes muda a cada vez.
  • O echo não lê o arquivo, só imprime o nome. Para ver o conteúdo, alguém tem que abrir e ler:
$ cat <(echo "olá de dentro")
olá de dentro
cat
Um comando que recebe nomes de arquivo como argumento.
<(
Abre a substituição de processo. O < e o ( ficam colados, sem espaço.
echo "olá de dentro"
O comando que roda "por trás", em paralelo. A saída dele vai para o cano.
)
Fecha. No lugar de tudo isso, o cat recebe /dev/fd/63.

O cat nunca viu os parênteses: para ele, foi chamado como cat /dev/fd/63. O comando de dentro roda num subshell, ao mesmo tempo que o cat.

Arquivo com nome × entrada sem nome

Repare na diferença entre passar o "arquivo" como argumento e redirecionar a entrada:

$ wc -l <(sort frutas.txt)
7 /dev/fd/63                        « o wc recebeu um NOME (e mostra esse nome)
$ wc -l < <(sort frutas.txt)
7                                   « o wc recebeu só o conteúdo pela entrada

A segunda forma junta duas coisas: o < de sempre (redirecionar a entrada) e, depois de um espaço, o <(…). Ela vai ser a chave do while read, mais abaixo.

Comparar saídas: diff <( ) <( )

Agora a linha da professora, por partes:

diff
Compara dois arquivos linha a linha e mostra o que muda do primeiro para o segundo.
<(tail -n +2 alunos.csv | cut -d, -f1 | sort)
Primeiro "arquivo": os nomes da lista oficial, sem o cabeçalho, em ordem. Dentro do <( ) cabe um pipe inteiro.
<(sort chamada.txt)
Segundo "arquivo": a chamada em ordem. O diff só funciona bem com as duas listas ordenadas do mesmo jeito.
$ cat chamada.txt
Ana
Bruno
Carla
Diego
Elisa
Fabio
$ diff <(tail -n +2 alunos.csv | cut -d, -f1 | sort) <(sort chamada.txt)
5a6                                 « depois da linha 5 do 1º, acrescente (a) a linha 6 do 2º
> Fabio                             « > = está só no segundo "arquivo"
$ echo $?
1                                   « 1 = os arquivos são diferentes

O diff não sabe que leu de comandos: ele simplesmente abriu /dev/fd/63 e /dev/fd/62. Os códigos de saída do diff são: 0 iguais, 1 diferentes, 2 deu erro. Isso permite usar a comparação num if ou com && e ||:

$ diff <(sort frutas.txt) <(sort -u frutas.txt) > /dev/null && echo iguais || echo diferentes
diferentes
$ cmp <(sort frutas.txt) <(sort frutas.txt) && echo "mesmo conteúdo"
mesmo conteúdo

No primeiro, a lista com repetições (sort) é comparada com a lista sem repetições (sort -u); o > /dev/null esconde o relatório e só o código de saída importa. O cmp é um comparador mais simples: não diz o que mudou, só se mudou.

Só o que difere: comm

O comm (de common, "em comum") também quer dois arquivos ordenados. Ele mostra três colunas: só no 1º, só no 2º, nos dois. A opção -3 esconde a terceira coluna, a dos nomes em comum:

$ comm -3 <(tail -n +2 alunos.csv | cut -d, -f1 | sort) <(sort chamada.txt)
	Fabio                           « o TAB na frente = 2ª coluna (só na chamada)

Juntar colunas: paste <( ) <( )

O paste cola arquivos lado a lado, linha 1 com linha 1, linha 2 com linha 2. Com substituição de processo você monta uma tabela a partir de pedaços de outros comandos:

$ paste <(cut -d, -f1 alunos.csv) <(cut -d, -f4 alunos.csv)
nome	nota
Ana	9.5
Bruno	7.0
Carla	8.5
Diego	6.0
Elisa	10.0
$ paste -d' ' <(seq 3) <(printf 'a\nb\nc\n')
1 a
2 b
3 c

A primeira tabela pegou a coluna 1 (nome) e a 4 (nota) e juntou com TAB, o separador padrão do paste. Na segunda, -d' ' troca o separador por um espaço.

Ler linhas sem perder as variáveis: done < <(comando)

Este é o uso mais comum em scripts. Quer contar quantas linhas um comando produz, guardando o total numa variável? A primeira ideia é um pipe para o while. Veja o que acontece:

$ total=0
$ cat frutas.txt | while read -r f; do total=$((total+1)); done
$ echo "total: $total"
total: 0                            « contou 7 vezes… e o total sumiu!

Por quê? Cada lado de um pipe roda num subshell, uma cópia do shell. O while somou na cópia, e a cópia morreu no fim do pipe. O total do seu shell continuou 0.

Com a substituição de processo, quem roda em paralelo é o comando que produz as linhas; o while fica no shell atual:

$ total=0
$ while read -r f; do total=$((total+1)); done < <(cat frutas.txt)
$ echo "total: $total"
total: 7                            « agora sim
while read -r f; do …; done
O laço que lê uma linha por volta (veja Ler Arquivos Linha a Linha). Roda no shell atual.
<
Redireciona a entrada do laço inteiro…
<(cat frutas.txt)
…para o "arquivo" ligado à saída do comando. Entre os dois < há um espaço obrigatório.

Para ler uma linha só, a mesma ideia funciona com read sozinho:

$ read -r primeira < <(sort frutas.txt)
$ echo "$primeira"
banana
Outras saídas para o mesmo problema

Se a lista vem de um arquivo, basta done < arquivo. Se vem de uma variável, use uma here-string: done <<< "$texto" (veja Here-docs e Here-strings). E em scripts dá para pedir ao Bash que rode o último comando do pipe no shell atual, com shopt -s lastpipe (veja Subshells e Grupos).

O outro sentido: >(comando)

O >(comando) também vira um nome de arquivo, mas ao contrário: quem escrever nele está mandando texto para a entrada do comando. Ele brilha com o tee, que copia a entrada para vários arquivos ao mesmo tempo (veja Pipes).

A Ana quer, numa passada só, guardar a lista ordenada compactada e saber quantas linhas ela tem:

$ sort frutas.txt | tee >(gzip > frutas.gz) >(wc -l) > /dev/null
7
$ ls -l frutas.gz
-rw-rw-r-- 1 ana ana 48 out 16 09:46 frutas.gz
$ zcat frutas.gz
banana
banana
banana
laranja
maçã
maçã
uva
sort frutas.txt |
Produz a lista ordenada e manda para o tee.
tee
Copia o que recebe para cada arquivo dado e também para a saída.
>(gzip > frutas.gz)
1º "arquivo": a entrada do gzip, que compacta e grava em frutas.gz.
>(wc -l)
2º "arquivo": a entrada do wc -l, que conta e escreve 7 na tela.
> /dev/null
A saída normal do tee não interessa aqui: vai para o lixo.

O 7 na tela veio do wc -l; o frutas.gz tem 48 bytes, e o zcat (o cat que descompacta) prova que a lista está lá dentro.

Cuidado: o comando de dentro corre em paralelo

O Bash não espera o comando de um >(…) terminar. Ele dispara o processo e segue em frente. Num terminal de verdade, isso pode fazer a saída aparecer depois do prompt:

$ echo "fim" > >(sleep 1; cat)
$ fim                                « não é um comando: o prompt voltou e o "fim" chegou 1 s depois, grudado nele

$ echo "fim" > >(sleep 1; cat); wait $!
fim                                  « com wait $!, o Bash espera o processo
$ echo pronto
pronto

O $! guarda o número (PID) do último processo lançado em segundo plano, e uma substituição de processo conta como tal. O wait $! espera por ele (veja Jobs). Em scripts, isso importa quando a linha seguinte usa o resultado do >( ), por exemplo lendo o arquivo que ele gravou:

$ seq 5 | tee >(wc -l > linhas.txt) | tail -n 1
5
$ cat linhas.txt
5                                   « deu tempo aqui, mas não há garantia

Nesse caso o wc é rápido e o arquivo já estava pronto. Com um comando lento, o cat linhas.txt poderia ler o arquivo vazio. Na dúvida: wait $! antes de usar o resultado.

Formas diferentes de ligar comandos

FormaExemploVantagensLimites
Pipe |sort a | uniq -cSimples, funciona em qualquer shell (POSIX).Só uma entrada por comando; o lado direito roda em subshell (variáveis se perdem).
<(cmd)diff <(sort a) <(sort b)Várias "entradas" com nome; sem arquivo para apagar.Só no Bash/zsh/ksh; o "arquivo" só pode ser lido uma vez, do começo ao fim.
< <(cmd)while read …; done < <(cmd)O laço fica no shell atual: as variáveis sobrevivem.Só no Bash; o código de saída de cmd se perde.
>(cmd)tee >(gzip > x.gz) >(wc -l)Uma saída alimentando vários comandos.Roda em paralelo: a ordem das saídas não é garantida.
Arquivo temporáriot=$(mktemp); sort a > "$t"Pode ser lido várias vezes, em qualquer ordem; funciona no sh.Precisa apagar (rm, de preferência num trap); ocupa disco.

Qual usar? Uma entrada só, de um comando para outro: pipe. O comando quer nomes de arquivo e você tem saídas de comandos: <( ). Laço que precisa guardar variáveis: done < <( ). O programa precisa ler o arquivo mais de uma vez, ou o script tem que rodar no sh: arquivo temporário.

Quando não funciona

Syntax error: "(" unexpected 
$ sh compara.sh
compara.sh: 2: Syntax error: "(" unexpected
$ echo $?
2

O que aconteceu: o script usa <( ), mas foi rodado com sh. No Debian e no Ubuntu, sh é o dash, que segue o padrão POSIX e não conhece substituição de processo. O formato da mensagem (arquivo: linha: …, em inglês) já entrega que não foi o Bash.

Como resolver: rode com bash compara.sh, ou dê permissão e rode ./compara.sh com a primeira linha #!/usr/bin/env bash (veja Formas de Executar). Se o script precisa ser POSIX, troque por arquivos temporários (veja POSIX sh e Bashismos).

erro de sintaxe próximo ao token inesperado 
$ while read -r l; do echo "$l"; done <<(echo a)
bash: erro de sintaxe próximo ao token inesperado `('
$ while read -r l; do echo "$l"; done < < (echo a)
bash: erro de sintaxe próximo ao token inesperado `<'

O que aconteceu: no primeiro, os dois < colados viraram <<, o começo de um here-doc. No segundo, sobrou um espaço entre < e (, então o <( deixou de existir.

Como resolver: a regra é espaço entre os dois <, nenhum espaço entre < e (: done < <(echo a).

"/dev/fd/63: Arquivo ou diretório inexistente" 
$ arq=<(echo oi)
$ echo $arq
/dev/fd/63
$ cat $arq
cat: /dev/fd/63: Arquivo ou diretório inexistente

O que aconteceu: o cano só existe durante o comando em que o <( ) aparece. Guardado numa variável, sobrou só o nome; quando o cat rodou, o descritor 63 já tinha sido fechado.

Como resolver: use o <( ) direto no comando que vai ler: cat <(echo oi). Se precisa do conteúdo mais tarde, guarde o texto (txt=$(echo oi), veja Substituição de Comando) ou grave um arquivo de verdade.

O comando de dentro falhou, mas $? é 0 
$ cat <(ls nada)
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente
$ echo $?
0                                   « é o código do cat, não do ls
$ wait $!; echo $?
2                                   « este sim é o código do ls

O que aconteceu: o $? é sempre do comando de fora. O cat leu um "arquivo" vazio e terminou bem. Nem o set -e nem o pipefail enxergam o erro do comando de dentro.

Como confirmar e resolver: logo depois, wait $! devolve o código do último <( )/>( ) lançado, como acima. Quando o erro importa de verdade, gere a saída antes (lista=$(ls nada) || exit 1) ou use um arquivo temporário e confira cada passo.

A saída aparece embaralhada ou depois do prompt

O que aconteceu: o comando dentro de >( ) roda em paralelo, e o Bash não o espera. Com vários >( ), cada um escreve quando termina.

Como resolver: mande cada >( ) para um arquivo próprio (>(wc -l > linhas.txt)) e, antes de usar os resultados, wait $! (espera o último) ou um sleep curto só para testes. Para muitos processos em paralelo, veja Rodar em Paralelo.

Resumo

  • <(cmd) é trocado por um nome de arquivo (/dev/fd/63…) ligado à saída de cmd; >(cmd), a um arquivo que alimenta a entrada de cmd.
  • Use quando um comando quer nomes de arquivo: diff, comm, paste, tee.
  • while read …; done < <(cmd) mantém o laço no shell atual, e as variáveis sobrevivem. Espaço entre os <, nenhum antes do (.
  • O comando de dentro roda em paralelo: o $? não é dele, e a ordem das saídas não é garantida (wait $! ajuda).
  • É recurso do Bash: no sh/dash dá Syntax error. Lá, use arquivos temporários.
