Bash Tratar Erros

O modo estrito para o script quando algo dá errado, mas em silêncio e às vezes no lugar errado. Tratar erros é decidir, em cada passo importante, o que fazer quando ele falha: avisar com uma mensagem clara, devolver um código que diga o que houve e sair sem deixar sujeira. É isso que separa um script "que funciona na minha máquina" de uma ferramenta de verdade.

Você vai aprender
  • Três jeitos de checar se um comando deu certo: if, || e $?, e qual usar.
  • A escrever mensagens de erro do jeito certo: na saída de erro (>&2), com o nome do script.
  • A criar uma função erro e usar códigos de saída que significam algo.
  • A validar tudo antes de começar: argumentos, arquivos e programas necessários (command -v).
  • A ler o código de cada parte de um pipe com PIPESTATUS.

O problema: o script mente

A Ana fez um script para guardar uma cópia de um arquivo na pasta ~/backup:

#!/usr/bin/env bash
cp "$1" ~/backup/
echo "Cópia feita!"

Ela ainda não criou a pasta backup. Veja:

$ bash copia.sh frutas.txt
cp: não foi possível criar arquivo comum '/home/ana/backup/': Não é um diretório
Cópia feita!                                   « mentira: nada foi copiado
$ echo $?
0                                              « e o código diz "sucesso"

Duas mentiras: a tela diz "Cópia feita!" e o código de saída diz 0. Se esse script rodasse sozinho toda noite, a Ana só descobriria o problema no dia em que precisasse do backup. Tratar o erro é fazer o script dizer a verdade.

Checar o código de saída com if

Todo comando devolve um número ao terminar: 0 é sucesso, qualquer outro é falha. O if testa exatamente esse número: ele roda o comando e escolhe o caminho pelo resultado.

#!/usr/bin/env bash
if cp "$1" ~/backup/; then
  echo "Cópia feita!"
else
  echo "A cópia falhou." >&2
  exit 1
fi
if cp "$1" ~/backup/; then
Roda o cp. Código 0 → executa o bloco do then.
else
Qualquer outro código → executa este bloco.
echo "…" >&2
Escreve a mensagem na saída de erro (canal 2), e não na saída normal. Explicado logo abaixo.
exit 1
Termina o script com o código 1, avisando quem chamou que deu errado.
$ bash copia2.sh frutas.txt
cp: não foi possível criar arquivo comum '/home/ana/backup/': Não é um diretório
A cópia falhou.
$ echo $?
1                                              « agora o código conta a verdade

Repare que não usamos [ ]: o if não precisa de colchetes para testar um comando. Os colchetes são só mais um comando, o test, usado para comparar textos e números.

Mensagens de erro vão para a saída de erro (>&2)

Todo programa tem dois canais de saída (veja Redirecionamento): o 1 (stdout), para o resultado, e o 2 (stderr), para avisos e erros. Os dois aparecem na tela, mas quem usa o seu script pode separá-los. O >&2 quer dizer "mande a saída deste comando para onde o canal 2 aponta".

>
Redirecionar a saída (canal 1)…
&2
…para o canal 2. O & diz que 2 é um canal, e não um arquivo chamado "2".

Por que isso importa? Porque quem redireciona a saída do seu script espera receber só o resultado. Os erros precisam continuar visíveis, ou poder ser descartados à parte:

$ bash copia2.sh frutas.txt 2>/dev/null      « joga fora o canal 2
$ echo $?
1                                              « nenhuma mensagem, mas o código continua lá

Com 2>/dev/null, tanto a mensagem do cp quanto a nossa sumiram, porque as duas foram para o canal 2. Se a nossa mensagem tivesse ido para o canal 1, ela teria "vazado" para dentro de um arquivo de resultado ou de um pipe, misturada aos dados.

Regra prática

Resultado (o que outro programa vai ler) → canal 1, echo normal. Tudo o mais (erros, avisos, "processando…", mensagem de uso pedida por engano) → canal 2, >&2. A exceção é a ajuda pedida de propósito (-h): aí ela é o resultado e vai para o canal 1.

A forma curta: cmd || { …; exit 1; }

Escrever if/else para cada comando deixa o script comprido. A forma mais usada é o || ("ou"): "rode o cp; se falhar, rode o bloco".

#!/usr/bin/env bash
cp "$1" ~/backup/ || { echo "copia3.sh: a cópia falhou" >&2; exit 1; }
echo "Cópia feita!"
cp "$1" ~/backup/
O comando que pode falhar.
||
"Se o da esquerda falhar (código diferente de 0), rode o da direita."
{ … ; }
Um grupo: junta vários comandos para que todos dependam do ||. Precisa de espaço depois do { e de ; antes do }.
exit 1
Sai do script inteiro, porque o grupo { } roda no próprio shell.
$ mkdir ~/backup
$ bash copia3.sh frutas.txt
Cópia feita!
$ bash copia3.sh nada.txt
cp: não foi possível obter estado de 'nada.txt': Arquivo ou diretório inexistente
copia3.sh: a cópia falhou
$ echo $?
1

Na primeira vez, o cp funcionou e o bloco nem rodou. Na segunda, o arquivo não existia: o cp deu a mensagem dele, o nosso bloco deu a nossa, e o script saiu com 1.

Chaves, não parênteses; e não esqueça as chaves

cmd || echo "falhou" >&2; exit 1 (sem chaves) sai sempre, porque o ; separa: o exit 1 não depende do ||. E cmd || ( echo "falhou"; exit 1 ) (com parênteses) nunca sai do script, porque ( ) cria um subshell e o exit encerra só ele. Os dois casos estão em "Quando não funciona".

Uma função erro para não repetir

Quando o script tem muitos pontos de falha, a mensagem e o exit se repetem. Crie uma função que faz as duas coisas. Ela costuma se chamar die ("morra", em inglês) ou, em português, erro:

readonly PROG=${0##*/}

erro() {
  printf '%s: erro: %s\n' "$PROG" "$1" >&2
  exit "${2:-1}"
}

cp -- "$arquivo" ~/backup/ || erro "a cópia de '$arquivo' falhou" 74
${0##*/}
$0 é o caminho usado para chamar o script (./guardar.sh, /home/ana/guardar.sh…). O ##*/ apaga tudo até a última barra e sobra só o nome: guardar.sh. Veja Expansão de Parâmetros.
readonly PROG=…
Uma constante: ninguém consegue mudar PROG depois.
printf '%s: erro: %s\n'
Formato nome: erro: mensagem, o mesmo padrão dos comandos do sistema (cp: …, ls: …). printf é mais previsível que echo com textos variáveis.
"$1"
A mensagem, primeiro argumento da função.
>&2
Tudo para o canal de erro.
exit "${2:-1}"
Sai com o código do segundo argumento; se ele não veio, com 1.

Começar a mensagem com o nome do script é importante quando ele roda junto com outros (num pipe, no cron, dentro de outro script): você sabe quem reclamou.

Códigos de saída que significam algo

O código de saída é um número de 0 a 255. Para quem chama o script, ele é a única informação garantida sobre o que aconteceu. Alguns valores já têm significado combinado:

CódigoSignificadoQuem usa
0Sucesso.Todos.
1Erro genérico.A maioria dos comandos. Também "não achei" no grep, "diferentes" no diff.
2Uso errado (opção ou argumento inválido).Comandos internos do Bash, grep, ls…
64–78Erros específicos do padrão sysexits: 64 uso, 65 dados ruins, 66 arquivo de entrada não existe, 69 serviço/programa indisponível, 70 erro interno, 73 não conseguiu criar, 74 erro de E/S, 77 sem permissão, 78 configuração.Programas que querem ser bem específicos. Opcional, mas útil.
126Achou o comando, mas não pôde executá-lo (sem permissão x).O Bash.
127Comando não encontrado.O Bash.
128+NMorto pelo sinal N: 130 = Ctrl+C (INT, 2), 137 = KILL (9), 141 = PIPE (13), 143 = TERM (15).O Bash. Veja trap e Sinais.
255Código fora da faixa (exit -1).Evite: ssh usa 255 para "a conexão falhou".
$ programa-que-nao-existe
bash: programa-que-nao-existe: comando não encontrado
$ echo $?
127
$ chmod -x guardar.sh
$ ./guardar.sh frutas.txt
bash: ./guardar.sh: Permissão negada
$ echo $?
126
$ bash -c 'exit 300'; echo $?
44                                             « 300 não cabe: o Bash usa o resto da divisão por 256
$ bash -c 'exit 256'; echo $?
0                                              « 256 vira 0: um "sucesso" acidental!

Na prática: 0 para sucesso, 1 para erro geral e 2 para uso errado já é um ótimo começo. Se quiser distinguir mais casos, use a faixa 64–78 e documente na ajuda do script. Nunca use valores acima de 125, que se confundem com os do próprio Bash.

Validar antes de começar

O melhor erro é o que aparece antes de o script mexer em qualquer coisa. Confira três coisas logo no início:

1. Os argumentos

$# é quantos argumentos vieram. Se for diferente do esperado, mostre como usar o script e saia com 2:

uso() {
  printf 'Uso: %s ARQUIVO\n' "$PROG"
  printf 'Guarda uma cópia de ARQUIVO em %s.\n' "$DESTINO"
}

if [[ $# -ne 1 ]]; then
  uso >&2
  exit 2
fi

2. Os arquivos

Os testes de arquivo dizem se o caminho existe e o que você pode fazer com ele. Teste do mais geral ao mais específico, para a mensagem ser exata:

TesteVerdadeiro quando…Mensagem típica
[[ -e $a ]]existe (qualquer tipo)"não existe"
[[ -f $a ]]é um arquivo comum"não é um arquivo comum"
[[ -d $a ]]é uma pasta"não é uma pasta"
[[ -r $a ]] / -w / -xvocê pode ler / escrever / executar"sem permissão para ler"
[[ -s $a ]]existe e não está vazio"está vazio"

3. Os programas de que o script precisa

Se o script usa um programa que pode não estar instalado, confira com command -v. Ele mostra onde o comando está e devolve 0; se não achar, não mostra nada e devolve 1:

$ command -v cp
/usr/bin/cp
$ command -v ls
alias ls='ls --color=auto'                     « no terminal, aliases também contam
$ command -v convert
$ echo $?
1                                              « não está instalado
command
Comando interno que roda ou descreve outros comandos, ignorando funções.
-v
"Diga onde está" (verbose), sem executar.
#!/usr/bin/env bash
for programa in convert zip; do
  if ! command -v "$programa" > /dev/null; then
    echo "fotos.sh: erro: este script precisa do '$programa'." >&2
    echo "Instale-o (no Debian/Ubuntu: sudo apt install imagemagick) e tente de novo." >&2
    exit 69
  fi
done
echo "tudo pronto"

$ bash fotos.sh
fotos.sh: erro: este script precisa do 'convert'.
Instale-o (no Debian/Ubuntu: sudo apt install imagemagick) e tente de novo.
$ echo $?
69
Por que não which?

which é um programa externo, que não existe em todo sistema e se comporta diferente em cada um. command -v é do próprio Bash (e do POSIX), sempre está lá e enxerga funções e comandos internos. Para ter só o caminho de um programa, há também type -P zip. Veja PATH.

O script completo: guardar.sh

Juntando tudo o que vimos, eis a versão profissional do script da Ana:

#!/usr/bin/env bash
# guardar.sh — guarda uma cópia de ARQUIVO em ~/backup
set -euo pipefail

readonly PROG=${0##*/}
readonly DESTINO=~/backup

erro() {
  printf '%s: erro: %s\n' "$PROG" "$1" >&2
  exit "${2:-1}"
}

uso() {
  printf 'Uso: %s ARQUIVO\n' "$PROG"
  printf 'Guarda uma cópia de ARQUIVO em %s.\n' "$DESTINO"
}

# 1. Validar os argumentos
if [[ $# -ne 1 ]]; then
  uso >&2
  exit 2
fi
arquivo=$1

# 2. Validar o arquivo
[[ -e $arquivo ]] || erro "'$arquivo' não existe" 66
[[ -f $arquivo ]] || erro "'$arquivo' não é um arquivo comum" 66
[[ -r $arquivo ]] || erro "sem permissão para ler '$arquivo'" 77

# 3. Fazer o trabalho, checando cada passo
mkdir -p -- "$DESTINO" || erro "não consegui criar $DESTINO" 73
cp -- "$arquivo" "$DESTINO/" || erro "a cópia de '$arquivo' falhou" 74
echo "Guardado: $DESTINO/${arquivo##*/}"

Passo 3Cada comando que pode falhar tem um || erro. O -- protege contra nomes que começam com - (veja Boas Práticas).

if ! cmd, $? ou ||: qual usar?

Às vezes você só quer agir quando dá errado. O ! na frente de um comando inverte o resultado: 0 vira 1 e qualquer falha vira 0.

#!/usr/bin/env bash
if ! grep -q kiwi frutas.txt; then
  echo "não tem kiwi (\$? aqui vale $?)"
fi
grep -q kiwi frutas.txt
status=$?
echo "o grep devolveu $status"

$ bash negacao.sh
não tem kiwi ($? aqui vale 0)                  « o $? é o resultado do "!", já invertido
o grep devolveu 1                              « para ter o código real, guarde-o logo depois

A primeira linha mostra uma pegadinha: dentro do then, $? é o resultado do ! grep (0), e não o do grep (1). Se você precisa do código exato (por exemplo, para separar "não achei" = 1 de "arquivo não existe" = 2 no grep), guarde $? numa variável na linha seguinte, antes que outro comando o sobrescreva.

FormaExemploQuando usar
if cmd; then … else … fiif cp a b; then echo ok; else …; fiHá algo a fazer nos dois casos.
if ! cmd; then … fiif ! command -v zip >/dev/null; thenSó o caso de erro importa e ele tem várias linhas.
cmd || erro "…"cd "$d" || erro "sem $d"O mais comum: uma linha por passo.
cmd || truerm -f tmp || trueA falha é aceitável (com set -e ligado).
cmd; s=$? + casegrep -q x a; s=$?Precisa distinguir códigos diferentes (1 × 2). Com set -e, escreva s=0; cmd || s=$?.
cmd; if [ $? -ne 0 ]—Evite: mais longo, frágil (qualquer linha no meio estraga) e não funciona com set -e. O ShellCheck avisa (SC2181).

Erros dentro de um pipe: PIPESTATUS

Num pipe, $? é o código do último comando. O array PIPESTATUS guarda todos, da esquerda para a direita:

$ grep 500 Documentos/acesso.log | wc -l
0
$ echo "${PIPESTATUS[@]}"
1 0                                            « grep: não achou (1); wc: ok (0)

Ele é refeito a cada comando, até por um echo. Para usar mais de uma vez, copie para outro array logo em seguida:

$ grep 404 Documentos/acesso.log | cut -d' ' -f1 | sort
192.168.0.57
$ codigos=("${PIPESTATUS[@]}")
$ echo "grep=${codigos[0]} cut=${codigos[1]} sort=${codigos[2]}"
grep=0 cut=0 sort=0

Se só interessa "alguma parte falhou?", o set -o pipefail é mais simples (veja Modo Estrito). PIPESTATUS serve quando você quer saber qual parte.

Limpar antes de sair

Se o script criou arquivos temporários e falhou no meio, eles ficam para trás. Em vez de lembrar de apagar antes de cada exit, registre a limpeza uma vez só com trap … EXIT: o Bash a executa sempre que o script terminar, com erro ou não. Isso tem uma aula própria: trap e Sinais.

Quando não funciona

O script sai com erro mesmo quando dá certo 
$ cat chaves-erradas.sh
#!/usr/bin/env bash
cp frutas.txt ~/backup/ || echo "a cópia falhou" >&2; exit 1
echo "Cópia feita!"
$ bash chaves-erradas.sh
$ echo $?
1                                              « a cópia funcionou, mas o script saiu com 1

O que aconteceu: o ; encerra a lista cp || echo. O exit 1 é um comando separado, que roda sempre.

Como resolver: agrupe com chaves: cp … || { echo "…" >&2; exit 1; }, ou use a função erro.

O exit não sai do script 
$ cat parenteses.sh
#!/usr/bin/env bash
cp nada.txt ~/backup/ || ( echo "a cópia falhou" >&2; exit 1 )
echo "Cópia feita!   (ué, o exit não saiu?)"
$ bash parenteses.sh
cp: não foi possível obter estado de 'nada.txt': Arquivo ou diretório inexistente
a cópia falhou
Cópia feita!   (ué, o exit não saiu?)
$ echo $?
0

O que aconteceu: os parênteses criam um subshell, um "shell filho". O exit 1 encerrou o filho, e o script continuou.

Como resolver: troque ( … ) por { …; }. O mesmo vale para um exit dentro de $( ) ou de um pipe: ele não sai do script.

Redirecionei a saída e a mensagem de erro foi parar no arquivo

O que aconteceu: o script escreve o erro com echo normal (canal 1). Com ./script.sh > resultado.txt, o erro vai junto com os dados e ninguém vê.

Como confirmar: rode com 2>/dev/null. Se a mensagem de erro continuar aparecendo, ela está no canal errado.

Como resolver: acrescente >&2 em todo echo/printf de erro, ou concentre tudo numa função erro.

Não apareceu nada, e o código é 1

O que aconteceu: um comando falhou com set -e ligado e o script parou antes de chegar às suas mensagens. Isso é comum com grep, diff e ((n++)), que devolvem 1 sem ser um erro de verdade.

Como resolver: rode bash -x script.sh para ver a última linha executada (Depurar) e trate essa falha (|| true, ou um if). Para sempre saber a linha, use o trap … ERR de trap e Sinais.

Resumo

  • Cada passo que pode falhar precisa de uma decisão: if cmd, cmd || erro "…" ou cmd || true.
  • Mensagens de erro vão para o canal 2 (>&2) e começam com o nome do script (${0##*/}).
  • Uma função erro junta mensagem e exit; use chaves { }, nunca parênteses, para agrupar.
  • Códigos: 0 sucesso, 1 erro, 2 uso errado, 64–78 se quiser detalhar; 126, 127 e 128+N são do Bash.
  • Valide argumentos ($#), arquivos (-e -f -r) e programas (command -v) antes de começar. PIPESTATUS mostra qual parte do pipe falhou.
